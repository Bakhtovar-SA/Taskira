# Безопасные миграции Taskira

Эта политика обязательна для on-prem релизов. После передачи архива у команды
может не быть доступа к серверу клиента, поэтому миграция должна либо примениться
целиком, либо оставить базу совместимой с предыдущим образом.

## Expand / contract

Изменение схемы, заменяющее существующие данные или контракт, делится минимум на
два релиза.

1. **Expand:** добавить nullable-колонку, новую таблицу или новый индекс без
   удаления старого объекта. Код этого релиза должен понимать старую схему,
   выполнить безопасный повторяемый backfill и начать писать в обе версии
   данных, если это необходимо.
2. Выпустить и проверить expand-релиз на реальных инсталляциях. Предыдущий образ
   должен по-прежнему запускаться на расширенной схеме.
3. **Contract:** только в следующем релизе прекратить чтение старого объекта и
   удалить его отдельной миграцией.

Нельзя удалять или переименовывать колонку в том же релизе, в котором появилась
её замена. Переименование выполняется как «добавить → скопировать/двойная запись
→ выпустить → удалить старое в следующем релизе», а не через `RENAME COLUMN`.

Опасные contract-операции `DROP COLUMN`, `DROP TABLE` и `ALTER ... TYPE`
разрешены только со строкой непосредственно в том же SQL-файле:

```sql
-- contract-phase: подтверждено, добавлено в релизе 1.8.0
```

Версия после слов `в релизе` — expand-релиз, уже доставленный клиентам. Наличие
маркера проверяет CI; оно не заменяет ревью совместимости со старым образом.

## Транзакционность и восстановление

`server/src/db.ts` применяет каждый файл миграции на одном соединении внутри
отдельных `BEGIN` / `COMMIT`. При любой ошибке выполняется `ROLLBACK`, а запись в
`schema_migrations` создаётся в той же транзакции. Поэтому:

- не добавляйте `BEGIN`, `COMMIT` или `ROLLBACK` внутрь SQL-файла;
- одна миграция должна содержать только изменения, которые PostgreSQL допускает
  в транзакции;
- backfill должен быть идемпотентным и ограниченным понятным условием;
- до удаления данных должен существовать проверенный expand-релиз и резервная
  копия согласно эксплуатационной инструкции.

DDL, который нельзя выполнить в транзакции (например,
`CREATE INDEX CONCURRENTLY`), нельзя просто добавить в существующий раннер. Для
такого исключения PR обязан:

1. начинать файл строкой `-- migration-transaction: none`;
2. содержать строку `-- recovery: ...` с точными идемпотентными командами
   определения и удаления частично созданного объекта;
3. добавить поддержку этого режима в собственный раннер Taskira и
   автоматическую проверку восстановления после искусственного обрыва;
4. описать действия в release notes.

Пока такой режим не реализован и не проверен, используйте транзакционный вариант
DDL (например, обычный `CREATE INDEX`) или не включайте изменение в релиз.

## Имена и неизменяемость

Существующие миграции `001_*.sql`–`029_*.sql` являются историей установленных
систем: их нельзя переименовывать, редактировать или переиспользовать.

Каждая новая миграция получает UTC timestamp с точностью до минуты:

```text
20260919T1200_add_x.sql
YYYYMMDDTHHMM_kratkoe_imya.sql
```

Допустимы строчные латинские буквы, цифры и `_`. Timestamp-имена
лексикографически идут после старых числовых имён и устраняют конфликт, когда две
ветки одновременно выбирают следующий последовательный номер.

## Чек-лист PR

- Файл имеет timestamp-имя и не меняет существующую миграцию.
- Изменение аддитивно либо contract-маркер ссылается на уже выпущенный
  expand-релиз.
- SQL транзакционный; для исключения выполнены все требования выше.
- Новый образ проверен на схеме до миграции, предыдущий образ — на схеме после
  expand-миграции.
- Backfill можно безопасно повторить.
- Оценены блокировки и объём свободного места.

## Снимок на релиз

Перед каждым релизом добавьте новый неизменяемый снимок в
`fixtures/db-snapshots/` с помощью `server/scripts/create-db-snapshot.mjs`.
Job `upgrade from snapshot` автоматически обнаруживает все `.sql` в каталоге и
для каждого проверяет восстановление, применение миграций, запуск сервера,
health/login и сохранность probe-данных. Старые снимки не удаляются: они задают
поддерживаемые опорные точки последовательного обновления.
