# Ключи лицензии (ТЗ 4.3)

Механизм — `server/src/services/license.ts`. Формат токена и обе причины, по которым это ТЗ
явно требовало `kid` и подсчёт мест по активности с первого дня, а не как доработку потом, —
в файловом комментарии `license.ts`. Здесь — только эксплуатация ключевой пары: где хранится
приватный ключ, кто имеет доступ, как ротируется, что делать при утечке.

## Формат

Токен — `header.payload.signature`, каждая часть — base64url. `header = {alg: "RS256", kid}`.
`payload` — `LicenseClaims` (`server/src/services/license.ts`): `plan`, `maxSeats`, `features[]`,
`activeWindowDays`, необязательный `issuedTo`, `iat`, `exp` (все временные метки — unix-секунды).
Подписывается RSA-парой, отдельной от `JWT_SECRET` пользовательских сессий — та симметрична и
общий секрет процесса, лицензия асимметрична и приватная половина никогда не покидает вас.

## Где хранится приватный ключ

Приватный ключ **никогда не коммитится** — ни в этот репозиторий, ни в форк, ни в issue/PR. Он
живёт только там, где вы сами решите (менеджер паролей с приватными заметками, отдельный
зашифрованный том, аппаратный токен) — репозиторий и CI намеренно не содержат для него никакого
хранилища, чтобы не создавать иллюзию, что оно уже есть. Публичная половина той же пары —
**не секрет** и коммитится в `server/src/licenseTrustedKeys.ts`, под своим `kid`.

## Кто имеет доступ

Только вы (единственный человек, выпускающий лицензии на момент этого ТЗ — юридический владелец
продукта, см. `docs/tickets/` Трек 0). Если/когда появится второй человек с правом выпуска —
отдельный ключ со своим `kid`, не общий доступ к одному файлу: так утечка/уход одного человека не
требует перевыпуска чужих лицензий.

## Как выпустить лицензию

```bash
cd server
npx tsx scripts/generate-license.ts \
  --private-key /path/to/2026-09.pem --kid 2026-09 \
  --plan pro --max-seats 500 --expires-in-days 365 \
  --active-window-days 30 \
  --features sso,sprints \
  --issued-to "Название клиента"
```

Выводит подписанный токен в stdout. `--active-window-days` — окно "активности" для подсчёта
занятых мест (см. `license.ts`), дефолт 30, если не указан. Это поле подписанного документа, а не
конфигурация сервера — зафиксируйте согласованное с клиентом N здесь же, при выпуске, и в
переговорном документе, а не оставляйте неявным.

## Как установить лицензию на инсталляции клиента

```bash
cd server
DATABASE_URL=... npx tsx scripts/install-license.ts '<токен>'
```

Скрипт проверяет токен локально перед записью (та же проверка, что использует работающий сервер)
и пишет его в `instance.license_key`. Изменение подхватывается проверкой лицензии в течение суток
или сразу при следующем перезапуске сервера — обновление кэша между процессами не нужно, `license.ts`
читает `instance.license_key` напрямую при каждой проверке (см. комментарий `getLicenseStatus()`).

## Ротация ключа

1. Сгенерировать новую RSA-пару (`openssl genrsa -out 2027-01.pem 2048 && openssl rsa -in 2027-01.pem -pubout -out 2027-01.pub.pem`).
2. Добавить публичную половину в `server/src/licenseTrustedKeys.ts` под новым `kid` — **не удаляя**
   старую запись.
3. Задеплоить эту версию сервера клиентам **до** того, как им будет выпущена первая лицензия новым
   ключом — иначе их сервер ответит `unknown_kid` на новый токен, которого ещё не знает.
4. Новые лицензии — выпускаются новым ключом/`kid`. Старые лицензии, выпущенные предыдущим ключом,
   продолжают проверяться и работать без изменений до истечения — `licenseTrustedKeys.ts` доверяет
   обоим `kid` одновременно, ровно для этого.
5. Старую запись в `licenseTrustedKeys.ts` можно удалить только после того, как истекли **все**
   лицензии, когда-либо выпущенные этим `kid` — реестр kid’ов растёт медленно, это ожидаемо, не
   «мусор для уборки».

## При компрометации приватного ключа

1. Немедленно сгенерировать новую пару с новым `kid` (шаги 1–3 ротации выше), считая это срочным,
   не плановым, релизом.
2. Перегенерировать (`generate-license.ts`) и разослать новые токены всем клиентам, чьи лицензии
   выпущены скомпрометированным ключом, тем же `plan`/`maxSeats`/сроком, что были — только новым
   `kid`.
3. Скомпрометированный `kid` **не удаляется** из `licenseTrustedKeys.ts` немедленно: если удалить
   его раньше, чем все клиенты обновят сервер и установят новый токен, их старые (всё ещё технически
   валидные с точки зрения подписи) лицензии перестанут проверяться раньше времени — сервер ответит
   `unknown_kid` там, где токен на самом деле был легитимным на момент выпуска. Удалить запись можно
   только после того, как все затронутые инсталляции подтверждённо перешли на новый токен.
4. Задокументировать инцидент отдельно (дата компрометации, дата ротации, список затронутых
   инсталляций) — вне этого файла, он про механизм, не про историю конкретных утечек.

## Что этот механизм не делает

Не проверяет ничего через сеть ("phone home") — офлайн-инсталляция без интернета (см.
`docs/adr/0009-database-per-tenant.md`, `DOCKER_SETUP.md`) должна продолжать работать. Не блокирует
работу при истечении — только пишет предупреждение в `audit_log` (`license.expired`,
`license.invalid`, `license.seats_over_limit` — `checkLicenseAndWarn()`, запускается при старте
сервера и раз в сутки). UI-предупреждение администратору и подключение `requiresPlan()` к реальным
фичам — намеренно вне этого ТЗ (план v2, ТЗ 4.3, «Что НЕ делать»); инфраструктура готова, точки
подключения — отдельная задача.
