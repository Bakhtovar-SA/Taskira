# Развитие Taskira — референс и проверка

## Результат

[Руководство по функциям и рабочим сценариям](../../WORKSPACE.md) описывает реализованное поведение.
[ADR-0037](../../adr/0037-project-workspace.md) фиксирует архитектуру и ограничения.
[reference.html](reference.html) — самостоятельный кликабельный референс на демонстрационных данных.
Он не обращается к API, CDN или облачным сервисам. Изменения референса не меняют рабочую Taskira.

Референс содержит библиотеку, редактор, версии и комментарии, реестр и карточку объекта,
конструктор процессов, выполнение с журналом, планирование, сценарий со срочной работой и каталог файлов проекта.
Вверху выбираются три сценария, тема, узкая компоновка и состояния потери связи, ошибки,
пустого раздела и чтения. Кнопка «Следующий шаг» проводит по сценарию. Формы подтверждаются
в диалоге; экспорт создаёт локальный JSON. Данные референса сбрасываются при перезагрузке.

CSS-токены скопированы из текущего `src/styles/tokens.css` воспроизводимым скриптом:

```sh
node scripts/sync-workspace-reference.mjs
node scripts/sync-workspace-reference.mjs --check
```

Функциональные референсы из утверждённого плана:

- [Владельцы и актуальность Notion](https://www.notion.com/help/wikis-and-verified-pages).
- [Комментарии и обратные ссылки Notion](https://www.notion.com/help/comments-mentions-and-reminders).
- [Карточка записи Airtable](https://support.airtable.com/articles/5805061650-Airtable-interface-layout%3A-Record-detail).
- [События и действия Asana](https://developers.asana.com/reference/rules).
- [График выполнения Linear](https://linear.app/docs/project-graph).

## Проверки

Серверный набор `workspace.test.ts` проверяет доступ, версии, подтверждения, архив,
типизированные поля, конфликты, связи, неизменяемые версии процессов, параллельность, проверяющего,
ветвление и объединение веток, потерю прав, паузы, переоткрытие, повторы событий, устойчивые ключи,
напоминания, события пользовательских полей, изоляцию сценариев, нормализацию этапов и прогнозы.

`workspaceCollaboration.test.ts` использует настоящие WebSocket: два автора, наблюдатель,
разрыв связи, синхронизация накопленных правок, запись в БД, перезапуск API и восстановление версии.
Все новые маршруты внесены в общую матрицу доступа и межпроектную проверку реальных вложенных ID.

Для интеграционных тестов нужна отдельная PostgreSQL БД с именем `taskira_test…`,
UTF-8 и Unicode-локалью. `C` некорректно проверяет регистронезависимое сравнение кириллицы.
Тесты одной БД нельзя запускать параллельно.

```sh
npm run typecheck
npm --prefix server run typecheck
npm test
npm --prefix server test
npm run permissions:check
npm run docs:check
npm run colors:check
npm run motion:check
npm run build
npm run bundle:check
```

Сквозная проверка на реальном API и production CSP:

```sh
# DATABASE_URL_TEST — отдельная БД с префиксом taskira_test_workspace_e2e.
# Тестовый сервер пересоздаёт только свои данные, не использует рабочую БД.
npm run build
npx playwright test --config playwright.workspace.config.ts
```

Тестовый API слушает loopback 28181, preview — 28182 (либо `PLAYWRIGHT_PORT`, например 28184 при работающем стенде). Семь проверок проходят три рабочих
сценария и самостоятельный референс; скриншоты сохраняются в `test-results/`.
Проверяются задача из выделения, живой статус, комментарии, версии, таблица под CSP,
отложенное создание этапов, подтверждение, прямые ссылки, обновление, узкий экран, обе темы, клавиатура, включение модулей менеджером и ленивая загрузка редактора.
Точная сводка итогового прогона находится в [verification.md](verification.md).

## Размер и поставка

[bundle.json](bundle.json) содержит фактические размеры gzip. Начальная загрузка и
ленивый редактор ограничены отдельно; историческая база и лимит entry сохранены.
Обоснование нового бюджета: [PERF-BUDGET.md](../PERF-BUDGET.md).

Стандартные Dockerfile, offline release и штатный backup сохраняются. Для документов
nginx использует те же потоковые upload-ограничения, а sweeper учитывает новые файлы.
Новые SQL-таблицы и бинарные CRDT-состояния входят в полный PostgreSQL-бэкап.
Перед включением в production примените миграцию на проверочной копии и выполните штатную
репетицию восстановления БД вместе с используемым файловым хранилищем.
