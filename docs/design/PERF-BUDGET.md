# Taskira — бюджет производительности трека UX

Решение ТЗ 5.2, 25.09.2026. Бюджет действует на весь трек UX (ТЗ 5.x): любая задача трека, которая его нарушает,
либо чинит нарушение, либо явно пересматривает цель здесь (с причиной и датой). Связанные решения:
[ADR-0010](../adr/0010-dynamic-styles-under-csp.md) (динамические стили под CSP),
[ADR-0011](../adr/0011-store-selector-subscriptions.md) (перерисовки, стор).

## Эталонная машина

Intel Core i3-N305, 8 ГБ ОЗУ, Chromium (актуальный стабильный). Цели ниже — для неё.

**Важно:** на эталонной машине замеры **не проводились** — её нет в среде разработки. Все цифры «сейчас» сняты в
контейнере разработки: Intel Xeon 2.1 ГГц × 4 vCPU, Chromium 141, production-сборка под production CSP, API замокан
(ответ ≈ 3–6 мс). Столбец «CPU 4×» — то же с замедлением CPU через CDP: грубая пессимистичная граница, а не модель
i3-N305. Первый прогон на эталонной машине — `scripts/perf-board/run.mjs` там же, результат дописать сюда.

## Цели и точка отсчёта

Сценарий доски — 3 колонки × 100 карточек (300 видимых), как в целевом «≥ 50 fps на 300 карточках».

### Что стоит за нарушениями

- **п. 2.** Подсветка колонки под курсором — `setState` в `Board`, а `Board` передаёт в `memo(Card)` новые колбэки и
  массивы на каждый рендер: каждый кадр перерисовываются все 300 карточек (2 861 компонент, замер ADR-0011).
  Контрольная строка 2′ показывает цену: ≈ 13–16 мс на кадр. Лечится шагом 0 ADR-0011 (стабильные пропсы карточки)
  — он не зависит от переделки стора.
- **п. 3, первое открытие.** Чанк `IssueModal` грузится лениво при первом клике (8.5 КБ gzip) плюс три запроса
  (задача, комментарии, история) и перерисовка всего дерева по `setUi`/`setData`. Варианты — предзагрузка чанка в
  простое (`requestIdleCallback` / при наведении на карточку) и шаги 3–4 ADR-0011; выбрать при реализации.
- **п. 5.** На карточках доски ключ задачи набран JetBrains Mono (ADR-0012 п. 5), поэтому первый экран доски тянет
  третий файл. Экран входа и главная не замерялись (на главной в «Моих задачах» тоже есть ключи). Решение за
  владельцем трека: либо цель «≤ 2» относится только к экрану входа, либо ключи на доске переходят на табличные цифры Onest
  (моно остаётся в карточке задачи), либо моно сабсетится и встраивается в Onest-файл. Пока — зафиксированное
  нарушение.

## Бюджет бандла (п. 4)

База — сборка коммита 7d500ad (ТЗ 5.4) без изменений кода продукта в ТЗ 5.2. gzip — `node:zlib` с уровнем по
умолчанию (совпадает с отчётом Vite).

| метрика | база | допуск роста за трек | потолок |
|---|---|---|---|
| JS + CSS | 196.49 КБ | **+80 КБ** — цель трека | 276.49 КБ |
| JS, все чанки | 183.09 КБ | +80 КБ | 263.09 КБ |
| CSS | 13.39 КБ | +20 КБ | 33.39 КБ |
| входной чанк `index-*.js` | 79.14 КБ | +40 КБ | 119.14 КБ |

Справочно (не проверяется): JS до первого экрана — вход + `modulepreload` (`ui-*.js`, `issuePages-*.js`) — 127.88 КБ.
Крупнейшие чанки: `index` 79.1, `ui` 46.9, CSS 13.4, `DocsView` 11.2, `IssueModal` 8.5, `Backlog` 6.4 КБ.
Шрифты (не входят в бюджет, у них п. 5): Onest cyrillic 15.9, Onest latin 33.8, JetBrains Mono latin 40.4 КБ woff2;
зерно `grain.png` 25.1 КБ.

Допуск на входной чанк — половина общего: он на критическом пути первого экрана. CSS отдельно ограничен 20 КБ, чтобы
рост стилей не «съедался» запасом JS.

### Проверка в CI

`scripts/check-bundle-size.mjs` (`npm run bundle:check`) читает `dist/assets/*.js|*.css`, сжимает каждый файл gzip,
считает JS, CSS, JS+CSS и входной чанк (скрипт из `dist/index.html`) и сравнивает с `base + allowedGrowth` из
`scripts/bundle-budget.json`; превышение любой метрики — код выхода 1. В `.github/workflows/test.yml` (job `client`)
шаг идёт сразу после `npm run build`.

Мутационная проверка (25.09.2026):
- входной чанк: `base.entry` уменьшена на 1 КБ, допуск 0.5 КБ → «входной чанк = 79.14 KB > 78.64 KB», код 1;
- рост бандла: в `dist/assets` добавлен несжимаемый чанк на 96 КБ gzip → «JS + CSS = 292.94 KB > 276.49 KB» и
  «JS, все чанки = 279.54 KB > 263.09 KB», код 1; при +64 КБ — в пределах, код 0;
- после отката — код 0.

Ловушка, найденная при замере базы: Tailwind v4 сам ищет классы во **всех** файлах репозитория, включая `docs/*.md`
и тесты. Упоминание at-правила контейнерного запроса (слово container с «собакой» впереди) в документации добавило в
production CSS одноимённую утилиту (+16 байт gzip; здесь оно намеренно не написано буквально); классы в тестовых стендах — тоже. Бюджет такое ловит, если рост заметный; мелочь видна в выводе
как ненулевой рост CSS при неизменённом коде.

Как менять базу: `node scripts/check-bundle-size.mjs --update` переписывает `base` текущими размерами. Делать это
только вместе с правкой этого документа (новая точка отсчёта — новое решение), не чтобы «пройти CI».

## Как мерить

| что | команда | где цифры |
|---|---|---|
| бандл | `npm run build && npm run bundle:check` | вывод + `scripts/bundle-budget.json` |
| перерисовки (jsdom, число компонентов) | `npm run perf:rerenders` | таблицы в выводе, ADR-0011 |
| кадры, открытие задачи, шрифты, CSP (браузер) | `npm run build`, затем `SPIKE_NODE_MODULES=… CHROMIUM_PATH=… node scripts/perf-board/run.mjs` (шапка файла) | JSON в выводе |
| CSP-механизмы стилей | `SPIKE_NODE_MODULES=… npm run csp:spike` | таблица в выводе, ADR-0010 |

`perf:rerenders` идёт и в обычном `npm test` — без порогов, только «замер состоялся»: цифры видны, но улучшение или
ухудшение CI не роняет. Порог на число перерисовок имеет смысл ввести после шагов 0–2 ADR-0011, когда цифра станет
стабильной и маленькой.
