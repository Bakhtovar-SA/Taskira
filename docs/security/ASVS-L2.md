# Самопроверка по OWASP ASVS 5.0, уровень 2 (серверная часть)

**Тикет:** SEC-ASVS-01 (Трек M, §M1) · **Дата:** 2026-10-06 · **Ветка кода:** `main` на коммите `ed362c8`

> **Это самопроверка разработчика, не аудит.** Её провёл тот же коллектив, который писал код, чтением кода и точечными
> пробами; независимой верификации нет. Внешний аудит — отдельный тикет **SEC-EXT-01**: этот документ входит в его пакет
> и должен считаться утверждением, которое аудитор проверяет, а не доказательством, которому он верит.

## 1. Что именно проверялось

**Источник требований.** OWASP ASVS **5.0.0** (английская редакция), файл
`OWASP/ASVS/5.0/docs_en/OWASP_Application_Security_Verification_Standard_5.0.0_en.csv` в репозитории
<https://github.com/OWASP/ASVS> (ветка `master`, получен 2026-10-06; колонки `req_id`, `req_description`, `L`).
Нумерация и формулировки взяты из него; в таблицах формулировка воспроизведена дословно и **сокращена** до ~170 символов
(полный текст — по номеру в CSV). Перевода или пересказа требований нет.

**Уровень 2** понимается как все требования, у которых в колонке `L` стоит 1 или 2 (требования L3 в охват не входят).

**Расхождение в нумерации глав.** В тексте тикета главы названы так: V1 кодирование/инъекции, V2 валидация, V6 аутентификация,
V7 сессии, V8 авторизация, V9 токены, **V12 файлы, V13 API, V14 конфигурация**. Это схема ASVS 4.0. В ASVS 5.0 те же номера
означают другое: **V12 «Secure Communication» (TLS), V13 «Configuration», V14 «Data Protection»**, а загрузка файлов — **V5**,
API/WebSocket — **V4**. Проверены главы **по номерам из тикета в нумерации 5.0** — V1, V2, V6, V7, V8, V9, V12, V13, V14
(136 требований L1–L2) — и, поскольку тикет явно называет загрузку файлов и API целями проверки, дополнительно
**V4 и V5** (19 требований, раздел 6). Главы V3 (веб-фронтенд), V10 (OAuth/OIDC), V11 (криптография), V15, V16, V17
не проверялись.

**Метод.** Чтение кода `server/src` (`auth.ts`, `middleware.ts`, `config.ts`, `app.ts`, `sessionCookie.ts`,
`passwordPolicy.ts`, `routes/*`, `services/{attachments,fileGuard,ldap,userProvisioning,apiTokens,egress,emailTemplates}.ts`),
`nginx.conf`, `docker-compose.yml`, `server/Dockerfile`, `deploy/https/`, `docs/SECURITY_OVERVIEW.md`; сверка с тестами
`server/test`; статический скан всех объявлений маршрутов на наличие guard и `zbody`; три воспроизводимых пробы
(JWT-токены против `@fastify/jwt` 10.2.2, `bcryptjs` 2.4.3 и `checkUpload` на сконструированных входах — помечены
«проба вне репозитория» в таблицах; сами скрипты в репозиторий не добавлены).

**Чего не делалось.** Серверный набор тестов не запускался (в среде нет PostgreSQL), ссылки на тесты — по чтению их кода.
Динамического сканирования (ZAP, фаззинг) не было. Клиентский код (`src/`) читался только точечно там, где требование
касается его прямо (поле пароля, `localStorage`). Инфраструктура клиента (host-nginx, ОС, файрвол, резервное копирование)
вне кода и проверена только по документам поставки.

**Статусы.**

| Статус | Значение |
|---|---|
| выполнено | механизм прочитан в коде (`файл:строка`) и/или подтверждён тестом либо пробой; в столбце «Доказательство» указано, чего именно не хватает (например «автотеста нет») |
| частично | механизм есть, но не полностью, не документирован или не подтверждён так, как требует ASVS |
| нет | механизма нет |
| неприменимо | технология/функция в продукте не используется (с причиной) |

Правило из тикета соблюдено: «выполнено» не ставилось без ссылки на код, тест или пробу. Для требований, где защита есть
только в коде без теста, это сказано явно и заведён **SEC-TEST-01** / профильный тикет.

## 4. Самые серьёзные находки

1. **Нет смены и сброса пароля у локальных пользователей** (V6.2.2, V6.2.3, V6.4.1, V6.4.3, V7.4.3) — **high**, [SEC-PWD-01](../tickets/SEC-PWD-01-local-password-change-reset.md).
   Пароль задаёт и знает администратор, пользователь сменить его не может, забытый — восстановить. Для клиентов без LDAP это основной режим.
2. **Транспорт «из коробки» небезопасен** (V12.2.1, V12.3.1) — **medium**, [SEC-TLS-01](../tickets/SEC-TLS-01-transport-security-defaults.md).
   Штатная поставка — HTTP, `Secure`-кука по умолчанию выключена, LDAP принимается без StartTLS (пароли по сети открытым текстом), PostgreSQL без TLS; предупреждений при старте нет.
3. **Политика паролей противоречит ASVS 5.0 и тихо усекает пароль** (V6.2.4, V6.2.5, V6.2.8, V6.2.9) — **medium**, [SEC-PWD-02](../tickets/SEC-PWD-02-password-policy-vs-asvs.md).
   Три группы символов обязательны (ASVS это запрещает), списка топ-3000 нет, `bcryptjs` учитывает 72 байта (проба: 40 кириллических символов совпадают с первыми 36 + «x»).
4. **Загрузка файлов: центральный guard без автотестов, нет антивирусной проверки** (V5.2.2, V5.4.3) — **medium**, [SEC-FILE-01](../tickets/SEC-FILE-01-attachment-guard-tests-av-hook.md).
5. **Сессии без тайм-аута неактивности, без списка и принудительного завершения** (V7.3.1, V7.4.5, V7.5.2) и JWT в теле ответа входа — **medium**, [SEC-SESS-01](../tickets/SEC-SESS-01-session-lifecycle-controls.md).
6. **Нет второго фактора для локального режима и защиты аварийного входа от блокировки** (V6.3.3, V6.1.1, V6.3.2) — **medium**, [SEC-AUTH-01](../tickets/SEC-AUTH-01-second-factor-local-mode.md), [SEC-AUTH-02](../tickets/SEC-AUTH-02-auth-pathways-lockout-identity.md).
   Break-glass администратор по умолчанию называется `admin` (compose и все `.env.example`), поэтому его имя известно заранее, а заблокировать его может любой, кто видит форму входа.
7. **Секреты — открытым текстом в `.env`, одна роль БД на миграции и рантайм** (V13.2.2, V13.3.1) — **medium**, [SEC-CFG-02](../tickets/SEC-CFG-02-secrets-db-privileges-egress.md).
8. **Доступ по объектам подтверждён выборочно** (V8.2.1, V8.2.2): все маршруты, кроме трёх публичных, имеют guard (статический скан), но полного манифеста «маршрут × роль» нет — **SEC-IDOR-01** (Трек M, в работе у другого исполнителя).

Положительное: параметризованные SQL-запросы без найденных исключений; единый серверный слой авторизации с ролью из БД, а не из токена;
отзыв сессий через `session_version` (logout, деактивация, смена роли); хеш секрета API-токена, 256 бит, сравнение постоянного
времени; вложения отдаются потоком через API как `attachment` + `nosniff`; allowlist исходящих целей вебхуков; лимиты и блокировка входа.

## 8. Честные пробелы самопроверки

- **Тесты не запускались.** Без PostgreSQL набор `server/test` не выполнялся; ссылки на тесты означают, что я прочитал их код и он проверяет заявленное, а не что они зелёные на `ed362c8`.
- **Динамики нет.** Ни сканера, ни ручного пентеста работающего стенда; пробы JWT/`bcryptjs`/`checkUpload` — на библиотеках и чистых функциях, не на живом сервере.
- **Клиент не покрыт.** V3 и клиентские части V7.4.4, V14.3 — поверхностно; рендеринг пользовательского текста в браузере не проверялся.
- **Инфраструктура оператора** (host-nginx, TLS, файрвол, права на `.env`, шифрование дисков) оценена по документам поставки, не по реальной установке.
- **Зависимости.** Транзитивные библиотеки (AWS SDK, nodemailer, ldapts) не разбирались; их покрывает `npm audit`/Trivy в CI.
- **SQL.** Отсутствие инъекций установлено чтением шаблонов `${…}` в запросах и закрытостью их источников; автоматического гарда нет (SEC-TEST-01).
- **Код Трека L** проверен только пересечениями (раздел 2); SSRF-ревизия не проведена.
- **Утверждения в `CLAUDE.md`** местами отстают от кода (например, про «не awaited» запись аудита: `audit.ts` теперь ждёт `INSERT`); я опирался на код, а не на описание.
- Оценки severity в тикетах — рабочие, для приоритизации внутри команды; внешний аудитор вправе оценить иначе.
