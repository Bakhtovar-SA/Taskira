# Realtime-синхронизация задач

Изменения задач доходят до открытого проекта через WebSocket. Клиент перечитывает
актуальные данные по HTTP и сохраняет курсор после успешной сверки кеша задач и
необходимых метаданных. Списки и счётчики обновляются отдельными фоновыми запросами;
периодическая сверка повторяет их, в том числе после временной ошибки чтения.
После обрыва сети или перезапуска API он восстанавливает пропущенные изменения.
При недоступном WebSocket видимая вкладка сверяет данные каждые 20 секунд, а также
при возвращении фокуса и восстановлении сети.

## Надёжная доставка

Миграция `20261102T1000_realtime_sync.sql` добавляет две отдельные таблицы:

- `realtime_pending`: триггеры пишут идентификаторы изменённых задач в транзакции
  с изменением данных. Откат транзакции откатывает и событие. Удалённые задачи
  оставляют идентификатор, чтобы клиент мог убрать их из кеша.
- `realtime_events`: диспетчер переносит зафиксированные изменения в журнал
  доставки с последовательным курсором, объединяя изменения задач проекта.

Журнал независим от `integration_events` и подписок на вебхуки. Он охватывает
создание, изменение и удаление задач, связанные комментарии, историю, исполнителей,
участников, файлы, чек-листы, пользовательские поля и связи. Изменения метаданных
проекта создают сигнал полного обновления.

ID из `realtime_pending` нельзя использовать как курсор: транзакция с меньшим ID
может завершиться позже. Публичную последовательность назначает диспетчер после
фиксации исходной транзакции, под общей транзакционной advisory-блокировкой PostgreSQL.
Перенос в журнал и удаление pending-записей атомарны. Диспетчер и журнал не зависят
от памяти процесса: конкурентные обработчики сериализуются через PostgreSQL.
Однако штатный deployment Taskira по ADR-0024 по-прежнему разрешает один serving
API на базу и защищает это session-level блокировкой. Уведомления и некоторые кеши
прав остаются локальными. Этот realtime-слой не включает поддержку нескольких
serving API; тестовые проверки конкуренции журнала не меняют ограничение deployment.

Доставка допускает повторы. Событие сообщает, какие данные надо перечитать, и не
содержит готовую карточку для безусловного добавления. Повторное чтение не создаёт
дубликаты. Неприменённый курсор остаётся прежним и повторяется при восстановлении.
Локальная запись или смена проекта не позволяет применить устаревший HTTP-ответ.

## Протокол

После обычной cookie-аутентификации WebSocket сервер отвечает `auth_ok`. Сохраняется
поддержка первого сообщения `{ "type": "auth", "token": "…" }` для прежних клиентов.
На соединении активна одна подписка проекта; следующая заменяет предыдущую:

```json
{ "type": "sync:subscribe", "projectId": "UUID", "cursor": "1234" }
```

Для первого подключения `cursor` равен `null`. Сервер отправляет пакет:

```json
{
  "type": "sync",
  "projectId": "UUID",
  "cursor": "1235",
  "issueIds": ["UUID"],
  "reset": false,
  "ts": 1793606400000
}
```

Курсор — десятичная строка PostgreSQL bigint. Его нельзя преобразовывать в
JavaScript `number`. Это глобальная позиция журнала, поэтому номера событий
одного проекта могут иметь промежутки.

Клиент использует пакет WebSocket как сигнал для
`GET /api/projects/:projectId/sync?cursor=1234`. Ответ имеет ту же форму. Без
параметра `cursor` сервер возвращает полный сброс. HTTP-ответ запрещён к кешированию.
Пакеты объединяются короткой задержкой перед чтением, чтобы серия событий не
создавала отдельную перезагрузку данных для каждого изменения.

`reset: true` требует сверки текущего состояния, когда клиент подключился впервые,
изменились метаданные, курсор устарел или оказался впереди сервера, либо накопилось
больше 500 событий/идентификаторов. История хранится семь дней и очищается ограниченными
порциями. Последнее глобальное событие остаётся долговечным watermark. Истёкшая
история восстанавливается через текущее состояние, а не через полный журнал правок.

## Соединение, права и редактирование

При активных подписках сервер проверяет журнал каждые 500 мс. Фоновый диспетчер
работает каждые пять секунд и при отсутствии открытых досок. Сервер посылает
heartbeat каждые 25 секунд; не отвечающие соединения и медленные получатели с
буфером более 256 КиБ отключаются. Браузер переподключается с увеличением задержки
и jitter; после подключения перечитывает пропущенное со своего применённого курсора.
Если восстановление затянулось больше трёх секунд, существующая статусная полоса
показывает состояние синхронизации; отсутствие сети показывается сразу.

Перед каждой доставкой сервер заново проверяет актуальную сессию и право просмотра
проекта, обходя кеш прав. При потере доступа приходит `sync:denied`, при временной
ошибке — `sync:error`. При отзыве сессии соединение закрывается. Персональное
приглашение в одну задачу не даёт подписку на весь проект.

Списки и счётчики перечитываются с текущими фильтрами; открытая задача обновляет
детали, комментарии и историю. Несохранённые заголовок, описание и комментарий
остаются в редакторе. Изменение задачи и перевод статуса передают `expectedVersion`
на основе `updatedAt`; устаревшая запись получает HTTP 409. Для заголовка и описания
можно проверить актуальное значение и явно сохранить свой вариант. Текстовые и
числовые пользовательские поля также сохраняют черновик; `expectedValue` проверяется
атомарно при сохранении, чтобы не затирать параллельную правку того же поля.
Это не механизм совместного посимвольного редактирования и не очередь офлайн-записей.

## Проверки и эксплуатация

В комментариях основной карточки и приглашённой задачи `@` открывает ограниченный
список активных получателей. `GET /api/projects/:projectId/issues/:id/mention-candidates?q=…`
ищет по имени и логину под правом просмотра этой задачи. Список и серверная доставка
используют один предикат видимости: участники проекта, приглашённые к задаче и
глобальные администраторы; служебные записи и сам автор не предлагаются.
Выбор вставляет `@username`, после отправки комментария существующий механизм
`issue.mention` создаёт уведомление и push. Email зависит от настроек доставки.
Клавиатура: стрелки, Enter/Tab для выбора, Escape закрывает список; Ctrl+Enter
сохраняет обычную отправку. Несохранённый текст сохраняется при сбое поиска.

Раскрытие «Направления» в форме создания анимирует высоту в потоке формы и
закрывается без активных скрытых элементов. Системный и личный reduced motion
отключают движение. Браузерные проверки — `e2e/mentions-direction.pw.ts`.

Новых переменных окружения или сервисов нет. При обновлении сначала применяются
стандартные миграции и сервер с `/sync`, затем публикуется соответствующий клиент.
Обратный прокси должен пропускать WebSocket upgrade для `/api/ws`.
Существующее ограничение одного serving API на базу сохраняется.

`e2e/realtime.pw.ts` открывает два изолированных браузерных контекста с разными
пользователями: создание/перемещение/удаление и счётчики без навигации, обрыв сети
с replay, сброс после истечения истории, сохранность черновиков и разрешение 409.
HTTP и сокет контролируются установленным Playwright mock-harness; эти проверки
проверяют настоящий клиент, но не транзакции PostgreSQL. Журнал и реальный WebSocket
проверяются отдельно в `server/test/realtimeJournal.test.ts` и
`server/test/realtimeSocket.test.ts`.

```powershell
npx playwright test e2e/realtime.pw.ts --workers=1
npm run build
npx playwright test --config playwright.production.config.ts e2e/realtime.pw.ts --workers=1
```

Для диагностики следить за возрастом и размером `realtime_pending`, ростом
`realtime_events` и сообщениями `realtime dispatcher failed`, `realtime tick failed`,
`realtime subscription failed`, `realtime background drain failed`. Постоянно
растущая pending-очередь означает, что диспетчер не успевает или падает; повторные
ошибки `/sync` означают, что клиент ещё не подтвердил следующий курсор. Задержку
между фиксацией записи и появлением у второго пользователя надо измерять на
реальном стенде; интервал диспетчера сам по себе не является гарантией SLA.
