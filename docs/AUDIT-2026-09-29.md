### Исправления по ревью PR #102

- Подсеть Compose задана через `TASKIRA_NETWORK_CIDR` (default `172.30.0.0/24`).
  IPAM и `TRUST_PROXY` API получают одну переменную; Docker default-address-pools
  больше не может незаметно объединить всех клиентов в один IP bucket.
  Контейнерный smoke дополнительно проверяет альтернативную подсеть `10.253.250.0/24`.
- Соединение владения выполняет heartbeat каждые 10 с с таймаутом 5 с.
  Закрытие HTTP/WS, пула и владения ограничено общим сроком 10 с; Compose даёт
  15 с для остановки. Документация сервера описывает дополнительное соединение,
  PgBouncer и idle-timeout. Повторный захват при обслуживании без лока и освобождение
  лока до закрытия API сознательно не применены: оба нарушают гарантию одного serving API.
- LDAP сравнивает роль до/после UPDATE с ролью, прочитанной `FOR UPDATE` внутри
  общего лока администраторов. Детерминированные тесты локального adopt и LDAP-update
  меняют роль между исходным lookup и блокировкой и проверяют отзыв свежего WS/JWT.
- Неограниченное потоковое тело в nginx разрешено только на конечных путях загрузок;
  остальные API-запросы имеют предел 1 MiB. Для корпоративного LB добавлен include
  отдельной real-IP-конфигурации с ограниченными CIDR и пример mount в OPERATIONS.
- Исправлена причина первого падения container smoke: код ошибки API расположен
  в `body.error.code`. Старый CI подтвердил client/server/types/LDAP/SMTP/S3,
  visual, upgrade/rollback и backup/restore; security job остановился на этой
  ошибке проверки. Приёмка исправленного smoke подтверждается новым запуском CI.

Локально проверены 28 затронутых регрессионных тестов (26 успешных в первом
прогоне и все 7 concurrency-тестов в повторном), серверные типы и сборка,
release scripts и синтаксис smoke. В первых двух новых WS-тестах неверно
использовался строковый bigint `session_version`; тестовый JWT исправлен на число,
оба случая после этого прошли. Повторы не прибавляются к общему числу тестов.

### A01 — Неавторизованное WS-сообщение завершает API

**Место:** [ws.ts:82](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/ws.ts#L82), [ws.ts:93](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/ws.ts#L93).

`JSON.parse('null')` успешно возвращает `null`. TypeScript-приведение `as Partial<WsAuthMessage>` не валидирует данные. Доступ к `auth.type` происходит вне `try/catch` и бросает исключение из обработчика события `message`. Обработчик HTTP-ошибок Fastify это исключение не перехватывает.

**Условия:** доступ к `/api/ws`, соединение без cookie/токена, первое сообщение до истечения 5 секунд. Учётная запись не требуется.

**Фактический результат:** отдельный процесс завершился с exit code 1; стек указывает на `server/src/routes/ws.ts:93`, ошибка `Cannot read properties of null (reading 'type')`. Restart policy может поднять сервер снова, но повторные подключения повторяют отказ обслуживания.

**Исправление:** валидировать весь первый фрейм как объект с допустимыми полями, закрывать соединение с кодом 1008 при ошибке. Ограничить размер первого сообщения; обрабатывать исключения внутри event callback.

**Критерий приёмки:** `null`, число, строка, массив, повреждённый JSON, объект без token и слишком большой фрейм не завершают процесс; последующий `/health` отвечает. Валидная аутентификация продолжает работать.

### A02 — Подмена IP обходит лимит входа

**Места:** [nginx.conf:36](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/nginx.conf#L36), [docker-compose.yml:37](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/docker-compose.yml#L37), [app.ts:59](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/app.ts#L59), [auth.ts:73](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/auth.ts#L73), [loginRateLimit.ts:14](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/services/loginRateLimit.ts#L14).

nginx использует `$proxy_add_x_forwarded_for`, сохраняя переданный клиентом заголовок и добавляя реальный IP справа. Compose по умолчанию задаёт `TRUST_PROXY=true`; Fastify принимает левый адрес цепочки как `req.ip`. Именно он является ключом PostgreSQL-лимитера логина и попадает в аудит. Поведение nginx подтверждается [документацией переменной](https://nginx.org/en/docs/http/ngx_http_proxy_module.html#var_proxy_add_x_forwarded_for).

**Воспроизведение:** при одном `remoteAddress` и одном реальном клиенте `203.0.113.42` заголовки `198.51.100.10, 203.0.113.42` и `198.51.100.11, 203.0.113.42` дали соответствующие разные `req.ip`. Произвольная смена первого адреса создаёт новые buckets лимита. Полный сетевой прогон через контейнер nginx не выполнялся.

**Влияние:** обход IP-ограничения попыток, искажение IP в журнале. Локальная блокировка аккаунта остаётся дополнительным барьером; обход LDAP-защиты самой директории не утверждается. Если внешний доверенный прокси уже очищает этот заголовок, риск конкретной установки ниже, но стандартный прямой доступ к client-порту такой защиты не даёт.

**Исправление:** описать доверенную цепочку прокси. На внешней границе перезаписывать клиентский XFF; для Fastify доверять только известным прокси/CIDR. Согласовать изменения с `scripts/render-compose.sh`, из которого генерируется Compose.

**Критерий приёмки:** через настоящий nginx попытки с меняющимся XFF всё равно получают 429 после общего лимита; в audit записывается реальный адрес. Отдельно проверить установку за корпоративным LB.

### A03 — Загрузки больше примерно 1 MiB блокируются nginx

**Места:** [nginx.conf:31](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/nginx.conf#L31), [Dockerfile:30](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/Dockerfile#L30), [config.ts:329](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/config.ts#L329).

В поставляемом nginx-конфиге отсутствует `client_max_body_size`. Приложение допускает файл до 25 MiB по умолчанию. Стандартное значение nginx — `1m`; превышение тела запроса даёт 413 ещё до API. Это следует из [официального описания директивы](https://nginx.org/en/docs/http/ngx_http_core_module.html#client_max_body_size). Для multipart полезный размер файла немного меньше лимита тела.

**Влияние:** допустимое в UI вложение, например PDF размером 2 MiB, не загружается при стандартном развёртывании. Настройка `ATTACH_MAX_BYTES` сама по себе nginx не меняет. Локальный запуск API без nginx скрывает дефект.

**Исправление:** согласовать лимит nginx с максимально разрешённым телом multipart и накладными расходами; учитывать изменение env-лимита и другие upload-маршруты.

**Критерий приёмки:** проверки через собранный client image на 2 MiB, возле допустимого максимума и выше него. Превышение отклоняется с понятной ошибкой.

### A04 — Транзакция расчёта ранга не включает запись

**Места:** [rank.ts:55](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/services/rank.ts#L55), [rank.ts:77](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/services/rank.ts#L77), [issues.ts:697](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/issues.ts#L697), [issuesBulk.ts:53](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/issuesBulk.ts#L53).

`computeRank()` берёт advisory transaction lock, вычисляет число, делает COMMIT и возвращает его. Вызывающий маршрут пишет `issues.rank` позднее, в другом запросе. Поэтому второй расчёт после COMMIT первого, но до его UPDATE/INSERT, видит старые данные и получает то же число. Комментарий в сервисе об устранённой гонке не соответствует этой границе транзакции.

**Фактическое доказательство:** два вызова настоящего `computeRank` до записи, выполненные на TEMP-таблице, вернули `1000` и `1000`; после вставки результат `[{"rank":1000,"cards":2}]`. Это детерминированное воспроизведение допустимого чередования двух запросов, а не нагрузочный замер UI.

**Влияние:** порядок карточек определяется дополнительной сортировкой вместо ожидаемого положения; возможны скачки порядка после обновления.

**Исправление:** передавать общий PoolClient в расчёт ранга и удерживать лок до записи и COMMIT всего изменения. Проверить создание, одиночный переход и bulk.

**Критерий приёмки:** два конкурентных перемещения в одну позицию дают устойчивый порядок после перечитывания. Разные колонки сохраняют допустимый параллелизм.

### A05 — Конкурентные переходы обходят workflow

**Места:** [issues.ts:687](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/issues.ts#L687), [issues.ts:713](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/issues.ts#L713), [issuesBulk.ts:50](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/issuesBulk.ts#L50).

Текущий статус читается, затем отдельно проверяется `assertTransition`, после чего UPDATE фильтрует только по ID задачи. Нет блокировки строки на весь переход или условия `status_id = expectedStatus`.

**Чередование:** существуют A→B и A→C, но отсутствует B→C. Два запроса читают A и оба проходят проверку. Первый записывает B; второй затем записывает C. Фактический B→C не проверен. История второго перехода также записывает устаревший источник A. Bulk использует такую же схему. End-to-end конкурентный HTTP-тест в этом аудите не запускался.

**Исправление:** заблокировать и перечитать задачу внутри общей транзакции до проверки либо использовать optimistic concurrency и отдавать 409 при изменённом исходном состоянии. Согласовать порядок row/advisory locks с A04, чтобы не создать deadlock.

**Критерий приёмки:** описанный сценарий не допускает запрещённого фактического перехода; activity и done_at соответствуют принятой операции.

### A06 — Защита последнего администратора допускает write skew

**Место:** [users.ts:104](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/users.ts#L104).

Проверка «есть другой активный admin» встроена в UPDATE, но это не сериализует изменения разных строк. Две операции над последними администраторами A и B могут одновременно увидеть другого активным и обе снять права/активность. Каждая меняет собственную строку, поэтому общего row lock нет. Один SQL statement не гарантирует межстрочный инвариант при стандартном Read Committed; см. [модель изоляции PostgreSQL](https://www.postgresql.org/docs/16/transaction-iso.html).

**Влияние:** после двух успешно завершившихся административных операций может не остаться активного администратора; восстановление потребует служебного доступа. Это конкурентный сценарий, а не обычная последовательная правка. Отдельный API-тест с двумя одновременными понижениями не выполнялся.

**Исправление:** общий transaction advisory lock для операций, способных уменьшить число активных администраторов, затем проверка и UPDATE в одной транзакции; альтернативно Serializable с корректным retry. Проверить также пути изменения ролей через LDAP provisioning.

**Критерий приёмки:** два одновременных понижения/отключения оставляют минимум одного admin; один запрос получает конфликт.

### A07 — Экспорт не является согласованным снимком

**Места:** [dataExport.ts:135](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/dataExport.ts#L135), [dataExport.ts:149](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/dataExport.ts#L149), [dataExport.ts:161](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/dataExport.ts#L161), [db.ts:103](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/db.ts#L103).

Таблицы и страницы читаются отдельными `pool.query`; общий connection/snapshot не удерживается. После выгрузки таблицы issues может появиться новая задача с комментарием: таблица comments, читаемая позднее, уже содержит его, а задачи в файле нет. В OFFSET-таблицах удаление строки из предыдущей страницы сдвигает следующую и приводит к пропуску.

**Влияние:** административная NDJSON-выгрузка живой инсталляции может содержать несогласованные ссылки или неполные связи. Обычные тесты экспорта на неизменной БД этого не выявляют. Это замечание относится к HTTP-экспорту; `backup.sh` останавливает записи и использует pg_dump, поэтому у него другая модель согласованности.

**Исправление:** один выделенный клиент и read-only REPEATABLE READ transaction на генерацию экспорта; гарантированный rollback/release при отключении клиента; ограничение длительности. Для больших инсталляций рассмотреть фоновую подготовку файла, чтобы медленный клиент не держал snapshot бесконечно.

**Критерий приёмки:** конкурентные создание/удаление во время экспорта не нарушают ссылочную полноту полученного снимка; отмена скачивания освобождает соединение.

### A08 — В полном экспорте отсутствуют шаблоны задач

**Места:** [dataExport.ts:72](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/routes/dataExport.ts#L72), [022_issue_templates.sql:37](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/migrations/022_issue_templates.sql#L37), [issueTemplates.ts:33](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/services/issueTemplates.ts#L33).

В `KEYED_TABLES` и `OFFSET_TABLES` нет `issue_templates`. Это общие данные проекта с названием, полями и описанием шаблона. Они не относятся к явно исключённым личным настройкам. Наличие `project_templates` не покрывает действующие шаблоны задач каждого проекта.

**Влияние:** заявленная полная выгрузка рабочих данных не переносит настроенные командой шаблоны.

**Критерий приёмки:** созданный через API шаблон со всеми полями встречается в NDJSON и связан с правильным projectId.

### A09 — WS работает только внутри одного процесса

**Места:** [wsHub.ts:8](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/services/wsHub.ts#L8), [middleware.ts:155](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/middleware.ts#L155), [notify.ts:88](https://github.com/Bakhtovar-SA/Taskira/blob/f24e3d2b246e7882915b5566557b2338aa615a08/server/src/services/notify.ts#L88).

`byUser`, `revokedAt` и auth-cache находятся в памяти процесса. `emit()` вызывает локальный `pushToUser`; межпроцессного транспорта событий и отзывов не обнаружено. При WS на процессе B событие/логаут на A не достигает реестра B. Сокет на B может остаться открытым до своего JWT expiry. HTTP-проверка на B также может использовать старый auth-cache до 30 секунд.

**Условие:** два и более API-процесса. В стандартном Compose один сервер; поэтому это ограничение горизонтального масштабирования, а не обязательный дефект каждой установки. Payload push — только сигнал перечитать уведомления, без текста задач; утечка содержимого через него не установлена.

**Исправление:** общий транспорт уведомлений и invalidation, например PostgreSQL LISTEN/NOTIFY с механизмом восстановления состояния, либо явно закреплённый режим одного процесса. Sticky sessions сами по себе не доставляют события, созданные другим пользователем на другой реплике.

**Критерий приёмки:** на двух процессах комментарий с A доставляет push клиенту B, а отзыв сессии на A закрывает её WS на B в заданный срок.
