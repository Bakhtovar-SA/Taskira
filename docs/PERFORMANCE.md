# Производительность и рекомендуемый предел

## Интеграции: доставка очереди (INT-04) — 05.10.2026

Стенд: PostgreSQL 18, Node 24, 50 000 задач, 200 учётных записей, 4 активные подписки,
10 000 доставок на локальный приёмник с задержкой 50 мс. API и воркер работают в одном
процессе, приёмник и `performance-load.mjs` — в отдельных. PATCH: одно соединение,
4 000 измеренных запросов на вариант, три последовательных пары после прогрева.
Контроль использует тот же код и подписки с пустой очередью; отправка включается для
второго варианта. Все окна PATCH закончились до опустошения очереди (оставалось 5 920–7 520
доставок). Замер оценивает задержку одного пользователя во время фоновой работы;
нагрузка 200 одновременных пользователей здесь не проверялась.

Первая реализация записывала до 16 результатов одновременно. Прирост p99 PATCH составил
+14,725 / +11,088 / +13,005 мс — выше допуска INT-04. Запись результатов теперь ограничена
двумя транзакциями, до четырёх результатов одной подписки атомарно в каждой; HTTP остаётся
ограничен 16 отправками, до четырёх на подписку. Воркер оставляет два слота пула свободными,
когда размер пула это позволяет. Выбор подписок циклический: большая старая очередь не
вытесняет остальные подписки. Промежуточный вариант с четырьмя транзакциями и циклическим
выбором превысил допуск в одной паре на 0,333 мс; пакетная запись убрала это превышение
в следующем полном прогоне. Итог:

| Круг | PATCH без отправки p50 / p95 / p99, мс | PATCH во время отправки p50 / p95 / p99, мс | Δ p99, мс | Очередь, с | CPU API + воркер, с |
|---|---|---|---:|---:|---:|
| 1 | 5,532 / 7,475 / 10,757 | 5,608 / 14,617 / 16,995 | +6,238 | 69,824 | 25,781 |
| 2 | 5,743 / 9,247 / 12,395 | 5,807 / 12,653 / 17,247 | +4,852 | 88,801 | 25,829 |
| 3 | 5,468 / 7,464 / 9,649 | 5,699 / 11,151 / 16,507 | +6,858 | 90,761 | 25,032 |

Все пары уложились в допуск INT-04 **+8 мс** (бюджет трека +3 мс и +5 мс на опустошение
очереди). Это сравнение с пустой очередью при уже установленном outbox; отдельно стоимость
горячего пути outbox проверена ниже. Прирост p50 — +0,064…+0,230 мс. Медиана времени
опустошения — 88,801 с (около 113 доставок/с); CPU включает параллельные PATCH и составляет
28–37% одного ядра в отдельных кругах. В каждом круге все 10 000 доставок успешны, повторов нет,
пик одновременных запросов к приёмнику — 16. Время очереди не улучшилось существенно:
до ограничения записи медиана была 86,539 с, а худший итоговый круг занял 90,761 с.

**Планы SQL на 100 000 строках.** Исходный глобальный выбор плотной очереди
читал журнал полным сканом и сортировкой: 566,564 мс на захват 16 строк. Итоговый выбор
до четырёх строк каждой подписки использует частичный индекс
`idx_webhook_deliveries_queue (webhook_id, next_attempt_at, id)` и занимает 0,544 мс.
Это планы разных алгоритмов: итоговый одновременно соблюдает лимит подписки и не даёт
одной очереди блокировать остальные. Разреженная очередь (100 ожидающих из 100 000) —
1,764 мс; раскладка — 0,803 мс,
`idx_integration_events_undispatched`. Поиск доставок по `event_id`, необходимый каскадной
очистке, занимал 8,802 мс с полным сканом; `idx_webhook_deliveries_event` дал 0,040 мс.
В итоговых планах журналы читаются по индексам; сортировка ограничена выбранными строками,
полные сканы остаются только для малых справочников пользователей и подписок.
Старые индексы сохранены; новые создаются
конкурентно отдельными expand-миграциями с инструкцией восстановления.

### Замечания ревью и эксплуатация

В итоговой миграции `webhooks.events` ограничен шестью типами `issue.*`; неизвестные значения,
`ping`, NULL-элементы и пустые массивы отвергаются самой БД. API подписок INT-05 обязан использовать
тот же закрытый список. Регрессионный тест сверяет SQL-классификацию со всеми вариантами
`ActivityEvent`: добавление нового `kind` требует явного решения о его типе интеграции.
Изменение срока (`kind=due`) — `issue.updated`; напоминание по сроку — отдельное `issue.due` в INT-04.

Очисткой outbox владеет [INT-04](tickets/INT-04-webhook-dispatcher.md): пакетное удаление старых
событий по `occurred_at` и `webhookLogRetentionDays` (по умолчанию 30 дней), с каскадом доставок.
Очистка должна появиться до включения API подписок в INT-05. Пока активных подписок нет, событий нет;
ручное добавление подписок до INT-04 требует контроля роста этих таблиц. `id` — идентификатор sequence,
не порядок COMMIT: диспетчер выбирает `dispatched_at IS NULL`, а не `id > last_id`, чтобы не терять
транзакции, завершившиеся позже.

| `GET …/issues/epics`, запрос | 27 ms, Seq Scan по `issues` | 0,17 ms, Index Scan `idx_issues_active_epics` |
| смена статуса одной задачи в направлении | 0,8 ms | 3,7 ms (первый вызов в соединении — компиляция функции) |
| смена статуса 1 000 задач одним запросом | 56 ms | 507 ms (+0,45 ms на задачу) |
| backfill счётчиков при миграции | — | 18 ms |

Счётчики после всех правок совпали с прямым агрегатом (0 расхождений). Цену записи платит только правка задачи
в направлении, и только если меняются `epic_id`, статус или архивность; остальные правки триггер не будят. Счётчики
меняются на ±1, а не пересчитываются: так параллельные правки детей одного направления складываются верно
(тест в `server/test/epicCounts.test.ts`). Обслуживание — `docs/OPERATIONS.md`, раздел «Счётчики детей направлений».

**Блокировки.** Правка ребёнка держит строку его направления до конца своей транзакции, поэтому одновременные
правки детей одного «горячего» направления идут по очереди. Транзакции API короткие (единицы мс), массовые
действия сохраняют каждую задачу отдельной транзакцией, так что очередь заметна только при десятках одновременных
правок одного направления. Взаимных блокировок нет: перенос между направлениями берёт обе строки в порядке id,
воркер архивации берёт строки направлений заранее через `SKIP LOCKED` и занятые не ждёт (тесты — `epicCounts.test.ts`,
`maintenance.test.ts`).

## Методика (измерения 19 сентября 2026)

Сценарий из `server/scripts/performance-load.mjs` использует Autocannon 8 и
отдельный bearer token для каждого тестового пользователя. Фикстуру создаёт
`server/scripts/performance-seed.mjs`; команда защищена обязательным
`PERF_CONFIRM=seed-50000` и предназначена только для отдельной нагрузочной БД.

Основной прогон: 50 000 активных задач одного проекта, 200 одновременных
пользователей, 1 500 карточек в колонке `todo`, 15 секунд на сценарий, timeout
30 секунд. API и генератор нагрузки работали на одном хосте: Windows
10.0.26200 x64, Intel Core i3-N305 (8 логических CPU), 8 ГБ RAM, Node 24.20.0,
локальный PostgreSQL. Поэтому это консервативная single-host цифра, а не
универсальный benchmark для любого железа.

`board-column-1500` циклически читает восемь страниц колонки (7×200 + 100
карточек). Это измерение server/API; время React layout/paint в браузере в p95
не входит и вынесено в отдельный тикет.

## Рекомендуемый предел

**Подтверждено измерением (текущая версия): до 50 000 активных задач в одном проекте и 100 одновременных
соединений без пауз** — на одном процессе, без ошибок и таймаутов, p95 ключевых запросов не выше 292 ms.
Закрытые задачи следует архивировать, чтобы они не входили в активный набор.

Это **подтверждённая граница, а не найденный потолок**: верхнюю границу не искали — данных выше 50 000
активных задач и выше 100 соединений нет, «не измерено» не означает «не работает». Не перемерено: 200
одновременных соединений (в прежнем прогоне было 200), сценарий постраничного обхода `performance-load.mjs`
(прежний offset-путь оставлен сервером только для совместимости), два и более процессов сервера, настоящий nginx,
время React layout/paint в браузере. Для другого CPU, отдельного PostgreSQL или иной сети прогон следует
повторить и считать локальные результаты приоритетными.

**Предыдущий предел (до PERF-01…06):** не более 100 активных пользователей, 10 000 активных задач в проекте и
1 500 карточек в колонке; конфигурация 50 000 задач / 200 пользователей не рекомендовалась (p95 списка
8,4–11,6 с, при 10-секундном timeout глубокая страница переставала обслуживаться).
