## Текущее состояние (после PERF-01…06)

Клиент больше не загружает все задачи проекта при открытии: доска берёт по странице (100) на колонку, список и
таймлайн подгружают порциями по курсору, счётчики и направления приходят отдельными агрегатами. Нагрузка
измерена `server/scripts/performance-load-lazy.mjs` — теми запросами, которые клиент реально отправляет.

**Условия:** проект PERF — 50 000 активных (и 10 000 архивных) задач, ещё 9 проектов, всего 92 860 задач;
100 соединений (отдельный пользователь `perf_NNN` на соединение) **без пауз**, 60 с на сценарий после 10 с
прогрева; один процесс сервера, PostgreSQL и генератор на одной машине (Intel Core i3-N305, 8 логических CPU,
8 ГБ RAM, Windows 10.0.26200 x64, Node 24.20.0); `MAINTENANCE_ENABLED=false`, `RATE_LIMIT_ENABLED=false`,
триграммные индексы на месте (`/api/health` без предупреждений до и после).

| Сценарий | запр./с | Средняя | p95 | p99 | Ошибки / timeout / non-2xx |
|---|---:|---:|---:|---:|---:|
| Холодный старт доски (6 запросов) | 552 | 182 ms | 292 ms | 362 ms | 0 / 0 / 0 |
| Поиск с совпадениями | 658 | 153 ms | 220 ms | 259 ms | 0 / 0 / 0 |
| Поиск без совпадений | 1 530 | 65 ms | 87 ms | 108 ms | 0 / 0 / 0 |
| Смешанный (доска + поиск) | 682 | 148 ms | 277 ms | 318 ms | 0 / 0 / 0 |

Это **насыщение** (closed loop): каждое соединение шлёт следующий запрос сразу после ответа. Число показывает
потолок при такой нагрузке, а не поведение живых пользователей, которые делают запросы с паузами; перевод
«соединений» в «пользователей» здесь не выводится, потому что модели пользователя у стенда нет. Проверено также
вручную в браузере: доска с колонкой на ~1 500 задач, список (подгрузка следующей страницы), таймлайн
(60 направлений, раскрытие узла).

## Дашборды: 100 проектов (29 сентября 2026)

Замер `POST /api/dashboards/data` (ADR-0022) — тем запросом, который шлёт клиент, на стенде
`server/scripts/performance-dashboard-seed.mjs`: **100 проектов** в 10 командах, 50 000 задач (45% закрыты, часть в
архиве), 80 человек, 42 000 назначений, 150 000 записей истории. Замер — `server/scripts/performance-dashboard.mjs`,
сырой результат (до и после правок) — [`PERFORMANCE.dashboards.raw.json`](./PERFORMANCE.dashboards.raw.json).
Машина: 4 vCPU Intel Xeon 2.1 ГГц, 15 ГБ RAM, Linux, Node 22, PostgreSQL 16 на той же машине; один процесс сервера,
`RATE_LIMIT_ENABLED=false`, `MAINTENANCE_ENABLED=false`. Последовательно 30 запросов после 3 прогревочных.

| Сценарий | медиана | p95 | до правок (медиана / p95) |
|---|---:|---:|---:|
| «Обзор организации», администратор (все 100 проектов) | 66 ms | 87 ms | 161 / 230 ms |
| «Обзор организации», сотрудник (14 своих проектов) | 23 ms | 34 ms | 111 / 131 ms |
| «Обзор проекта» (500 задач) | 13 ms | 19 ms | 92 / 111 ms |
| 20 человек одновременно, без пауз, обзор организации | 237 ms | 305 ms | 1 042 / 1 165 ms |

Под нагрузкой 20 человек — **82 расчёта обзора в секунду** (до правок 19), ошибок 0. Узкие места, найденные замером:

- **Тренд «создано / закрыто»** считал два подзапроса на каждую неделю периода (за год — 106 проходов по задачам):
  90 дней — 165 ms, год — 476 ms. Теперь каждая сторона — один проход с группировкой по неделе: 21 и 30 ms.
  Правильность по неделям — тест в `server/test/dashboards.test.ts`.
- **«Активность»** сортировала всю таблицу `activity`: 73 ms на 150 000 записей и дальше линейно. Индекс
  `idx_activity_created` (миграция `20260929T1200_index_activity_created.sql`, `CONCURRENTLY`) — 4 ms.

Остальные виджеты по отдельности на всех 100 проектах — от 4 до 50 ms (самый тяжёлый — разбивка по исполнителям).
Отрисовка в браузере от числа проектов не зависит: каждый виджет показывает ограниченное число строк (разбивка —
10 групп и «остальное», списки и прогресс — до 30), поэтому отдельно не мерялась.

## Справочник направлений: 60% задач под направлениями (30 сентября 2026, EPIC-01)

`GET …/issues/epics` (доска, список, таймлайн) раньше считал детей направлений агрегатом по всем активным задачам
проекта. Замер на отдельной БД: `performance-seed.mjs` (50 000 задач), затем 60% задач (29 964) распределены по
направлениям — 36 из них с детьми. Та же машина, что выше; `EXPLAIN ANALYZE` после `VACUUM ANALYZE`.

| | до | после |
|---|---:|---:|
| `GET …/issues/epics`, запрос | 27 ms, Seq Scan по `issues` | 0,17 ms, Index Scan `idx_issues_active_epics` |
| смена статуса одной задачи в направлении | 0,8 ms | 3,7 ms (первый вызов в соединении — компиляция функции) |
| смена статуса 1 000 задач одним запросом | 56 ms | 507 ms (+0,45 ms на задачу) |
| backfill счётчиков при миграции | — | 18 ms |

Счётчики после всех правок совпали с прямым агрегатом (0 расхождений). Цену записи платит только правка задачи
в направлении, и только если меняются `epic_id`, статус или архивность; остальные правки триггер не будят. Счётчики
меняются на ±1, а не пересчитываются: так параллельные правки детей одного направления складываются верно
(тест в `server/test/epicCounts.test.ts`). Обслуживание — `docs/OPERATIONS.md`, раздел «Счётчики детей направлений».

**Блокировки.** Правка ребёнка держит строку его направления до конца своей транзакции, поэтому одновременные
правки детей одного «горячего» направления идут по очереди. Транзакции API короткие (единицы мс), массовые
действия сохраняют каждую задачу отдельной транзакцией, так что очередь заметна только при десятках одновременных
правок одного направления. Взаимных блокировок нет: перенос между направлениями берёт обе строки в порядке id,
воркер архивации берёт строки направлений заранее через `SKIP LOCKED` и занятые не ждёт (тесты — `epicCounts.test.ts`,
`maintenance.test.ts`).

## Методика (измерения 19 сентября 2026)

Сценарий из `server/scripts/performance-load.mjs` использует Autocannon 8 и
отдельный bearer token для каждого тестового пользователя. Фикстуру создаёт
`server/scripts/performance-seed.mjs`; команда защищена обязательным
`PERF_CONFIRM=seed-50000` и предназначена только для отдельной нагрузочной БД.

Основной прогон: 50 000 активных задач одного проекта, 200 одновременных
пользователей, 1 500 карточек в колонке `todo`, 15 секунд на сценарий, timeout
30 секунд. API и генератор нагрузки работали на одном хосте: Windows
10.0.26200 x64, Intel Core i3-N305 (8 логических CPU), 8 ГБ RAM, Node 24.20.0,
локальный PostgreSQL. Поэтому это консервативная single-host цифра, а не
универсальный benchmark для любого железа.

`board-column-1500` циклически читает восемь страниц колонки (7×200 + 100
карточек). Это измерение server/API; время React layout/paint в браузере в p95
не входит и вынесено в отдельный тикет.

Воспроизведение после запуска отдельного сервера:

```bash
cd server
PERF_CONFIRM=seed-50000 DATABASE_URL=postgresql://... npm run perf:seed
PERF_BASE_URL=http://127.0.0.1:8080 \
PERF_CONNECTIONS=200 PERF_DURATION_SECONDS=15 PERF_TIMEOUT_SECONDS=30 \
npm run perf:run
```

## История измерений: 19 сентября 2026 (до PERF-01…06)

Цифры ниже относятся к прежней версии, где клиент грузил проект целиком постраничным offset-обходом; с текущей
версией они не сопоставимы и оставлены как история.

| Сценарий | Нагрузка | p95 | p99 | Средняя | req/s | Ошибки / timeout / non-2xx |
|---|---:|---:|---:|---:|---:|---:|
| Bootstrap проекта | 50k / 200 users | 1 773 ms | 1 956 ms | 1 146 ms | 167.27 | 0 / 0 / 0 |
| Первая страница задач (200) | 50k / 200 users | 8 392 ms | 8 503 ms | 8 108 ms | 13.34 | 0 / 0 / 0 |
| Глубокая страница, offset 49 800 | 50k / 200 users | 11 646 ms | 11 758 ms | 11 344 ms | 13.34 | 0 / 0 / 0 |
| Колонка доски, 1 500 карточек | 50k / 200 users | 3 632 ms | 8 874 ms | 1 555 ms | 160.00 | 0 / 0 / 0 |

Контрольный прогон на 10 000 задачах и 100 пользователях (10 секунд на
сценарий) дал p95: bootstrap 821 ms, первая страница 1 150 ms, глубокая
страница 1 292 ms, колонка 730 ms; ошибок и timeout не было.

До увеличения timeout основной прогон глубокой страницы завершился 200
таймаутами при стандартном 10-секундном лимите. Повтор с 30 секундами дал
p95 11,646 сек — деградация начинается не на сетевом слое, а в обработке
списка под конкурентной нагрузкой. Глубокий `OFFSET`, обязательный `count(*)`
на каждой странице и клиентская последовательная загрузка всех страниц
усиливают друг друга.

## Рекомендуемый предел

**Подтверждено измерением (текущая версия): до 50 000 активных задач в одном проекте и 100 одновременных
соединений без пауз** — на одном процессе, без ошибок и таймаутов, p95 ключевых запросов не выше 292 ms.
Закрытые задачи следует архивировать, чтобы они не входили в активный набор.

Это **подтверждённая граница, а не найденный потолок**: верхнюю границу не искали — данных выше 50 000
активных задач и выше 100 соединений нет, «не измерено» не означает «не работает». Не перемерено: 200
одновременных соединений (в прежнем прогоне было 200), сценарий постраничного обхода `performance-load.mjs`
(прежний offset-путь оставлен сервером только для совместимости), два и более процессов сервера, настоящий nginx,
время React layout/paint в браузере. Для другого CPU, отдельного PostgreSQL или иной сети прогон следует
повторить и считать локальные результаты приоритетными.

**Предыдущий предел (до PERF-01…06):** не более 100 активных пользователей, 10 000 активных задач в проекте и
1 500 карточек в колонке; конфигурация 50 000 задач / 200 пользователей не рекомендовалась (p95 списка
8,4–11,6 с, при 10-секундном timeout глубокая страница переставала обслуживаться).
