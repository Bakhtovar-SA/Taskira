# Эксплуатация Taskira: резервное копирование и диагностика

## Проверки состояния и метрики

Служебные endpoints доступны на HTTP-порту сервера (в Compose — внутри сети,
`http://server:8080`):

- `GET /health` — liveness процесса, не обращается к зависимостям;
- `GET /ready` — readiness: PostgreSQL, полный набор миграций текущей версии и
  local/S3 storage. При любой неготовой зависимости возвращает `503`;
- `GET /metrics` — Prometheus exposition format. Сборщик должен опрашивать этот
  endpoint; Prometheus/Grafana в поставку Taskira намеренно не входят.

Экспортируются `taskira_http_request_duration_seconds` и
`taskira_http_requests_total` (labels используют шаблон route, а не UUID из
URL), `taskira_ws_connections`, `taskira_background_queue_size`,
`taskira_ldap_resync_duration_seconds` и `taskira_s3_errors_total`.

### API, прокси и загрузки

Поддерживается **один serving API-процесс на БД** ([ADR-0024](adr/0024-single-serving-api.md)).
Второй процесс отклоняется до запуска HTTP; потеря отдельного соединения владения останавливает
API. Используйте прямое соединение PostgreSQL, а при обновлении сначала остановите прежний API.
Rolling deployment и несколько serving-реплик требуют межпроцессного транспорта push/отзыва сессий.
Соединение владения занимает ещё одно подключение сверх `PG_POOL_MAX`; PgBouncer transaction pooling
не поддерживается. Heartbeat идёт каждые 10 с с таймаутом запроса 5 с. Если используется
`idle_session_timeout`, он должен быть больше интервала heartbeat с запасом на задержки.
При реальной потере владения API завершается, поскольку безопасно обслуживать запросы без лока нельзя.
Остановка HTTP/WS и пула ограничена 10 с; по истечении срока процесс выходит и освобождает лок через ОС.

Первый таймаут heartbeat тоже запускает штатную остановку, без повторных запросов
на сомнительном соединении. При half-open TCP обнаружение может занять примерно
10 с до heartbeat и 5 с ожидания ответа (дольше при задержке event loop), затем
до 10 с на закрытие. Session lock не является распределённым fencing: при разрыве
связи/переключении БД возможен интервал до обнаружения, когда прежний процесс ещё
обслуживает запросы. Не запускайте замену, пока прежний API не остановлен; при
failover БД сначала подтвердите остановку старого процесса. Автоматическое
одновременное обслуживание нескольких реплик этой архитектурой не поддерживается.

Публичный nginx перезаписывает `X-Forwarded-For` адресом своего TCP-клиента. Compose задаёт подсеть
через `TASKIRA_NETWORK_CIDR` (по умолчанию `172.30.0.0/24`) и использует то же значение для
`TRUST_PROXY` API. Настройки Docker `default-address-pools` больше не меняют границу доверия.
При конфликте адресов или нескольких инсталляциях на хосте задайте свободную подсеть в `.env`;
пересоздание сети планируйте с остановкой контейнеров. Для запуска вне Compose задайте `TRUST_PROXY`
адресом/CIDR непосредственного nginx-прокси в `server/.env`.
Не публикуйте порт API в обход nginx и не устанавливайте `TRUST_PROXY=true`.
За корпоративным LB настройте nginx `set_real_ip_from` только для адресов LB и `real_ip_header`
по его контракту; LB обязан очищать пользовательские forwarding-заголовки. В клиентском образе
есть include `/etc/nginx/taskira-real-ip/*.conf`, по умолчанию пустой. Например, создайте
`/etc/taskira/nginx-real-ip/lb.conf` (CIDR ниже замените реальным CIDR балансировщика):

```nginx
set_real_ip_from 10.20.30.0/24;
real_ip_header X-Forwarded-For;
real_ip_recursive on;
```

Подключите каталог через `compose.override.yml`:

```yaml
services:
  client:
    volumes:
      - /etc/taskira/nginx-real-ip:/etc/nginx/taskira-real-ip:ro
```

После пересоздания client проверьте `nginx -t`, IP в audit log и независимые IP-лимиты двух клиентов.
Без такой настройки все пользователи за LB будут разделять один IP-лимит.
Не доверяйте всем адресам через `set_real_ip_from 0.0.0.0/0`.

nginx передаёт потоком без собственного фиксированного предела только конечные пути загрузки
вложений, фото фона, аватара и знака. API ограничивает размер файла, число файлов и поля.
Для остальных `/api/` действует `client_max_body_size 1m`, дополнительно к Fastify body limit.
`ATTACH_MAX_BYTES` (по умолчанию 25 MiB) и `ATTACH_MAX_PER_ISSUE` передаются через Compose.
Контейнерная проверка `scripts/test-proxy-integration.sh` покрывает default/override,
2 MiB, ровно максимум, превышение и границу доверия IP.

### Фоновое обслуживание (MAINT-01)

Три джоба — `maintenance` (автоархив закрытых задач + уборка `audit_log` + остатки лимитера входа), `storage-sweep`,
`ldap-resync` — видны в `/metrics` **каждого процесса** (метрики по процессу, не по кластеру):
`taskira_background_job_runs_total{job,result}` (`success` / `error` / `skipped` — лок держит другой процесс),
`taskira_background_job_duration_seconds{job}`, `taskira_background_job_last_success_timestamp_seconds{job}`,
`taskira_background_job_running{job}`, `taskira_maintenance_archived_issues_total`,
`taskira_maintenance_audit_purged_total`. Алерт «нет успешного прохода дольше 3 интервалов»:
`time() - max(taskira_background_job_last_success_timestamp_seconds{job="maintenance"}) > 3 * 3600` — берите `max`
по всем процессам, потому что каждый тик исполняет один из них.

Значения по умолчанию: интервал 1 ч (`MAINTENANCE_INTERVAL_MS`); **первый проход через 5 минут после старта**
(`MAINTENANCE_START_DELAY_MS`, sweep и LDAP — ещё позже на 15 и 30 с); пачка 1 000 строк (`MAINTENANCE_BATCH_SIZE`)
с паузой 50 мс (`MAINTENANCE_BATCH_PAUSE_MS`); потолок 50 000 строк каждого вида за проход
(`MAINTENANCE_MAX_PER_RUN`) — на установке с накопленным архивом (восстановление из бэкапа, импорт) остаток
дообрабатывается следующими часовыми проходами, а лог пишет «достигнут потолок». Каждая пачка — отдельная короткая
транзакция; строку, которую в этот момент правит пользователь, проход пропускает (`SKIP LOCKED`).

Управление (только глобальный админ): `GET /api/maintenance` — состояние джобов **этого процесса** (последний запуск,
результат, длительность, следующий запуск) и действующие настройки; `POST /api/maintenance/run?dryRun=true` —
сколько задач будет архивировано и записей аудита удалено, без изменений; `?dryRun=false` — выполнить проход сейчас
(тот же лок, что у расписания; `409 maintenance_busy`, если проход уже идёт). Параметр `dryRun` обязателен. Проход,
который что-то сделал, оставляет в `audit_log` запись `maintenance.run` (кто/по расписанию, сколько, упёрлись ли в
потолок). Что **не** сделано из MAINT-01: порог «при N больше лимита не выполнять автоматически, а ждать
подтверждения администратора» — потолок за проход и dry-run покрывают тот же риск, но не блокируют проход.

Каждый HTTP-ответ содержит `X-Request-Id`. Если клиент прислал этот заголовок,
значение сохраняется; иначе сервер создаёт UUID. То же значение находится в
JSON-логах Fastify в поле `reqId`, поэтому его следует просить у пользователя
при обращении в поддержку. Не публикуйте `/metrics` и probes в интернет:
разрешите доступ только балансировщику и системе мониторинга.

Команды ниже выполняются из распакованного каталога установленного релиза. Они
работают без интернета и registry, с Docker Compose и rootless Podman Compose.

## Резервное копирование

```bash
./backup.sh --install-dir /opt/taskira/current \
  --output /var/backups/taskira/taskira-$(date -u +%Y%m%dT%H%M%SZ).tar.gz
```

Архив содержит согласованный `pg_dump`, полный снимок local/S3-хранилища
вложений, список применённых миграций, manifest, контрольные суммы и только
несекретные поля `.env`. Для согласованности `client` и `server` кратко
останавливаются; PostgreSQL остаётся доступен. Дамп проверяется полным тестовым
восстановлением до создания архива.

Рекомендуемое расписание — ежедневно в 02:00. Пример crontab:

```cron
0 2 * * * cd /var/backups/taskira && /opt/taskira/release/backup.sh --install-dir /opt/taskira/current >>/var/log/taskira-backup.log 2>&1
```

Переносите архивы на отдельный защищённый носитель и задайте срок хранения по
политике организации. Сам скрипт намеренно не удаляет старые архивы.

При ежедневном расписании целевой RPO — 24 часа. Фактический RPO равен времени
с последнего успешного архива. Плановый RTO для одного хоста — до 60 минут плюс
время копирования архива; он зависит от размера БД и бакета. Мониторинг cron
должен проверять код возврата и наличие свежего архива.

## Восстановление

```bash
./restore.sh --install-dir /opt/taskira/current \
  --archive /var/backups/taskira/taskira-20260919T020000Z.tar.gz
```

Скрипт проверяет SHA-256 и каждый объект, отказывается от неизвестной/более новой
схемы, затем требует вручную ввести `REPLACE`. Для автоматической репетиции есть
`--yes`. Текущая БД сохраняется под временным страховочным именем до успешного
`pg_restore`; после восстановления возвращаются все объекты хранилища и
проверяется health текущей версии приложения. Старый архив разрешено
восстанавливать на более новой совместимой версии: при старте применятся
оставшиеся миграции.

Секреты не входят в архив. Копию рабочего `.env` с секретами храните отдельно в
корпоративном менеджере секретов. Без неё восстановление на новом хосте потребует
новых JWT/admin/S3/LDAP/SMTP credentials.

## Настройка PostgreSQL

Для сервера на SSD задайте `random_page_cost = 1.1` (`postgresql.conf` или
`ALTER SYSTEM SET random_page_cost = 1.1; SELECT pg_reload_conf();`). Дефолт 4
рассчитан на HDD и на крупном проекте заставляет планировщик читать таблицу
целиком вместо индекса `idx_issues_active`: счётчики по статусам ≈19 мс вместо
≈7 мс на 50 000 задач. Compose-деплой — см. `DOCKER_SETUP.md`, раздел 5. Проверка:
`SHOW random_page_cost;`. Основание и замеры —
`docs/performance-tickets/PERF-05-step1-server-filters.md`.

## Расширение pg_trgm (поиск задач)

Текстовый поиск задач использует триграммные индексы (`pg_trgm`, миграция
`20260920T1420`). Расширение входит в contrib и помечено `trusted` (PostgreSQL ≥ 13):
его может создать владелец БД без суперпользователя. Если его нет — миграция
пропускает индексы (`NOTICE` в логе), поиск работает, но на большом проекте
медленнее (десятки–сотни мс). Проверка: `SELECT indexname FROM pg_indexes WHERE
indexname LIKE 'idx_issues_active_%_trgm';`. На установке с сотнями тысяч задач
создайте индексы заранее `CONCURRENTLY` (команды — в комментарии миграции), иначе
сборка на время блокирует запись в `issues`. Подробности:
`docs/tickets/SEARCH-01-trigram-index.md`.

## Счётчики детей направлений (EPIC-01)

Число задач в направлении и сколько из них закрыто хранятся на строке самого направления
(`issues.epic_child_total` / `epic_child_done`, миграция `20260930T0500`) и поддерживаются триггерами
на `issues` и `workflow_statuses` при любом пути записи, в том числе при ручном SQL.

- **Обновление большой установки.** Колонки добавляются без перезаписи таблицы; backfill идёт в той же
  транзакции и на это время держит блокировку записи в `issues`. Замер: 30 000 детей на 50 000 задач —
  18 мс; на миллионе задач ожидается порядка секунды (линейно, не замерялось). Индекс
  `idx_issues_active_epics` собирается отдельной миграцией `CONCURRENTLY` (`20260930T0501`) и запись не
  блокирует; при сбое — команды восстановления в её первой строке.
- **Проверка.** Расхождений быть не должно; запрос ниже возвращает число неверных строк:
  ```sql
  SELECT count(*) FROM issues e LEFT JOIN (
    SELECT ch.epic_id, count(*) t, count(*) FILTER (WHERE ws.category = 'done') d
      FROM issues ch JOIN workflow_statuses ws ON ws.id = ch.status_id
     WHERE ch.epic_id IS NOT NULL AND ch.archived_at IS NULL GROUP BY ch.epic_id) c ON c.epic_id = e.id
   WHERE (e.epic_child_total, e.epic_child_done) IS DISTINCT FROM (coalesce(c.t, 0), coalesce(c.d, 0));
  ```
- **Починка** — повторно выполнить файл миграции (`psql -f server/migrations/20260930T0500_epic_child_counts.sql`):
  он идемпотентен и пересчитывает все счётчики.
- **Массовая правка `epic_id` вручную** (десятки тысяч строк одним `UPDATE`) с включённым триггером медленная:
  каждая строка правит строку своего направления, 30 000 строк — около 20 с. Для такой правки в одной транзакции:
  `ALTER TABLE issues DISABLE TRIGGER trg_issues_epic_counts_upd;` → свой `UPDATE` →
  `ALTER TABLE issues ENABLE TRIGGER trg_issues_epic_counts_upd;` → повторить файл миграции (пересчёт).
  Приложение так не пишет: массовые действия идут через API ограниченными пачками.

## Нагрузочный стенд: правила изменения и отката данных

Для любых правок данных на стенде (схема `taskira_perf`, скрипты
`server/scripts/performance-seed*.mjs`), в том числе временных «для замера»:

1. **Только в изолированной схеме/БД**, с явным подтверждением (`PERF_CONFIRM`) и
   проверкой, что схема не `public`.
2. **Сервер поверх стенда запускать с `MAINTENANCE_ENABLED=false`**, иначе фоновая
   архивация меняет активный набор (инцидент: 15 073 архивированных задачи, MAINT-01).
3. **Перед правкой фиксировать исходное состояние тем, что позволит вернуть именно
   его** (id и значения изменяемых строк, а не диапазон «как я его помню»).
4. **Откат — по идентичности, а не слепым обнулением диапазона.** Слепое «верну как
   было» стирает настоящие данные: в диапазоне могут быть строки, у которых нужное
   значение было изначально. Различайте свои строки от исходных (сохранённые id либо
   `xmin`: строки одного `UPDATE` разделяют `xmin`, исходные — нет) и сверяйте
   итог с числом до правки. Пример (PERF-06): в диапазоне после правки было 65 строк с
   направлением; 64 добавленные различены по `xmin`, исходная осталась нетронутой.
5. **Побочные следы** (`activity`, `audit_log`) чистить или явно записывать в отчёт.
6. Всё, что осталось не откатанным, — в отчёт по замеру, а не «по умолчанию верну».
7. **Отсутствие триграммных индексов теперь видно в `/ready` и `/api/health`:** поле `warnings`
   (`search_index_missing`), при этом `ok` и код ответа не меняются (это деградация, а не отказ). Без
   contrib-расширения предупреждение ожидаемо. **Перед замером поиска проверяйте, что индексы на месте:**
   `SELECT indexname FROM pg_indexes WHERE indexname LIKE '%trgm%'` в схеме стенда. Раньше `npm test` в
   `server/` молча удалял их (общее для БД расширение `pg_trgm` терялось при сбросе тестовой схемы —
   TEST-01, воспроизведено дважды). Теперь тесты идут в отдельной БД `taskira_test` и стенд не трогают, но
   проверка дешёвая, а замер без индексов — Seq Scan 80–160 мс вместо 0,06–3 мс, и об этом ничего не скажет.

## Восстановление пароля администратора

Пароль локального пользователя-участника сбрасывает любой глобальный администратор в интерфейсе
(«Организация → Пользователи → Сбросить пароль»). Пароль **администратора** и break-glass учётки
`ADMIN_USERNAME` из интерфейса не сбрасывается (`409 PASSWORD_RESET_ADMIN`, SEC-PWD-01, ADR-0034), а
`ADMIN_PASSWORD` из `.env` применяется только при первом запуске на пустой таблице `users` (`seedAdmin`) —
его смена в `.env` ничего не меняет в работающей установке. Забытый пароль администратора восстанавливается
с хоста, где развёрнута Taskira:

```bash
cd /opt/taskira/current
docker compose run --rm --no-deps server node dist/resetPassword.js <логин>
```

Команда печатает временный пароль (действует `PASSWORD_RESET_TTL_HOURS`, по умолчанию 24 ч); при входе с ним
нужно сразу задать свой пароль. Одновременно снимается блокировка входа, отзываются API-токены учётки и все её
сеансы — работающий сервер перестаёт принимать старые сеансы и токены в течение 30 секунд (кэш свежести). В
`audit_log` пишется `user.password.reset` с `actor_id = NULL` и `via: "cli"`. Только для локальных учёток:
LDAP-пароль меняется в каталоге. В разработке: `cd server && DATABASE_URL=… npm run password:reset -- <логин>`
(нужны те же переменные окружения, что и серверу). Передайте временный пароль владельцу лично и не оставляйте
его в истории терминала или тикетах.

## Диагностический бандл

```bash
./support-bundle.sh --install-dir /opt/taskira/current --lines 500 \
  --output /tmp/taskira-support.tar.gz
```

Бандл содержит версии, идентификаторы образов, `compose ps`, health, состояние
миграций, последние строки логов, whitelist безопасных полей конфигурации и
названия таблиц с количеством строк. Строки таблиц, тексты задач и содержимое
вложений не выгружаются. Из логов дополнительно вырезаются известные секреты,
Bearer-токены и session cookie. Перед отправкой архив всё равно должен проверить
администратор клиента согласно внутренней политике.

## Что теряется при отказе компонентов

| Компонент | Последствие потери | Восстановление |
|---|---|---|
| PostgreSQL volume | Пользователи, проекты, задачи, история и метаданные вложений | `restore.sh` из последнего полного архива |
| `attachments` volume или S3/MinIO bucket | Бинарные вложения и аватары; строки БД останутся, скачивание будет нарушено | Раздел storage того же архива; не смешивать с дампом другой даты |
| Server/client containers | Постоянные данные не теряются | Повторно загрузить versioned image tar и выполнить `compose up -d` |
| Локальные image storage Docker/Podman | Запуск невозможен, данные в volumes остаются | `install.sh` из офлайн-релиза, затем `compose up -d` |
| `.env` | Теряются пароли и параметры интеграций | Восстановить из отдельного менеджера секретов; backup содержит только whitelist без секретов |
| Единственная копия backup | Нет точки аварийного восстановления | Хранить проверенные копии вне хоста Taskira |

## Репетиция восстановления

19 сентября 2026 года выполнена автоматизированная репетиция на чистой
Compose-инсталляции: создана задача и текстовое вложение, сформированы backup и
support bundle, стек остановлен с удалением PostgreSQL и attachments volumes,
после чего выполнен `restore.sh --yes`. Проверены новый логин, наличие задачи и
байт-в-байт скачивание вложения. Сценарий закреплён CI-job
`backup, destroy volumes, and restore`; его необходимо сохранять зелёным при
каждом изменении backup/restore или схемы.
