# ADR-0028 — События интеграций: транзакционный outbox из истории задач; исходящие вебхуки только на разрешённые адреса

**Статус:** Accepted
**Дата:** 2026-10-04

## Контекст

Трек L ([TRACK-L-INTEGRATIONS.md](../tracks/TRACK-L-INTEGRATIONS.md), ТЗ `TZ-ARCHITECTURE-BRIEF.md`): внутренним
системам организации нужны исходящие события по задачам — создана, изменена, сменила статус, назначена,
прокомментирована, наступил срок. Ограничения на момент решения:

- Один обслуживающий API-процесс на БД (ADR-0024); очередей, Redis и внешних планировщиков в поставке нет.
- Уведомления уже пишутся вызовом `emit()` **после** коммита и «никогда не бросают»
  (`services/notify.ts`): при падении процесса между коммитом и `emit()` уведомление теряется. Для уведомлений в
  интерфейсе это допустимо, для интеграции, по которой другая система ведёт учёт, — нет.
- История задачи — данные (`activity.kind` + `payload`, трек E). Каждое изменение задачи, видимое человеку, уже
  оставляет строку `activity`; создание, правка и переход пишут её **в той же транзакции**, что и изменение
  (`routes/issues.ts`, `services/issueTransition.ts`). Комментарии — строки `comments`.
- `SECURITY_OVERVIEW.md` обещает: «исходящие соединения только к адресам, явно заданным администратором».
  Цели вебхуков — внутренние системы, то есть адреса из частных сетей: запрет RFC 1918 как защита от SSRF
  сделал бы функцию бесполезной.
- Письма намеренно не содержат названий, описаний и комментариев задач.

## Рассмотренные варианты

**Источник событий.**

1. *Вызов `emitIntegrationEvent()` в каждом маршруте* (как `emit()`). Каждый новый путь записи нужно не забыть;
   массовые операции, ссылки и чек-лист пишут историю вне транзакции. Отклонено: пропуск пути — тихая потеря.
2. *Чтение таблицы `activity` курсором.* Порядок `id`/`created_at` не совпадает с порядком коммитов: курсор
   пропускает строку, закоммиченную позже соседней. Корректный вариант (`pg_snapshot_xmin`) слишком тонок для
   сопровождения. Отклонено.
3. **Триггер `AFTER INSERT` на `activity` и `comments` пишет строку outbox `integration_events` в той же транзакции.**
   Любой путь записи, оставивший историю, порождает событие; откат транзакции откатывает и событие. Тот же приём,
   что у счётчиков направлений (EPIC-01): «верно при любом пути записи, включая ручной SQL». **Принято.**

**Доставка.**

1. *Отправка HTTP прямо из маршрута.* Задержка и отказ чужой системы попадают в горячий путь. Отклонено.
2. *LISTEN/NOTIFY.* Уведомление теряется, если процесс не слушал в момент коммита; нужен опрос всё равно. Отклонено
   как основной механизм (может добавиться позже как «разбудить раньше»).
3. **Опрос outbox фоновым заданием в том же процессе (`startJob`, advisory-лок тика, как у MAINT-01),
   раскладка события на доставки по подпискам, отправка с повторами.** **Принято.**

**Защита от SSRF.**

1. *Запрет частных диапазонов.* Ломает основной сценарий (внутренние системы). Отклонено.
2. *Свободный ввод адреса менеджером проекта с проверкой на loopback/metadata.* Нарушает обещание
   `SECURITY_OVERVIEW.md` и открывает внутреннюю сеть любому, кто получил право. Отклонено.
3. **Функция выключена по умолчанию (`WEBHOOKS_ENABLED=false`); цели ограничены списком оператора
   `WEBHOOK_ALLOWED_TARGETS` (имена, `*.домен`, IP, CIDR) в env; поверх — неотключаемый запрет loopback,
   link-local (в т. ч. 169.254.169.254), multicast, unspecified и подсети compose (`WEBHOOK_DENY_CIDRS`).
   Проверка — при сохранении и перед каждой попыткой, по всем адресам DNS-ответа; соединение идёт на проверенный
   адрес (pinning), редиректы не выполняются.** **Принято.**

**Содержимое события.**

1. *Полная задача (название, описание, комментарий).* Удобно получателю, но вывозит текст задач туда, куда
   его не вывозят даже письма. Отклонено для версии 1.
2. **Тонкое событие: идентификаторы, ключи, ссылка, тип, автор и список изменений из истории без текстовых полей.**
   Содержимое получатель читает API-токеном (ADR-0029) с правами его учётной записи. **Принято.**

## Решение

1. **Outbox.** Таблица `integration_events` пишется триггерами на `activity` (событие с `kind`) и `comments`, и
   только если у проекта есть хотя бы одна активная подписка. События одной транзакции по одной задаче одного типа
   **склеиваются** в одну строку (`dedupe_key = 'tx:<pg_current_xact_id>:<issue>:<type>'`, `ON CONFLICT … changes ||`):
   PATCH, менявший три поля, — одно `issue.updated` с тремя изменениями. Событие срока (`issue.due`) пишет
   ежедневное задание с ключом `due:<issue>:<date>`. Типы v1: `issue.created`, `issue.updated`,
   `issue.statusChanged`, `issue.assigned` (любое изменение состава исполнителей), `issue.commented`, `issue.due`,
   служебный `ping`.
2. **Подписка — уровень проекта**, управляет **только глобальный администратор** (`requireGlobalAdmin`, без нового
   `PermId`): вебхук — вывоз данных проекта за пределы Taskira, а роль `admin` в проекте и так есть только у
   глобального администратора (ADR-0005). Дом в интерфейсе — «Настройки проекта → Интеграции» (раздел только для
   администратора, как «Общее» и «Модули»). Адрес и секрет подписи хранятся зашифрованными (AES-256-GCM, ключ
   `WEBHOOK_SECRET_KEY` из env); в аудит, логи и экспорт адрес попадает только без query и userinfo.
3. **Доставка at-least-once.** Задание `webhook-dispatch` раскладывает событие на строки `webhook_deliveries` по
   подпискам, тип которых совпал, и отправляет их: захват `FOR UPDATE SKIP LOCKED` с арендой (`locked_until`),
   отправка вне транзакции, запись результата. Падение после отправки до записи — повторная отправка после аренды.
   «Ровно один раз» по HTTP недостижимо: получатель отбрасывает дубль по `X-Taskira-Event-Id`. Порядок не
   гарантируется; в теле есть `occurredAt` и монотонный `sequence`.
4. **Подпись** — HMAC-SHA256 от `<unix-время>.<тело>` секретом подписки; заголовок
   `X-Taskira-Signature: t=…,v1=…`; получатель отвергает `t` старше 5 минут. Смена секрета держит прежний 24 часа и
   подписывает обоими.
5. **Повторы**: сетевые ошибки, таймаут, 408, 429 (с `Retry-After` не дольше часа), 5xx — до 8 попыток по
   расписанию 0, 1 мин, 5 мин, 30 мин, 2 ч, 6 ч, 12 ч, 24 ч с разбросом ±20 %; остальные 4xx — сразу `failed`;
   `410` — сразу отключение подписки. **Отключение после серии отказов**: 20 неудачных попыток подряд и первая из
   них старше 24 часов → подписка `disabled`, ожидающие доставки `cancelled`, запись аудита, сигнал на экране
   состояния. Повторное включение сбрасывает счётчик; отменённое можно повторить вручную.
6. **Журнал доставок** хранится `WEBHOOK_LOG_RETENTION_DAYS` (30) и чистится заданием обслуживания пачками.
   Тело ответа получателя хранится не длиннее 512 байт.
7. **Версия формата** — поле `version: 1` и заголовок `X-Taskira-Webhook-Version`. Добавление полей версию не
   меняет; несовместимое изменение — версия 2 с выбором версии в подписке, отдельным решением.

## Последствия

- Горячие пути (`PATCH`, `transition`, комментарий) платят одну проверку `EXISTS` по индексу на строку истории, а
  при подписке — ещё одну вставку/склейку; HTTP в запросе нет. Бюджет и замер — в треке L.
- Событие существует тогда и только тогда, когда существует строка истории или комментарий. Изменения, которые не
  пишут историю (наблюдатели, вложения, пользовательские поля, удаление задачи), событий не дают — это граница v1,
  а не ошибка; новое событие = новый член `ActivityEvent` (как требует трек E), и тогда оно приходит само.
- Триггер — логика в SQL: сопровождающий читает её в миграции; тесты обязаны покрыть все пути записи.
- Без `WEBHOOK_SECRET_KEY` (он не входит в бэкап, как и `JWT_SECRET`) восстановленные подписки не могут подписывать —
  доставки падают с `secret_unavailable` до смены секрета администратором.
- Автоматизации по правилам (дизайн в треке L) — второй потребитель того же outbox, без нового источника событий.
- Не входит: события удаления задачи, наблюдателей, вложений; полное содержимое задачи в теле; вебхуки уровня
  организации; входящие вебхуки.
