# ADR-0029 — API-токены: токен всегда действует от имени пользователя; сервисная учётная запись — пользователь без входа

**Статус:** Accepted
**Дата:** 2026-10-04

## Контекст

Интеграциям (трек L) нужен доступ к API без браузерной сессии: получатель вебхука читает задачу по тонкому событию
(ADR-0028), скрипты создают задачи. Сейчас API принимает только сессионный JWT (cookie или `Authorization: Bearer`),
который живёт 8 часов и отзывается logout'ом. Права целиком построены вокруг пользователя: `resolveRole`, членство в
проекте и отделе, правило «своей задачи» для сотрудника, кэши свежести в `middleware.ts`.

## Рассмотренные варианты

**Чьими правами действует сервисный токен.**

1. *Отдельная сущность «сервисный клиент» со своим набором прав (scope по ресурсам и проектам).* Вторая модель прав
   рядом с матрицей, своя проверка в каждом маршруте, свой `actor` в истории без строки `users`. Отклонено.
2. **Сервисная учётная запись — строка `users` с `auth_source = 'service'`: без пароля, без входа, только
   `global_role = 'member'`; доступ к проектам выдаётся обычным членством с ролью.** Вся матрица, видимость,
   история и аудит работают без изменений. **Принято.**

**Область действия токена.**

1. *Тонкие scope по ресурсам (`issues:read`, `comments:write`, …).* Каждый маршрут должен объявить scope; ошибка в
   разметке маршрута — эскалация. Отклонено для v1.
2. **Два scope: `read` (только `GET`/`HEAD`) и `write` (все методы), в пределах прав владельца токена; маршруты
   глобального администратора, управления токенами, входа и WebSocket для токенов закрыты всегда.** **Принято.**

**Хранение.**

1. *bcrypt хеша.* Секрет токена — 256 бит случайных данных, перебор невозможен; bcrypt на каждом запросе — лишние
   ~50 мс CPU. Отклонено.
2. **Формат `tsk_<prefix>_<secret>`; в БД — `prefix` (поиск) и SHA-256 секрета; сравнение постоянного времени;
   секрет показывается один раз.** **Принято.**

## Решение

1. **Персональный токен** создаёт любой пользователь для себя (`/settings/tokens`), не больше 10 активных; срок
   жизни обязателен, 1–365 дней (по умолчанию 90). **Сервисную учётную запись и её токены** (не больше 5 активных)
   создаёт глобальный администратор («Организация → Сервисные учётные записи»); он же видит и отзывает любой токен.
2. **Проверка** в `requireAuth`: заголовок `Bearer tsk_…` идёт по ветке токена — поиск по `prefix`, сравнение хеша,
   `revoked_at IS NULL`, `expires_at > now()`, затем та же проверка свежести пользователя (`is_active`), что у
   сессии. Токен не зависит от `session_version`: logout сессии токены не отзывает, деактивация пользователя —
   отзывает (через `is_active`). `last_used_at` пишется не чаще раза в минуту на токен.
3. **Токен никогда не несёт глобальную роль администратора.** Власть глобального администратора проверяется не в
   одном месте: `resolveRole()` даёт ему роль `admin` в каждом проекте (а с ней `manageAccess`, `editWorkflow`,
   удаление задач), и маршруты сверяют `req.user.globalRole === "admin"` напрямую — правка общих дашбордов,
   видимость проектов в роадмапе, отчётах, поиске, на главной, список отделов. Поэтому ветка токена в `requireAuth`
   ставит `req.user.globalRole = "member"` **независимо от роли владельца в БД**. Все эти проверки, нынешние и
   будущие, видят токен как обычного участника: права в проекте даёт только явное членство (`project_members`), а
   видимость — членство, отдел или общий проект. Вдобавок `requireGlobalAdmin` отвечает на токен
   `403 TOKEN_NOT_ALLOWED` (понятная ошибка вместо `FORBIDDEN`). Токен со scope `read` на не-`GET` — `403 TOKEN_SCOPE`.
   Маршруты токенов, входа и выхода, `/api/ws` принимают только сессию.
4. **Новых `PermId` нет**: персональный токен даёт права владельца **как участника** его проектов, сервисный — права
   сервисной записи по её членствам.
5. Сервисная запись не получает уведомлений, не предлагается в выборе исполнителей, упоминаниях и общем выборе
   людей; в выборе участников проекта видна с меткой «сервис». В подсчёт мест лицензии не входит (она не входит в
   систему — `last_login_at` пуст).
6. Лимит запросов. Глобальный лимитер (`keyGenerator` в `app.ts`) выполняется **до** `requireAuth` и в БД не ходит.
   Ключ `token:<prefix>` он даёт только токену, который уже **проверен**: есть в кэше проверенных токенов
   `apiTokens.ts` (30 с) и совпал по хешу с секретом из заголовка. Всё остальное получает `ip:<req.ip>`: неизвестный
   префикс, первый запрос токена до попадания в кэш, неверный секрет. Поэтому случайные префиксы не создают новые
   корзины, и перебор упирается в IP-лимит до запроса к БД. Проверенный результат кладётся на запрос
   (`req.authToken`), и `requireAuth` не считает хеш второй раз.

## Последствия

- Получить права администратора через токен нельзя ни при каком scope: роль понижается до `member` до любой проверки.
  Токен глобального администратора видит только проекты, где тот явно участник, отдел которых его, или общие.
  Выгрузку аудита в SIEM по-прежнему делают сессией администратора. Отдельный административный scope — будущее решение (открытый вопрос трека L).
- Действия токена в истории и аудите выглядят как действия его пользователя; в аудите добавляется
  `details.via = "token"` и `tokenId`.
- Расширение CHECK `users.auth_source` — expand без удаления; старый образ сервисные записи не создаёт, а войти по
  ним не может (вход ищет `auth_source = 'local'`).
- Утечка токена ограничена сроком жизни и scope; отзыв действует сразу (кэш токенов сбрасывается при отзыве).
