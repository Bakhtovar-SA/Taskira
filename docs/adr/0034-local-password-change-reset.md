# ADR-0034 — Смена и сброс пароля локальных учёток, политика по ASVS 5.0

**Статус:** Accepted
**Дата:** 2026-10-06

## Контекст

Самопроверка ASVS 5.0 L2 (SEC-ASVS-01) нашла два дефекта аутентификации локального режима:

- SEC-PWD-01 (high): пароль локальной учётки задаёт администратор и знает его; сменить его пользователь не может,
  забытый пароль восстановить нельзя — `password_hash` пишется только при создании пользователя и в сидере
  (V6.2.2, V6.2.3, V6.4.1, V6.4.3, V7.4.3). Для клиентов без LDAP это основной режим; затронут и break-glass
  администратор в LDAP-режиме.
- SEC-PWD-02 (medium): политика требовала три группы символов из четырёх (ASVS 5.0 V6.2.5 прямо запрещает составные
  правила), чёрный список из 8 значений вместо топ-3000 (V6.2.4), контекстных слов нет (V6.1.2, V6.2.11), а `bcryptjs`
  учитывает только первые 72 байта: `я`×40 совпадал с `я`×36+`x` (V6.2.8, V6.2.9).

Ограничения: on-prem часто без интернета; один serving API на БД (ADR-0024); сессия — JWT с `session_version`,
которую уже повышают logout, деактивация и смена роли; второго фактора нет (SEC-AUTH-01).

## Решение

1. **Хэш без усечения.** Новые хэши — `sha256b64$` + bcrypt(base64(SHA-256(пароль))), cost 10. Префикс делает формат
   самоописываемым; старые bcrypt-хэши проверяются как раньше и переписываются в новый формат при первом успешном входе
   (условный `UPDATE … WHERE password_hash = прежний`). Переход на argon2id отклонён: новая нативная зависимость в
   образе ради того же результата.
2. **Политика без составных правил.** 14–128 символов (считаются символы, не байты) любого состава; отвергаются
   5000 самых частых паролей длиной ≥ 14 (SecLists xato-net, в коде сервера, проверка офлайн), тривиальные повторы
   (меньше 4 разных символов), логин, известные дефолты и контекстные слова: Taskira, название инсталляции и бренд,
   названия команд, имя пользователя, `PASSWORD_CONTEXT_WORDS`. Проверка `ADMIN_PASSWORD` при старте остаётся базовой
   (длина, логин, дефолты), полная — при создании администратора, чтобы обновление не останавливало работающую
   установку. Онлайн-проверки скомпрометированных паролей (V6.2.12) нет: документированное исключение для
   изолированных установок, список из утечек — частичная замена.
3. **Смена своего пароля** — `POST /api/me/password`, только пользовательская сессия, текущий + новый пароль.
   Неверный текущий пароль — `403` (не `401`: клиент понимает 401 как конец сессии) и засчитывается в тот же счётчик
   блокировки, что вход. После смены `session_version + 1`, `revokeUserSessions()`; текущей вкладке выдаётся новая
   cookie, как при входе. Остальные сессии завершаются всегда, без отдельного выбора (V7.4.3 допускает «опцию»;
   принудительное завершение строже).
4. **Административный сброс** — `POST /api/admin/users/:id/password-reset` (глобальный администратор, сессия).
   Сервер генерирует временный пароль (CSPRNG, 20 символов из 57 без похожих, ≈116 бит, проходит ту же политику),
   отдаёт его один раз с `Cache-Control: no-store`, ставит `must_change_password` и срок `password_expires_at`
   (`PASSWORD_RESET_TTL_HOURS`, 24 ч, не больше 168), снимает блокировку и отзывает сессии. Администратор не задаёт
   пароль сам — тогда он знал бы постоянный пароль пользователя. Свой пароль сбросом не меняется (`409`).
5. **Сессия «только смена пароля».** Флаг `must_change_password` читается вместе с активностью и версией сессии
   (`freshActiveUser`, кэш 30 с, сбрасывается отзывом). Пока он стоит, JWT-сессия допускается только к
   `/auth/me`, `/auth/config`, `/auth/logout`, `/me/lang`, `/me/password`; остальное — `403 PASSWORD_CHANGE_REQUIRED`.
   Истёкший временный пароль на входе — обычный неверный пароль. Тот же режим администратор включает при создании
   пользователя (`mustChangePassword`, в UI по умолчанию включён; в API по умолчанию выключен ради совместимости).
6. **Только локальные учётки.** LDAP и сервисные записи — `409 PASSWORD_NOT_LOCAL`; при «усыновлении» локальной
   учётки LDAP-входом флаги смены сбрасываются.
7. **Лимит запросов.** На обоих маршрутах — `@fastify/rate-limit` из `app.ts` с порогами лимита входа
   (`RATE_LIMIT_LOGIN_MAX` за `RATE_LIMIT_LOGIN_WINDOW_MS`) и своей корзиной на маршрут; после SEC-RATE-01 —
   `routeLimit("sensitive")`.

## Последствия

- Миграция `20261006T2000_users_password_lifecycle.sql` (expand-only): `must_change_password`, `password_expires_at`,
  `password_changed_at`. Прежний образ эти колонки не читает.
- API-токены `tsk_` смена и сброс пароля не отзывают: это отдельные учётные данные, ими управляет владелец и
  администратор. Сессия «только смена пароля» на них тоже не распространяется.
- WebSocket-хендшейк флаг смены не проверяет: по сокету идёт только сигнал «перечитай», а само перечитывание
  получает 403.
- До первого входа учётки с хэшем старого формата сохраняется усечение до 72 байт.
- Самообслуживаемого восстановления по почте нет: сброс — через администратора (V6.4.3 выполняется
  административным процессом). Второго фактора по-прежнему нет (SEC-AUTH-01), обходить нечего.
- Блокировка по неверному текущему паролю, как и у входа, может использоваться для DoS известного логина —
  это общий вопрос SEC-AUTH-02.
