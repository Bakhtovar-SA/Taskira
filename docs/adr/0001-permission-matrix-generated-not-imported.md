# ADR-0001 — матрица прав генерируется из одного источника, а не импортируется общим модулем

**Статус:** принято (ТЗ 2.2, 2026-09-21). **Не предлагать «просто сделать общий импорт»** — это невозможно при текущих
контекстах сборки (ниже).

## Контекст

Матрицу прав (`MATRIX`, `PermId`) нужно знать и серверу (авторитетная проверка), и клиенту (мгновенные подсказки UI).
Раньше она была продублирована вручную в `src/permissions.ts` и `server/src/permissions.ts`.

## Ограничение: сервер и клиент собираются из разных контекстов

- Сервер: `server/Dockerfile` собирается из контекста `server/` (`docker build … server`), `tsconfig.json` имеет
  `rootDir: "src"`. Файл вне `server/` в образ не попадает, а `tsc` отвергает импорт из-за пределов `rootDir`.
- Клиент: корневой `Dockerfile` собирается из корня, но `.dockerignore` исключает `server/`. Импорт рантайм-значений из
  `server/src/...` в образе клиента не разрешится (для *типов* это неважно — `import type` стирается при сборке).
- Следствие: общий *рантайм*-модуль, лежащий в любом одном из двух мест, недоступен другой сборке.

## Решение

Общий источник — **данные**: `shared/permissions.matrix.json`. `scripts/generate-permissions.mjs` порождает из него
одинаковые `src/permissions.matrix.ts` и `server/src/permissions.matrix.ts` и `docs/PERMISSIONS.md`; `--check`
(`npm run permissions:check`, CI-джоба `types`, `server/test/permissions-sync.test.ts`) падает при любом расхождении,
включая ручную правку сгенерированного файла.

Логика поверх матрицы (`resolveRole`, `isOwnIssue`, `roleCan`/`can`, `denialReason`) остаётся продублированной в коде
и проверяется тестом **поведения**: клиентские `can()`/`denialReason()` против серверных на всех сочетаниях
роль × право × (нет задачи / своя как исполнитель / своя как автор / чужая).

## Последствия

- Изменение прав: правится JSON → `npm run permissions:generate` → коммитятся все три порождённых файла.
- Тот же приём допустим для других данных, которые нужны обеим сборкам (например, лимиты валидации сейчас сверяются
  разбором файла — кандидат на перевод в генерацию).
- Типы ответов API от этого ограничения не страдают: клиент импортирует их `import type` из `server/src/contract.ts`
  (ТЗ 2.1), в бандл ничего не попадает.
- **Идеальный вариант** — единый пакет логики прав, собираемый в оба образа. Это отдельная более крупная задача по
  архитектуре сборки (workspace/пакет + изменение контекстов Docker), не в скоупе ТЗ 2.2.
- Оговорка про типы контракта: zod-схемы в `contract.ts` — источник *типов*, не рантайм-гарантия соответствия БД
  (`.parse()` на границе сознательно не добавлен).
