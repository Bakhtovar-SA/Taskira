# ADR-0011 — Стор: подписки с селектором (`useSyncExternalStore`), миграция по доменам

**Статус:** Accepted
**Дата:** 2026-09-25 (технический спайк ТЗ 5.2)

## Контекст

Весь клиентский стор — один React Context (`src/store.tsx`, STORE-01). Значение контекста — объект `api`, который
собирается заново на **каждый** рендер `StoreProvider` (не мемоизирован), а в провайдере живут `data`, `ui`, `toasts`,
`bootStatus`, ревизии. Любая смена любого из них даёт новый `api` → перерисовываются все компоненты, вызвавшие
`useStore()`, и `memo` их не спасает: подписка на контекст обходит `memo`. Так `Card` на доске обёрнута в `memo`
(PERF-01), но сама вызывает `useStore()` ради `openIssue`.

Спайк должен был **измерить**, а не оценить, сколько компонентов перерисовывается на действиях доски, и, если
перерисовывается всё дерево, сделать прототип подписки с селектором для одного домена (список задач) и замерить
до/после. Переписывать стор в рамках спайка запрещено.

### Замер 1 — настоящая доска в jsdom

`src/perf/rerenders.test.tsx` (идёт в `npm test` без порогов; таблицы — `npm run perf:rerenders`): `StoreProvider` +
настоящие `Board`, `Bell`, `Toasts`, API замокан как в `board.lookups.test.tsx`, 3 колонки × 100 карточек.
Перерисованный компонент определяется через хук React DevTools: волокно в коммите — новый объект с флагом
`PerformedWork`. Время — сумма `actualDuration` из `<Profiler>`, медиана 7 повторов, диапазон по двум прогонам; это
jsdom и development-сборка React, абсолютные мс не браузерные. Число перерисовок от прогона к прогону не меняется.

| действие | коммитов | компонентов перерисовано | из них карточек | Σ actualDuration, мс |
|---|---|---|---|---|
| (a) тост | 1 | 2 868 | 300 | 102–124 |
| (b) счётчик непрочитанных +1 (WS `notify`) | 1 | 2 868 | 300 | 98–104 |
| (c1) правка приоритета одной задачи: ответ PATCH | 2 | 5 729 | 600 | 182–194 |
| (c2) … и перечитывание колонок по `issuesRevision` | 1 | 2 847 | 300 | 90–92 |
| (d1) начало перетаскивания | 1 | 2 861 | 300 | 111–185 |
| (d2) карточка над другой колонкой (`dragover`) | 1 | 2 861 | 300 | 90–93 |

**Перерисовывается всё дерево на каждое действие**, включая тост и счётчик уведомлений, к доске не относящиеся.
Причин три, и они независимы:
1. контекст (a, b, c1): новый `api` на каждый рендер провайдера;
2. `Board` передаёт в `memo(Card)` новые функции и массивы на каждый свой рендер (`onDragStart`, `onDropOn`,
   `moveTargets={targetsFor(…)}`, `assignees={….map(…)}`) — поэтому **локальное** состояние доски (d1, d2: подсветка
   колонки при перетаскивании) тоже перерисовывает все 300 карточек, и стор тут ни при чём;
3. перечитывание колонок (c2) заменяет все 100 объектов задач колонки новыми, даже неизменившиеся.

### Замер 2 — тот же сценарий в браузере

`scripts/perf-board/run.mjs`: production-сборка под production CSP, Chromium 141, API замокан через `page.route`,
300 карточек, два прогона при 1× и один при 4×; машина — контейнер разработки (Intel Xeon 2.1 ГГц × 4 vCPU), **не** эталонный i3-N305.

| метрика | CPU 1× | CPU 4× (замедление CDP) |
|---|---|---|
| кадры при `dragover`, колонка под курсором меняется каждый кадр | 29–32 мс/кадр, **31–34 fps** | 181 мс, 6 fps |
| то же, колонка не меняется (контроль: React не перерисовывает) | 16.3–16.6 мс, 60 fps | 19.7 мс, 51 fps |
| `dragstart` → кадр отрисован | 26–31 мс | 166 мс |
| клик по карточке (Event Timing `click`) | 56–80 мс | 272–336 мс |
| счётчик непрочитанных: событие → кадр с новым числом | 35–45 мс | 160 мс |

Разница строк 1 и 2 (≈13–16 мс на кадр при 1×) — это цена перерисовки 2 860 компонентов на кадр; её хватает, чтобы
перетаскивание по доске из 300 карточек не держало 50 fps уже на этой машине.

### Замер 3 — прототип селекторов и альтернатива

`src/store/experimental/selectorStore.ts` — прототип (~110 строк, без зависимостей): `createExternalStore`,
`useStoreSelector(store, selector, isEqual)` поверх `useSyncExternalStore`, домен «список задач» (`byId` + порядок по
колонкам, `useIssue(id)`, `useColumnIssueIds(statusId)`). **В продукте не используется** — его импортирует только замер.
Синтетический стенд в том же файле — 300 одинаковых карточек, три способа подписки:
A — как `store.tsx` (один контекст, `value` новый на каждый рендер); B — те же `useState`, но три контекста
(данные / тосты / действия) с мемоизированными `value`; C — прототип селекторов.

| действие (мс — диапазон по двум прогонам) | A: перерисовано / мс | B: перерисовано / мс | C: перерисовано / мс |
|---|---|---|---|
| (a) тост | 1 207 / 21–23 | 2 / 0.2–0.4 | 1 / 0.4–0.5 |
| (b) счётчик непрочитанных | 1 207 / 17–19 | 3 / 0.2 | 1 / 0.1–0.2 |
| (c) правка одной задачи | 1 207 / 18–18.5 | 10 (1 карточка) / 1.6 | 4 (1 карточка) / 0.6 |
| (c′) перенос задачи в другую колонку | 1 207 / 22–23 | 10 / 2.3–4.6 | 6 / 3.2–3.5 |

Выигрыш от ухода с одного контекста — два-три порядка по числу перерисовок и в 7–100 раз по времени. Разделённые
контексты (B) забирают почти весь выигрыш на тосте и счётчике, но остаются грубыми: любой потребитель «данных»
перерисовывается на любое изменение данных (в B доска перерисовалась от счётчика уведомлений), а правка одной задачи
перерисовывает все колонки и сравнивает 300 карточек. Селекторы (C) перерисовывают ровно тех, чьё значение
изменилось, и не требуют дробить контексты вручную.

## Решение

1. Стор переводится на **внешние хранилища доменов с подпиской по селектору** на встроенном
   `useSyncExternalStore` (прототип — `src/store/experimental/selectorStore.ts`). Без внешней библиотеки состояния:
   ~100 строк, 0 КБ к бюджету бандла.
2. Миграция **по доменам**, по одному PR на шаг; `useStore()` остаётся фасадом (возвращает то же, что сейчас),
   пока его вызывает хоть один компонент, — поэтому шаги не требуют переписывать экраны разом.
3. Каждый шаг расширяет `src/perf/rerenders.test.tsx` строкой «настоящей доски» для своего сценария и прикладывает
   таблицу до/после в PR. Порог в тест не вносится (замер, а не проверка), но регресс виден в выводе
   `npm run perf:rerenders`.

### План миграции

| шаг | домен | что меняется | снимает сценарий |
|---|---|---|---|
| 0 | не стор: пропсы карточки | `Board` передаёт в `Card` стабильные колбэки (по id задачи, через `useCallback`/ref), `moveTargets` мемоизирован по статусу, `assignees` — по списку id; `flash` вычисляется селектором. `useIssueSet.revalidate` сохраняет прежний объект задачи, если она не изменилась (`updatedAt`). | d1, d2, c2 — без этого шаги 1–5 не дадут 50 fps при перетаскивании |
| 1 | тосты | отдельное хранилище, `useToasts()`; `toast()` стабилен | a |
| 2 | уведомления | `unreadCount`, лента, настройки — хранилище; `Bell`/`BellPanel` через селекторы | b |
| 3 | действия | один стабильный объект действий (`useActions()`), состояние читается через ref'ы; компоненты, которым нужны только действия (`Card` → `openIssue`), перестают зависеть от данных | часть c1 |
| 4 | задачи | кэш `data.issues`, наборы колонок/списка и `issuesRevision` — в хранилище задач (`byId` + наборы); `useIssue(id)`, `useIssueSet` читает из хранилища; ответ PATCH меняет одну запись | c1 |
| 5 | UI-состояние | `view`, `selectedIssueId`, `createOpen`, `lastEvent` | переключение вида/модалок |
| 6 | проект и сессия | `project`, `users`, `members`, `workflow`, шаблоны, поля, спринты, `bootStatus`, `me`; `can()` — селектор над `me` | смена проекта |
| 7 | — | `useStore()` и контекст удаляются, когда вызовов не осталось | — |

Шаг 0 не зависит от стора и самый дешёвый; шаги 1–2 дают весь выигрыш на фоновых событиях при минимуме кода.

## Последствия

- Фоновые события (тост, WS-уведомление, 30-секундный опрос счётчика) перестают перерисовывать доску; правка
  задачи перерисовывает одну карточку. Это предпосылка бюджета «перетаскивание ≥ 50 fps на 300 карточках» и
  «открытие задачи < 150 мс» (docs/design/PERF-BUDGET.md).
- Появляется правило для нового кода: компонент читает стор **селектором ровно того, что показывает**; селектор
  возвращает стабильную ссылку (примитив, запись из `byId`, массив с `shallowEqual`), иначе `useSyncExternalStore`
  перерисует на каждое изменение хранилища.
- На время миграции живут два способа доступа (фасад `useStore()` и селекторы) — это осознанная цена поэтапности;
  фасад удаляется последним шагом.
- Прототип не перенесён в продукт и не проверен на реальных экранах, кроме синтетического стенда; цифры C —
  верхняя граница выигрыша для домена задач, а не обещание для всего приложения.
- Не решено здесь: реальное время для доски (`issue:upsert` по WS — `WsMessage` объявлен, не реализован) ляжет на
  хранилище задач шага 4 естественно, но это отдельное решение.

Отличия от плана, принятые при реализации:
- `src/store/external.ts` — прототип `createExternalStore`/`useStoreSelector`, перенесённый в продукт
  (`useExternalStore`, селектор и `isEqual` читаются через ref). Сам прототип `src/store/experimental/` оставлен
  как есть: его по-прежнему импортирует только замер (синтетический стенд A/B/C).
- Хранилища создаются на каждый `StoreProvider` (не модульные синглтоны) и раздаются через отдельный контекст
  `SlicesCtx` со значением, стабильным всё время жизни провайдера.
- Фасад `useStore()` сохранил все поля, **кроме `toasts`**: нереактивное поле фасада (читается, но не перерисовывает)
  тихо перестало бы обновляться у того, кто его использует, — ошибка компиляции при слиянии честнее. Тесты читают
  тосты и уведомления через свои пробы (`useToasts()`/`useNotifications()`), `store.api.test.tsx` обновлён.
- Лента и счётчик сбрасываются ровно там, где раньше сбрасывались вместе с `data`: ветки `bootstrap()`,
  `switchProject()`, `logout()`, 401 в `handleApiError`. Сброс счётчика при смене проекта (до следующего опроса или
  фокуса) — прежнее поведение, сохранено сознательно; уведомления не принадлежат проекту, и это стоит исправить
  отдельно.
- Шаг 0: структурное разделение сравнивает задачу по содержимому, а не только по `updatedAt` — ранг и состав
  исполнителей сервер может менять, не трогая `updated_at`. `flash` вычисляется в колонке из `ui.lastEvent` и
  приходит в карточку булевым пропсом (memo держит), а не отдельным селектором.
- Замер: в фикстуре `src/perf/rerenders.test.tsx` метки времени задач фиксированы (раньше `new Date()` на каждый
  ответ давал «изменившиеся» задачи при каждом перечитывании, чего настоящий сервер не делает).

Не шаг этого ADR, но в той же работе: предзагрузка чанков `IssueModal`/`CreateIssueModal` (`src/lazyModals.ts`,
