# ADR-0010 — Динамические стили под CSP: CSSOM и кастомные свойства, а не правило на значение

**Статус:** Accepted
**Дата:** 2026-09-25 (технический спайк ТЗ 5.2)

## Контекст

Продукт отдаёт строгую CSP (`nginx.conf`, все три `add_header` совпадают):

```
default-src 'self'; script-src 'self'; style-src 'self'; style-src-attr 'none'; img-src 'self' data: blob:;
font-src 'self'; connect-src 'self'; object-src 'none'; base-uri 'none'; frame-ancestors 'none';
form-action 'self'; manifest-src 'self'
```

Инлайн-стилей нет с коммита 9c4d560 («security procurement artifact»): `src/secure-jsx/` перехватывает JSX, превращает
проп `style` в класс `taskira-dyn-N` и вставляет правило `insertRule` в same-origin лист `public/dynamic.css`
(`src/secure-jsx/dynamicStyle.ts`). **Каждое новое значение — новое CSS-правило навсегда** (кэш по `cssText`, правила
не удаляются). Сейчас в клиенте 76 мест с `style={…}` (без тестов); неограниченные значения уже есть — полосы таймлайна
(`left`/`width` на задачу), прогресс импорта Trello (дробные проценты), цвета пользователей и направлений. Трек UX
добавит ещё: анимации, drag&drop, прогресс-бары, фоны проектов, позиционирование поповеров — всё это значения из
данных или из кадра анимации.

Вопрос спайка: какие механизмы передачи динамических значений реально работают под **этой** CSP и при каком из них
число CSS-правил не растёт с числом значений. Проверять в браузере, а не по документации.

### Как проверяли

`scripts/csp-spike/` (воспроизводимо, команда — в шапке `run.mjs`): `server.mjs` читает строку CSP из `nginx.conf`
и отдаёт `page/` с этим заголовком; `run.mjs` открывает страницу в Chromium через Playwright, собирает
`securitypolicyviolation` (подписка до разбора `<body>`, `page/early.js`) и консоль браузера, меряет
`getComputedStyle`/геометрию и число CSS-правил в документе до и после каждой проверки. Три контрольные проверки
обязаны быть заблокированы — иначе скрипт выходит с кодом 1 («CSP не действует, результатам верить нельзя»).
`@floating-ui/dom` 1.8.0 и `playwright-core` ставились во временный каталог вне репозитория; React-проба собирается
esbuild'ом из `node_modules` репозитория (production-сборка React 19.3.0, **без** `secure-jsx`).

Прогон 25.09.2026, **Chromium 141.0.7390.37 — единственный доступный браузер**:

Итог прогона: 3 нарушения CSP за страницу — ровно три контроля; в консоли браузера три «Refused to apply inline
style…» (`style-src-attr 'none'` ×2, `style-src 'self'` ×1); остальные 20 проверок — без единого нарушения. Отдельно
(`scripts/perf-board/run.mjs`): вся production-сборка на доске из 300 карточек с открытием задачи — 0 нарушений.

Что говорит спецификация (для Firefox/Safari — **проверено по спецификации/документации, не в браузере**):
директива `style-src-attr` / `style-src` без `'unsafe-inline'` блокирует атрибут `style` в разметке и через
`setAttribute`, но **не** присваивания свойствам `element.style` (CSSOM) — их, по замыслу CSP, ограничивает
`script-src`. Отдельно CSP3 описывает `'unsafe-eval'` для `style-src` как разрешение **строковых** методов CSSOM
(`insertRule()`, сеттеры `cssText`); по данным MDN, ни один браузер эти методы сейчас не блокирует — то есть
текущий `dynamicStyle.ts` (строковый `insertRule`) и сконструированные листы (`replaceSync`) работают потому, что
этот пункт не реализован, а не потому, что он разрешён. Web Animations API под CSP не подпадает.

## Решение

1. **Непрерывные значения из данных** (координаты и ширины полос таймлайна, прогресс, цвета пользователей и
   направлений, фон проекта) передаются **кастомными свойствами через CSSOM** на самом элементе
   (`el.style.setProperty('--bar-left', …)`) или на корне (`document.documentElement` — тема/фон проекта) и
   потребляются **конечным набором статических правил** в `src/index.css` (`.timeline-bar { left: var(--bar-left);
   width: var(--bar-width) }`). Число правил не зависит от числа значений (замер: 1000 значений → +0 правил).
2. **Значения кадра** (позиция перетаскиваемого элемента, позиционирование поповеров) пишутся прямыми
   присваиваниями CSSOM (`el.style.transform`, `left/top`) из обработчика или `ref`. `@floating-ui/dom` делает именно
   это и под нашей CSP работает во всех режимах (`absolute`, `transform`, `fixed`, `autoUpdate`). Это вывод о
   механизме, а не выбор библиотеки поповеров.
3. **Анимации** — `@keyframes` в статическом CSS для постоянных движений и **Web Animations API** (`el.animate`) для
   движений, зависящих от данных (из точки A в точку B); анимируемые кастомные свойства регистрируются `@property` в
   статическом CSS. Генерировать `@keyframes` в рантайме нельзя.
4. **Перечислимые состояния** (категория статуса, тон, плотность, режим) — `data-*` атрибуты + конечный набор правил,
   как уже сделано для `data-theme`/`data-atmosphere`/`data-texture` (ADR-0012).
5. **Не используем:** правило на значение — ни `insertRule` в `dynamic.css`, ни сконструированные листы
   (`adoptedStyleSheets` работает, но растёт так же: +1000 правил на 1000 значений, и опирается на тот же
   нереализованный пункт CSP3 про строковые методы CSSOM); `<style>`, `setAttribute('style')`, `style=""` в строках
   HTML (заблокированы, проверено). Типизированный `attr()` работает в Chromium, но в Firefox/Safari его нет —
   только как прогрессивное улучшение поверх п. 1.
6. **Судьба `secure-jsx`.** Проверено: React 19 сам применяет проп `style` через CSSOM (`style[prop] = …`,
   `style.setProperty` — `setValueForStyle` в `react-dom`), и под production CSP это работает без нарушений, в том
   числе с кастомными свойствами. Значит, генерация класса на каждое значение в `dynamicStyle.ts` для соответствия
   CSP **не нужна**, а рост правил она создаёт. Решение: перевести `secure-jsx` на передачу `style` штатной обработке
   React (CSSOM) — отдельной задачей трека, с обновлением `dynamicStyle.test.tsx`; `public/dynamic.css` после этого не
   нужен. До перевода новый код с непрерывными значениями **не** передаёт их через проп `style` (сейчас это тоже
   класс на значение), а пишет кастомное свойство в `ref`/`useLayoutEffect` по п. 1.
7. CSP не меняется: ни `'unsafe-inline'`, ни хэшей, ни `'unsafe-eval'` для стилей.

## Последствия

- Число CSS-правил в документе становится константой сборки; `dynamic.css` перестаёт расти за сессию (сейчас
  таймлайн с N задачами добавляет правила на каждую полосу и каждый сдвиг).
- В DOM появится отражённый атрибут `style="…"` на элементах с CSSOM-стилями — это **не** нарушение CSP (браузер его
  не блокирует, проверено), но аудит «нет атрибута style в DOM» больше не выполняется. Гарантия безопасности —
  заголовок CSP (`style-src-attr 'none'`), и она не ослабляется: разметка из строк по-прежнему не может принести стиль.
- Из этого следует ограничение: DOM с CSSOM-стилями нельзя сериализовать в HTML и вставлять обратно
  (`innerHTML`-копия, печать через строку) — стили потеряются. SSR не используется, поэтому сейчас это не проблема.
- Санитайзер значений из `dynamicStyle.ts` (запрет `{};@`, `url(`) остаётся нужен только там, где пользовательская
  строка попадает в значение; через `setProperty` значение разбирается как значение одного свойства, вставить
  соседнее правило нельзя.
- Firefox и Safari не проверены в браузере — вывод по ним опирается на спецификацию и MDN; перед выпуском трека
  спайк нужно прогнать в них (страница `scripts/csp-spike/page/` не зависит от Chromium, драйвер — да).
- Если браузеры когда-нибудь реализуют `'unsafe-eval'` для строковых методов CSSOM, текущий `dynamicStyle.ts`
  сломается; после п. 6 это нас не касается.
