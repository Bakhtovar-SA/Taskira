# Architecture Decision Records (ADR)

Документ вида «SCOPE.md» утверждает что-то о настоящем времени, а решения меняются — поэтому такие документы
устаревают. **ADR фиксирует решение на дату и не устаревает по построению:** он либо `Accepted`, либо
`Superseded by ADR-MMMM`. Что *сейчас* реализовано, показывает код и порождаемые из него документы
([`PERMISSIONS.md`](../PERMISSIONS.md), [`MIGRATION-LIST.md`](../MIGRATION-LIST.md), [`API-SCHEMAS.md`](../API-SCHEMAS.md));
*почему* так решили — здесь.

## Правила

1. Одно решение — один файл `NNNN-краткое-имя.md` по [шаблону](./TEMPLATE.md) (Контекст / Решение / Последствия /
   Статус / Дата). Дата — дата **самого решения** (миграция, коммит, PR), а не дата написания ADR.
2. Изменение решения = **новый ADR** со строкой `Supersedes ADR-NNNN`; в старом меняется **только** строка
   `Status: Superseded by ADR-MMMM`. Содержание старого ADR никогда не редактируется.
3. Опечатки и битые ссылки править можно; менять смысл — нельзя.
4. ADR не описывает «как сейчас устроено» — только выбор, причины и цену.

## Что здесь намеренно нет

**Database-per-tenant.** В репозитории нет решения об этом: ни в SCOPE.md, ARCHITECTURE.md, UI_RESTRUCTURE.md, ни в
миграциях, ни в истории; в `CLAUDE.md` зафиксировано обратное — «single project, no multi-tenant» — и это
ограничение реализации, а не оформленное решение. ADR задним числом про то, чего не решали, не создаётся; если
мультитенантность будет обсуждаться — это будет новый ADR с реальной датой.
