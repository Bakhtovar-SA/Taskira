# ADR-0008 — Клиентский роутинг: `wouter`, а не `react-router`

**Статус:** Accepted
**Дата:** 2026-09-22

## Контекст

ТЗ 3.1 (план v2, Трек 3) требует настоящего роутера с адресуемыми URL вместо самодельного
разбора `location.hash` в сторе (`readIssueHash`/`HASH_ISSUE_RE`, `src/store/mappers.ts`,
`src/store/session.ts`) и переключения вида через `ui.view` без роутера (`App.tsx`). До этого
момента в проекте роутера не было: `react-router-dom` входил в исходный набор зависимостей и был
удалён как неиспользуемый (см. `CLAUDE.md`, «Root package.json был подрезан»,
`react-router-dom` в списке убранного) — на тот момент ни одна часть приложения роутер не
использовала, обычный hash-переход обслуживал только deep link на задачу.

Ограничение, зафиксированное в самом ТЗ 3.1: фронтенд отдаётся из закрытой сети (on-prem
инсталляция, см. Трек 1 плана v2), вес бандла имеет значение — «выбрать по размеру бандла».

## Решение

Роутер — `wouter` (не `react-router`/`react-router-dom`).

- `wouter` (ядро + hooks) — единицы КБ minzipped; `react-router-dom` v7 — на порядок больше
  (полный набор: data router, loaders/actions, nested layouts — ничего из этого приложению не
  нужно: нет SSR, нет server actions, у стора уже есть собственный слой данных `src/store.tsx`
  и `src/api/`, дублировать его через router loaders было бы шагом назад).
- Требованиям ТЗ 3.1 (path-параметры, программная навигация, синхронизация query-параметров,
  защищённые роуты с сохранением целевого URL) `wouter` отвечает напрямую (`useRoute`,
  `useLocation`, `useSearch`/ручная работа с `URLSearchParams`, `<Redirect>`), без надстроек.
  Список видов (`ViewId` в `src/types.ts`) плоский, без вложенных лэйаутов — фичи
  `react-router`, которых приложению не хватает, ему и не нужны.
- Совместим с React 19 (`peerDependencies: react >=16.8.0`), API стабилен последние несколько
  мажорных версий.

## Последствия

- Плюс: минимальный вклад в вес бандла на закрытых инсталляциях (см. Контекст).
- Минус: меньше «из коробки» — нет предзагрузки данных под роут, нет встроенного intent-based
  prefetch. Приложению это и раньше было не нужно (данные тянутся через `store.bootstrap()`/
  `switchProject()`, не через роутер) — не потеря относительно текущей архитектуры.
- Минус: экосистема меньше, чем у `react-router` (меньше сторонних расширений, меньше вопросов
  на Stack Overflow) — риск для проекта такого размера (десяток видов, без вложенной
  маршрутизации) признан незначительным.
- Если требования вырастут (вложенные лэйауты, data loaders, SSR) — это повод для нового ADR,
  а не для расширения этого решения задним числом.
