# ADR-0025 — Календарь проекта; организация — про проекты, проект — про задачи

**Статус:** Accepted
**Дата:** 2026-10-01
**Supersedes:** ADR-0013 (в части списка представлений проекта и клавиш 1–4: добавлена 5)

## Контекст

Календарь нужен для планирования задач по срокам без изменения их таймлайна. Организационный обзор должен
показывать портфель проектов, а обзор одного проекта — его задачи. Основание: трек J.

| Уровень | Объекты | Представления |
|---|---|---|
| Организация | Проекты | Роадмап и дашборды |
| Проект | Задачи | Доска, список, таймлайн, календарь, обзор; спринты при включённом модуле |

## Решение

Календарь — пятое рабочее представление проекта (`calendar`, `/p/:projectKey/calendar`). Клавиши 1 Доска,
2 Список, 3 Таймлайн, 4 Спринты сохраняются; 5 открывает Календарь. Вкладка стоит после Таймлайна.
Обзор остаётся отдельной вкладкой. Календарь не входит в `PROJECT_DEFAULT_VIEWS`, миграция не нужна.

Плашка находится в дне `dueDate`. Отдельное поле начала задачи не вводится: как календарь Jira по умолчанию,
календарь отвечает на вопрос «когда срок», а таймлайн сохраняет свою модель. Перенос и клавиша M используют
обычный PATCH задачи с правом `edit`; панель «Без срока» — `dueEmpty=1`, возврат туда ставит `dueDate=null`.
Фильтр не записывается в сохранённые виды. Противоречие с dueFrom/dueTo/overdue даёт VALIDATION 400 в общем
построителе WHERE, без ZodEffects на расширяемой схеме.

Месяц всегда содержит шесть недель с понедельника, неделя — семь дней. Все страницы видимого диапазона
загружаются до 500 задач; дальше показано ограничение. День и плашка мемоизированы, обработчики стабильны.
Срок меняется после принятого сервером ответа; при отказе прежняя дата остаётся, ошибка показывается тостом.
Месячный «ещё N» дублирует плашки в поповере без `data-issue-id`: J/K читают единственный порядок всех задач
в сетке, включая скрытый хвост дня. «Без срока» — немодальная колонка, чтобы перенос в сетку оставался доступен.

Три виджета расширяют закрытый список ADR-0022: `projects`, `projectHealth`, `milestones`. Сохранённые дашборды
не преобразуются. Организационный набор: состояние, вехи, таблица проектов, прогресс, разбивка проектов, тренд.
Каталог обзора проекта не предлагает projects/projectHealth/by-project/progress; сохранённые старые виджеты работают.
Встроенный обзор проекта добавляет вехи только при их наличии. Данные всегда ограничены видимостью проектов.

Состояние вычисляет одна серверная функция по **всем** задачам, включая архив. Первое подходящее правило:

1. total > 0 и open = 0 — Завершён.
2. Прошедшая целевая дата и open > 0 — Просрочен.
3. До целевой даты ≤ 14 дней и закрыто < 80%, или open > 0 и overdue × 4 ≥ open — Под угрозой.
4. Есть целевая дата — По плану.
5. Иначе — Без срока.

Для 80% используется целочисленное сравнение `(total-open)*5 < total*4`; пустой проект имеет долю 0 и никогда
не завершён. Таблица проектов получает агрегаты одним запросом с группировкой. «Сегодня» для общего портфеля
и счётчиков — `CURRENT_DATE` сервера; календарь и сроки карточек используют локальную дату смотрящего.
Около полуночи в разных поясах возможно расхождение на день — это принятое различие областей представления.

В текущей схеме вехи имеют только имя, дату и порядок: признака «отмечена» нет. Без новой миграции все вехи
считаются неотмеченными; прошедшие показаны первыми, будущие — до `periodDays` включительно. Возможность отмечать
завершение вехи требует отдельного решения и не имитируется завершением задач проекта.

## Проверка и последствия

Юнит-тесты раскладки, состояния, границ контрактов; компонентные тесты действий и запретов; браузерные сценарии
RU/EN в обеих темах, axe и снимки в `test-results`. Замеры — `docs/PERFORMANCE.md`.
Дополнительных разрешений, индексов или миграций нет. Таймлайн и роадмап не меняются.
