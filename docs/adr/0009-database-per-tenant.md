# ADR-0009 — Database-per-tenant: одна БД = одна организация, без `organization_id` в схеме

**Статус:** Accepted
**Дата:** 2026-09-22

## Контекст

`CLAUDE.md` фиксирует «single project, no multi-tenant» как *свойство кода*, но в репозитории до
сих пор не было решения о мультитенантности как таковой — ни в `SCOPE.md`, ни в
`ARCHITECTURE.md`, ни в миграциях, ни в истории ADR (см. `docs/adr/README.md`, раздел «Что здесь
намеренно нет», записанный при закрытии ТЗ 2.4). Диагностика перед этим ADR
(`docs/tickets/TENANCY-01-isolation-diagnosis.md`) установила факты:

- Ни в одной таблице или колонке нет `organization_id`/`tenant_id` — ни в 29 legacy-миграциях,
  ни в коде сервера.
- Один процесс сервера держит ровно один `DATABASE_URL` (`config.ts`) и один пул подключений
  (`db.ts`), без переключения БД/схемы по запросу.
- Единственный деплой-путь (`docker-compose.yml`, `DOCKER_SETUP.md`) поднимает один `postgres` +
  один `server` + один `client` на инсталляцию.
- Миграция 007 уже ввела **multi-project внутри одной БД** (`departments`, `projects.is_shared`,
  резолв проекта по `:projectId`) — это отдельная ось от мультитенантности: несколько проектов
  одной организации в одной БД, не несколько организаций в одной БД. Смешивать эти две оси —
  источник будущей путаницы, которую предыдущий роадмап (см. план v2, преамбула Трека 4) уже
  называл по имени: сущность `organizations` в схеме тенанта провоцирует писать
  `WHERE organization_id = ...` и получить худшее из обоих вариантов мультитенантности.

Продукт уже эксплуатируется в проде у одного клиента (Мегафон) в описанной выше физической
изоляции. Вопрос — не «переходить ли на database-per-tenant», а «признать ли явным решением то,
что уже так устроено», прежде чем ТЗ 4.1 (singleton `instance` вместо таблицы `organizations`)
начнёт писать код поверх этого предположения.

## Решение

1. **Модель мультитенантности — database-per-tenant.** Одна физическая база PostgreSQL и один
   процесс сервера (или их отказоустойчивый набор за одним `DATABASE_URL`) обслуживают ровно одну
   организацию-клиента. Разных организаций в одной базе не бывает и не планируется.
2. **В схеме тенанта нет и не будет `organization_id`/`tenant_id`** ни в одной таблице — ни в
   существующих, ни в новых. Это осознанное решение, а не пробел: обратное («общий инстанс с
   несколькими БД/схемами на клиента») отклонено, потому что необходимости в нём никто не
   предъявил (единственный текущий клиент — одна инсталляция), а код, различающий тенантов внутри
   одной БД, добавляет постоянный риск межтенантной утечки (забытый `WHERE organization_id = ...`
   в одном из множества запросов) ради возможности, которой продукт не использует.
3. **Multi-project (миграция 007) — это ось, ортогональная тенантности**, и ей не переименовывается
   и не сворачивается: несколько проектов/департаментов одной организации в одной БД остаются как
   есть, вне контура этого решения.
4. **Control plane — отдельный сервис**, не таблица внутри тенантской БД. Управление парком
   инсталляций (версии, лицензии, provisioning) не должно жить в той же базе, которую оно же
   администрирует — иначе операция над самим объектом администрирования (например, снос БД при
   деprovisioning) сносит и историю об этой операции.
5. **Конфигурация уровня организации остаётся в `.env` процесса, не переезжает в БД.** LDAP/S3/SMTP
   и прочие настройки, специфичные для инсталляции, — это уже конфигурация уровня организации при
   database-per-tenant: свой процесс, свой `.env`, ничего общего с соседней инсталляцией не
   разделяется в принципе. Таблица `instance` (ТЗ 4.1) хранит только то, что читается из самой БД
   в рантайме (имя, план, лицензия) — не LDAP-байнд, не SMTP-креды. Прежнее ТЗ 3/4 из старого
   роадмапа (перенос .env-конфига в БД) отклонено как отдельная задача — переносить нечего:
   `.env` на инсталляцию уже даёт то разделение, которое эта задача пыталась бы получить второй раз.

## Последствия

**Даёт:**
- Физическая изоляция клиентских данных по определению — нет запроса, который может случайно
  прочитать чужого тенанта, потому что чужого тенанта нет в этой БД вообще.
- ТЗ 4.1 может ввести singleton `instance` без `organization_id`-миграции по всем таблицам —
  экономит миграцию через 15+ таблиц и постоянный риск забыть колонку в новой таблице.
- Снимает двусмысленность, которую предыдущий роадмап уже назвал ловушкой: `organizations` как
  сущность в схеме тенанта.

**Стоит:**
- Нет пути к «общему SaaS на одной БД» без нового ADR и реальной миграции данных — если это
  понадобится, это отдельное решение с собственной ценой, не расширение текущего.
- Provisioning новой инсталляции (ТЗ 4.2) — это разворачивание нового процесса + новой БД, а не
  INSERT новой строки в существующую; операционная стоимость на клиента выше, чем у shared-схемы,
  и её несёт control plane (см. решение п.4), а не тенантский код.
- Резервное копирование/восстановление/апгрейд — за инсталляцию, не централизованно; это
  предпосылка, которую последующие ТЗ Трека 4 (backup, апгрейд) обязаны принять как данность, а не
  переоткрывать.

**Осталось за скобками:** формат и протокол control plane (какой сервис, как аутентифицируется
перед инсталляциями) — предмет отдельного ADR при реализации Трека 4 дальше ТЗ 4.1.
