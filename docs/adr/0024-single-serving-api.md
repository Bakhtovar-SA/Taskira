# ADR-0024: Один обслуживающий API-процесс на БД

**Статус:** Accepted
**Дата:** 2026-09-30

## Контекст

Реестры WebSocket, отметки отзыва сессий и кэш авторизации находятся в памяти API.
Блокировки фоновых задач и общий лимитер входа в PostgreSQL не обеспечивают доставку
push и инвалидацию авторизации между репликами (A09 аудита 2026-09-29).

## Решение

Поддерживаем один обслуживающий API-процесс на БД организации. До миграций и listen
процесс получает session advisory lock `taskira:serving-api` на отдельном соединении.
Второй процесс завершается с объяснением. При потере соединения владелец немедленно
завершается; штатная остановка освобождает владение после закрытия HTTP и пула БД.
Используется прямое PostgreSQL-соединение, без transaction pooling.
Heartbeat каждые 10 с с таймаутом 5 с предотвращает обычный idle-disconnect и ограничивает
время обнаружения неотвечающего соединения. Повторный захват при продолжающемся обслуживании
не допускается: за окно без владения могут быть пропущены отзывы сессий.
Остановка HTTP/WS и пула имеет общий срок 10 с; зависшее закрытие завершается выходом процесса,
который освобождает session lock. Освобождать лок до закрытия API нельзя.

## Последствия

Обновление требует остановки предыдущего API перед запуском нового. Rolling deployment
и горизонтальное масштабирование serving API пока не поддерживаются. Для их введения
нужны общий транспорт push/invalidation, восстановление после потери событий и новый ADR.
Межпроцессные локи фоновых задач сохраняются для служебных запусков и будущего расширения.
