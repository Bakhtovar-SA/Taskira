# Трек K — скорость доски и открытия задачи

Цели — [docs/design/PERF-BUDGET.md](../design/PERF-BUDGET.md): **≥ 50 fps** при перетаскивании на доске с 300 карточками,
**INP < 200 мс** на основных действиях. Последний замер (`docs/PERFORMANCE-CHECK-2026-09-30.md`, i3-N305, 300 карточек,
production-сборка):

| Что | CPU 1× | CPU 4× |
|---|---:|---:|
| Доска до 300 карточек | 2381 мс | 11479 мс |
| Перетаскивание со сменой колонки | 40 fps | 11 fps |
| Начало перетаскивания, медиана | 25,1 мс | 160 мс |
| Первое готовое содержимое задачи | 146,6 мс | 1310,6 мс |

Там же сказано: машина в момент замера была занята другой работой, разброс большой (40–78 fps между прогонами), и
нельзя понять, что даёт код, а что — шум. Поэтому трек начинается с честного замера и профиля, а не с правок наугад.

Порядок: K1 → K2 → K3 → K4 → K5. Исполнитель — Codex. Ветка `codex/board-speed` от свежего `main`, PR — черновик,
коммиты по-русски, по одному на задачу. Мерж — только после «да» владельца.

Перед началом прочитать `CLAUDE.md` («Client data flow», «Gotchas»), [ADR-0011](../adr/0011-store-selector-subscriptions.md)
(план шагов 0–7 и таблица выполнения), `docs/design/PERF-BUDGET.md`, `src/perf/rerenders.test.tsx`,
`scripts/perf-board/run.mjs`. Правила треков G–J в силе; поведение и внешний вид не меняются — меняется только
скорость. Тесты не ослаблять, только менять селекторы.

## Общие правила замеров

- Всё — `scripts/perf-board/run.mjs` на production-сборке под production CSP, `THROTTLE=1,4`, **3 прогона** на каждую
  точку, в отчёт — медиана и разброс. Перед прогоном остановить всё лишнее (другие рабочие копии, dev-серверы,
  сборки); в отчёте записать, что было запущено на машине.
- Каждый шаг K2–K4 — «до» и «после» на одной машине подряд. Шаг, который не улучшил свою цифру больше разброса,
  **не мержится** — откатить и записать в отчёт, почему не сработало. Это тоже результат.
- `npm run perf:rerenders` — таблица числа перерисовок до/после для каждого шага (как в ADR-0011).
- Сценарии, которые нельзя сломать: прокрутка колонок, поиск и фильтры, перетаскивание (включая запрещённый переход и
  откат при ошибке сервера), `J`/`K`, меню `M`/`Ь`, массовые действия, чтение экранным диктором (axe), обе темы.

## K1. Замер и профиль

1. Прогнать `run.mjs` на текущем `main` (там уже календарь трека J) — три прогона, 1× и 4×.
2. Разложить «доска до 300 карточек» на части: сеть/страницы (`ISSUE_PAGE_SIZE = 100`, сколько запросов и идут ли они
   друг за другом), разбор ответа, первый рендер, шрифты. Добавить в `run.mjs` отметки (`performance.mark`) по этим
   границам, если их нет — сам замер должен показывать, где время.
3. CDP-профиль (Performance) трёх сценариев при 4×: первая отрисовка доски, перетаскивание со сменой колонки,
   открытие задачи. Для каждого — топ-5 затрат (скрипт / стиль / раскладка / отрисовка; какие компоненты и функции).
4. Результат — раздел «Трек K» в `docs/PERFORMANCE.md`: таблица «сейчас», топ затрат, и **решение, какие из K2–K4 делать
   и в каком порядке** (с цифрами). Если профиль покажет причину, которой нет в K2–K4, — описать её и предложить шаг
   там же; владелец решает, делать ли его в этом треке.

## K2. Стабильные действия (ADR-0011 шаг 3)

- Один стабильный объект действий `useActions()` (ссылка не меняется за жизнь `StoreProvider`; состояние внутри
  действий читается через ref'ы, как `dataRef` в `store/session.ts`). `useStore()` остаётся фасадом и возвращает те же
  действия.
- Перевести на `useActions()` компоненты, которым от стора нужны только действия: карточка доски и календаря, строки
  списка, `BulkBar`, кнопки шапки — по результатам K1, в первую очередь то, что попало в профиль.
- Тест: ссылка `useActions()` одна и та же после изменения данных; `rerenders.test.tsx` — строка «до/после».
- ADR-0011, таблица выполнения: шаг 3 — «выполнен», коммит, что дал (цифры).

## K3. Задачи в своём хранилище (ADR-0011 шаг 4)

Сейчас ответ на открытие задачи (`openIssue` в `store/session.ts`) делает `setData` всего объекта `Data` — и
перерисовывается всё, что читает `useStore()`. Отсюда секунда на открытие при 4×.

- Хранилище задач по образцу `src/store/slices.ts`: `byId` + наборы (колонки доски, список, календарь),
  `issuesRevision`; подписка по селектору через `useSyncExternalStore`. `useIssue(id)` — одна задача; `useIssueSet`
  читает из хранилища.
- `openIssue`, `updateIssue`, `moveStatus`, `PATCH`-ответы и WS-«перечитай» меняют **одну запись**; панель задачи
  подписана на свою задачу, доска — на свои наборы.
- Переходный период: `useStore().data.issues` и `idx.issues` продолжают работать (собираются из хранилища), пока
  есть вызовы; новые места пишут только через хранилище. Удаление фасада — шаг 7, не в этом треке.
- Гоча из `CLAUDE.md` про `upsertIssue()` и `comments`/`activity` (открытая карточка должна показывать то, что пришло
  с сервера, а не прежнее пустое) — покрыть тестом до переноса и сохранить.
- `store.bootstrap.test.tsx` расширить: загрузка задач через хранилище, ответ открытия задачи меняет одну запись.
- Тест перерисовок: открытие задачи и смена статуса из панели не перерисовывают карточки доски, кроме изменившейся.
- Если K1 покажет, что открытие тормозит не из-за `setData`, а из-за содержимого панели (`IssueModal.tsx` — 1500
  строк), — сначала то, что показал профиль (ленивые вкладки «Комментарии»/«История», `memo` на тяжёлых секциях), с
  замером; шаг 4 тогда — отдельным PR после.

## K4. Первая отрисовка доски

По результатам K1, по одному изменению с замером:
- если страницы задач грузятся друг за другом — загружать колонки параллельно (сервер уже отдаёт набор по статусу);
- если время уходит на стили и раскладку 300 карточек — `content-visibility: auto` с `contain-intrinsic-size` у
  карточек вне экрана (DOM остаётся: поиск по странице, `J`/`K`, axe и перетаскивание работают как раньше; проверить
  каждое), правило — в `src/index.css` рядом со стилями доски;
- виртуализацию колонок (рисовать только видимые карточки) **не** делать в этом треке: она ломает перетаскивание,
  `J`/`K` и чтение диктором, и требует отдельного решения (ADR), если K4 без неё цели не достигнет.
