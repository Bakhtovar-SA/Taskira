## M1. Безопасность

### SEC-ASVS-01. Самопроверка по OWASP ASVS 5.0 уровня 2
**Что:** пройти главы V1 (кодирование/инъекции), V2 (валидация), V6 (аутентификация), V7 (сессии), V8 (авторизация),
V9 (токены), V12 (файлы), V13 (API), V14 (конфигурация) по серверу.
**Результат:** `docs/security/ASVS-L2.md` — таблица «требование → статус (выполнено / частично / нет / неприменимо)
→ доказательство (файл:строка или тест) → тикет, если не выполнено». Без доказательства статус «выполнено» не ставится.
**Критерии приёмки:** покрыты все требования L2 перечисленных глав; каждое «нет/частично» имеет тикет в `docs/tickets/`.
**Важно:** это самопроверка, не аудит. Документ явно говорит, что внешний аудит — SEC-EXT-01.

### SEC-IDOR-01. Матрица доступа по всем маршрутам
**Проблема:** доступ проверен по ресурсам, но нет гарантии, что *каждый* маршрут с `:projectId`/`:id` проверен на
«чужой проект / чужая команда / чужая задача / деактивированный / гость-коллаборатор».
**Что:**
1. Тест, который после `buildApp()` перечисляет все зарегистрированные маршруты (`app.printRoutes` или хук `onRoute`)
   и сверяет со списком `server/test/access/routes.manifest.ts`. Новый маршрут без записи в манифесте → тест падает.
2. Запись манифеста: метод, путь, ожидаемый ответ для каждой роли-сценария (`anon`, `outsider`, `employee-foreign-issue`,
   `collaborator-other-issue`, `deactivated`, `api-token-out-of-scope`) — `401/403/404`.
3. Табличный тест прогоняет манифест на реальной БД (фикстура: два проекта, две команды, по пользователю каждого типа).
**Критерии:** все маршруты в манифесте; тест в CI; найденные расхождения — исправлены в том же PR или вынесены тикетами
с пометкой severity. 404 vs 403 — единое правило (не раскрывать существование чужого ресурса), записать в SECURITY_OVERVIEW.

### SEC-RATE-01. Лимиты на чувствительные действия
**Проверить и при необходимости добавить:** смена пароля, сброс пароля (если есть), создание API-токена,
ручной повтор вебхука, экспорт данных/аудита, поиск, `POST /dashboards/data`, отчёты CSV.
**Результат:** таблица «маршрут → лимит → ключ (user/ip) → где реализовано» в SECURITY_OVERVIEW; тесты на 429.
Лимитер должен работать в рамках ADR-0024 (в памяти процесса допустимо, состояние входа — как сейчас).

### SEC-DEPS-01. Зависимости и образ — недостающее
**Уже есть в `test.yml`:** `npm audit --audit-level=high` в обоих пакетах, Trivy (fs + image) с `.trivyignore.yaml`,
`check-trivy-ignore.sh` (требует у исключения `owner=` и `expired_at`).
**Сделать:**
1. `check-trivy-ignore.sh`: падать, если `expired_at` уже в прошлом (сейчас проверяется только наличие даты).
2. gitleaks по всей истории — новый шаг в CI.
3. `npm audit`: оставить с dev-зависимостями (сборочные пакеты тоже попадают в цепочку поставки), но описать в
   SECURITY_OVERVIEW, как временно принять уязвимость в dev-зависимости, если исправления нет.
**Критерии:** просроченное исключение валит CI (тест в `test-release-scripts.sh` или отдельный); gitleaks зелёный на `main`.

### SEC-SSRF-01. Ревизия SSRF вебхуков
**Проверить тестами:** DNS rebinding (резолв на этапе проверки ≠ на этапе соединения — соединяться по уже проверенному IP),
редиректы (запрещены или повторно проверяются), IPv6 (`::1`, `fc00::/7`, `::ffff:127.0.0.1`), десятичная/восьмеричная
запись IP, `0.0.0.0`, link-local `169.254.0.0/16` (метаданные облака), порт-фильтр, таймауты и лимит размера ответа.
**Критерии:** каждый случай — тест в `egress.test.ts`; отсутствующее — исправлено.

### SEC-EXT-01. Внешний аудит (не код)
**Что:** подготовить пакет для внешнего аудитора: ASVS-L2 из SEC-ASVS-01, SECURITY_OVERVIEW, стенд, учётки всех ролей,
scope. Результат аудита — `docs/AUDIT-<дата>-external.md` + тикеты.
**Критерий:** аудит проведён до первой продажи; все high закрыты.

## M2. Обновления у клиента и Podman

### OPS-PODMAN-01. Rootless Podman — проверка и документация
**Проверить на чистой машине (RHEL 9 / Rocky 9 или Astra/РЕД ОС — что реально у клиентов):**
rootless запуск через `install.sh`; права на тома (UID mapping, `:Z`/`:z` под SELinux); `podman-compose` vs `podman kube`/quadlet;
автостарт после перезагрузки (`systemd --user` + `loginctl enable-linger`); порты < 1024 в rootless.
**Результат:** раздел в `README_INSTALL.md.in` «Podman rootless» + известные проблемы; при необходимости quadlet-юниты в релизе.
**Критерии:** прогон зафиксирован в `docs/MANUAL-CHECK-TRACK-M.md` (команды + вывод); CI-job с `podman` (ubuntu-runner
поддерживает) выполняет `install.sh` → health → `upgrade.sh`.

### OPS-UPG-01. Матрица «чистая установка» и «обновление с N-1» в CI
**Что:** проверить, что `test-upgrade-integration.sh` действительно берёт **предыдущий опубликованный релиз** (тег), а не
текущий код с другой БД. Если нет — job: поднять релиз N-1 → наполнить данными (`performance-seed` в малом объёме) →
`upgrade.sh` до HEAD → health + выборочные API-проверки данных. Отдельный job: чистая установка HEAD.
**Критерии:** оба job в CI на каждый PR, трогающий `server/migrations/` или `scripts/`, и ночью на `main`.

### OPS-UPG-02. Откат в `upgrade.sh`
**Что:** обновление = бэкап → стоп → новый образ → миграции → health-check → при провале: стоп, восстановление бэкапа,
запуск старого образа, ненулевой код выхода и понятное сообщение. Тест: искусственно сломанная миграция → система
вернулась к N-1 с прежними данными.
**Критерии:** сценарий отката покрыт интеграционным тестом; в OPERATIONS.md описано, когда откат автоматический, а когда
нужно руками (contract-миграции необратимы — указать явно).

### OPS-PG-01. Поддерживаемые версии PostgreSQL
**Что:** зафиксировать матрицу (например 14–17), CI-матрица серверных тестов по этим версиям (минимум мин. и макс.),
раздел «Обновление PostgreSQL» в OPERATIONS.md (pg_dump/restore между мажорами, `pg_upgrade`), проверка версии при
старте сервера с предупреждением в `/ready`/экране состояния.
**Критерии:** CI зелёный на всех версиях матрицы; сервер отказывается стартовать на версии ниже минимальной.

### OPS-DOC-01. Документация для администратора клиента
**Один документ** `docs/ADMIN-GUIDE.md` (RU), собирающий: требования к серверу (CPU/RAM/диск для 700 пользователей —
из замеров), порты, переменные окружения (сгенерировать список из `config.ts`, не вручную; проверка в CI как у
permissions), TLS/прокси (`deploy/https`), бэкап и восстановление, обновление, откат, сбор `support-bundle.sh`,
что прислать в поддержку. Ссылки, а не копии существующих документов.
**Критерии:** таблица переменных генерируется и проверяется на дрейф.

## M4. Нагрузка и фоновые задания

### PERF-OBS-01. Метрики латентности API и очередей
**Что:** гистограмма времени ответа по маршруту (шаблон пути, не URL), размер очереди вебхуков/outbox, возраст самого
старого недоставленного события, длительность фоновых заданий (частично есть `taskira_background_job_*`).
Пороговые предупреждения на экране состояния (ADR-0031).
**Критерии:** метрики в `/metrics`; описание в OPERATIONS.md; тест на наличие метрик.

### PERF-LIMIT-01. Ограничение тяжёлых запросов
**Что:** `statement_timeout` для отчётов, экспорта, поиска, дашбордов (на уровне транзакции, отдельный от обычных
запросов); лимит размера/строк экспорта; не более N одновременных тяжёлых запросов (семафор в процессе) с 429/503 сверх.
**Критерии:** тест: тяжёлый отчёт не увеличивает p95 обычного `GET issues` больше чем на X% (сценарий в
`performance-*.mjs`, цифры в PERFORMANCE.md).

### PERF-PG-01. pg_stat_statements и индексы
**Что:** инструкция включения `pg_stat_statements` в ADMIN-GUIDE; блок «медленные запросы (топ-10)» в `support-bundle.sh`
и на экране состояния, если расширение доступно (не требовать); проверка индексов больших таблиц (`issues`, `activity`,
`audit_log`, `notifications`, outbox) на объёме 500k+ — отчёт в PERFORMANCE.md.

### PERF-WORKER-01. Отдельный процесс фоновых заданий (проектирование, ADR)
**Что:** новый ADR: режим запуска того же образа `ROLE=worker` (без `listen`, без serving-lock ADR-0024) для архивации,
вебхуков, sweeper'а, LDAP resync, напоминаний. Учесть: push в WebSocket идёт из serving API — worker не может
вызвать `pushToUser` напрямую (нужен канал, например `LISTEN/NOTIFY`, или push остаётся за API).
**Критерии:** ADR принят; реализация — **только если** PERF-OBS-01 покажет влияние фоновых задач на p95 API.

## M5. Наблюдаемость и разбор инцидентов

### OBS-LOG-01. Структурные логи
**Проверить и довести:** JSON-логи pino с `reqId` во всех строках запроса, `userId` (не email/имя), `projectId`, маршрут-шаблон;
фоновые задачи с `job` и `runId`; `reqId` возвращается клиенту в заголовке `x-request-id` и показывается в тосте ошибки
(«Код ошибки: …») — пользователь клиента может его продиктовать. Редакция секретов: токены, пароли, cookie, `Authorization`.
**Критерии:** тест, что пароль/токен из тела не попадает в лог; тест заголовка.

### OBS-RUNBOOK-01. Ранбук «упало в 2 ночи»
**Что:** `docs/RUNBOOK.md` — симптом → где смотреть → команды: не открывается сайт, 500 на всём, не приходят письма,
не работает вход LDAP, не доставляются вебхуки, растёт диск, второй процесс не стартует (ADR-0024 lock), миграция упала

## M6. Bus factor и поддержка (не код)

### BUS-01. Документ для второго разработчика
`docs/ONBOARDING-DEV.md`: как поднять всё локально за час, путь запроса (клиент → store → api → middleware → route → service →
БД), где права, где фоновые задачи, где миграции, как выпустить релиз. Проверка: человек, не видевший проект, поднимает
стенд и исправляет учебный баг по документу; замечания внесены.

### BUS-02. Второй человек
Найти разработчика (частичная занятость / договор), провести по BUS-01, дать доступ к репо и стенду, совместно разобрать
один реальный инцидент. Без этого продажа нескольким клиентам — риск №1.

### BUS-03. Условия поддержки в договоре
SLA (время реакции по severity), каналы, что входит/не входит, порядок обновлений, эскроу исходного кода или передача
кода при прекращении поддержки. Согласовать с юристом.
