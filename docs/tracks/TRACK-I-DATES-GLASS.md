## I1. Оставшиеся нативные даты → `DatePicker` из `src/ds`

У `DatePicker` теперь есть `min`/`max` (G6), поэтому мешавшая причина ушла. Перевести:

| Файл | Поле | Особенность |
|---|---|---|
| `src/components/CreateIssueModal.tsx` (~395) | срок задачи | как срок в карточке задачи (`IssueModal.tsx`: `DatePicker block`) |
| `src/components/Backlog.tsx` (~830) | фильтр «срок с / по» | «с» → `max={to}`, «по» → `min={from}`; узкое меню фильтра — `block`; пустое значение — `null` ↔ `""` |
| `src/components/ReportsView.tsx` (~236, ~248) | период отчёта «с / по» | та же пара `min`/`max`; формат запроса к API не менять; `markOverdue={false}` |
| `src/components/SprintsView.tsx` (~137) | начало и конец спринта | `markOverdue={false}`; конец не раньше начала (`min`) |
| `src/components/settings/OrgSettings.tsx` (~443) | период экспорта журнала | пара `min`/`max`, `markOverdue={false}` |

- Подпись поля (`label`) и текст пустого значения (`placeholder`) — из словаря; у срока задачи — как в карточке.
- `DatePicker` отдаёт ISO `YYYY-MM-DD` или `null` — проверить, что сервер получает то же, что раньше получал из
  `<input type="date">` (пустое поле раньше было `""`).
- Тесты: характеризующие тесты списка и создания задачи — зелёные (менять только селекторы: ввод даты — текстом в поле
  календаря и Enter, как в `issueModal.characterize.test.tsx`). Новый тест на пару «с/по»: выбрать «с» позже «по»
  нельзя.
- В браузере, обе темы: каждое поле — открыть, выбрать, ввести словами, очистить; клавиатура (стрелки, Enter, Esc).
- В `COMPONENTS.md` убрать фразу «В «Отчётах» и спринтах пока нативные даты».

## I2. Прозрачность: «как в системе / включена / выключена»

Сейчас при `prefers-reduced-transparency: reduce` или `prefers-contrast: more` (в Chrome/Edge на Windows — выключенные
«Эффекты прозрачности») боковая панель и рабочий лист становятся непрозрачными (`src/index.css`, блок
`@media (prefers-reduced-transparency …)`). Это верно по умолчанию, но человек не видит, почему «пропало стекло», и не может
вернуть его только для Taskira.

- В «Личные настройки → Оформление» добавить выбор «Прозрачность»: «Как в системе» (по умолчанию), «Включена»,
  «Выключена» — `RadioGroup` из `ds`, рядом с темой и плотностью.
- Личный выбор — `localStorage` `taskira.transparency` (`auto | on | off`).
- **Итог вычисляет JS, CSS только читает атрибут.** Одна чистая функция `resolveTransparency(personal, org,
  reducedTransparency, contrastMore)` → `"on" | "off"` пишет на `<html>` `data-transparency="on|off"` (атрибут всегда
  стоит, значения `auto` в нём нет). CSS: правила снижения прозрачности из блока `@media (prefers-reduced-transparency …),
  (prefers-contrast: more)` переносятся под `[data-transparency="off"]`, сам `@media`-блок удаляется — системные признаки
  учитывает функция. Без JS (атрибута нет) — стекло, как в браузерах без поддержки этих признаков.
- Функцию вызывают `public/theme-init.js` до первой отрисовки и `src/theme.ts` при смене выбора, а также по событию
  `change` у `matchMedia` для обоих системных признаков (человек переключил настройку Windows при открытой вкладке).
- `public/theme-init.js` — обычный JS без сборки, импортировать TS-модуль он не может, поэтому функция в нём написана
  второй раз, слово в слово, между комментариями-метками `// resolveTransparency:start` и `// resolveTransparency:end`.
  Тест `src/transparency.test.ts` вырезает этот кусок из `public/theme-init.js`, исполняет его и сравнивает с версией из
  `src/transparency.ts` на полной таблице: 3 личных значения × 2 значения организации × 2 × 2 системных признака = 24 строки.
  Разошлись — тест падает.
- Под выбором — подсказка одной строкой, когда при личном «Как в системе» стекло выключила система: «Система просит
  меньше прозрачности — стекло выключено».
- `npm run contrast:check` должен проходить в обоих режимах; `motion:check`, `colors:check` — без изменений.
- Тест: атрибут на `<html>` ставится из `localStorage` и меняется при выборе; таблица функции — выше.

## I3. Прозрачность по умолчанию для всей организации

Владелец: у сотрудников на рабочих Windows «Эффекты прозрачности» часто выключены (политика, удалённый рабочий стол,
экономия батареи), и каждый увидит Taskira без стекла. Просить всех менять настройку системы нельзя, а личный выбор из I2
найдёт не каждый. Нужна настройка администратора, которая задаёт поведение «по умолчанию» для всех.

- «Организация → Брендирование»: «Прозрачность по умолчанию» — «Как в системе» (как сейчас) / «Всегда включена».
  Только глобальный администратор, как остальные поля брендирования.
- Сервер: столбец в `instance` (новая миграция по `docs/MIGRATIONS.md`, по умолчанию `auto`), значение — в контракте и в
  публичном `GET /api/instance/brand` (`transparencyDefault: "auto" | "on"`), правка — там же, где сохраняется бренд,
  запись в `audit_log` как у остальных полей бренда. Тест сервера: чтение, правка админом, запрет не админу.
- Клиент: значение кэшируется в `taskira.brand` вместе с оттенком (`src/brand.ts`); `public/theme-init.js` читает его
  оттуда и передаёт в ту же `resolveTransparency` как аргумент `org` — второго места с правилом нет.
- Правило внутри функции (таблица теста I2 его и проверяет):
  1. личное «Включена» → `on`; личное «Выключена» → `off` — независимо от остального;
  2. личное «Как в системе» и `prefers-contrast: more` → `off` (повышенный контраст — потребность доступности; организация
     его не перекрывает);
  3. личное «Как в системе» и организация «Всегда включена» → `on`, даже при `prefers-reduced-transparency`;
  4. личное «Как в системе» и организация «Как в системе» → `off` при `prefers-reduced-transparency`, иначе `on`.
- Подсказка из I2 под личным выбором учитывает и это: «Организация включила прозрачность для всех» / «Система просит
  меньше прозрачности — стекло выключено».
