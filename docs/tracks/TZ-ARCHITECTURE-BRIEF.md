# ТЗ для архитектора: следующий трек Taskira

Задача для Opus: спроектировать архитектуру, оформить её как ADR и разбить работу на трек с тикетами.
Код не писать. Результат отдаётся исполнителю (GPT), который будет реализовывать по тикетам без доступа к твоим рассуждениям, поэтому тикеты должны быть самодостаточными.

## 1. Контекст

Taskira — внутренний корпоративный трекер задач (доска, список, таймлайн, календарь, воркфлоу, дашборды) с ролевой системой прав.
Стек: React 19 + TypeScript + Vite (корень), Fastify 5 + PostgreSQL + JWT (`server/`).
Перед работой прочитай:
- `CLAUDE.md` — архитектура и ограничения (обязательно целиком);
- `server/README.md` — контракт API и модель данных;
- `docs/adr/README.md` и ADR-0001, 0005, 0009, 0017, 0019, 0022, 0024, 0025 — формат и прежние решения;
- `docs/MIGRATIONS.md` — правила миграций БД;
- `docs/SECURITY_OVERVIEW.md`, `docs/OPERATIONS.md`, `server/BACKUP.md`;
- `docs/tracks/` — примеры оформления треков.

## 2. Цель

Сократить ручную работу и дать интеграцию с внутренними системами, не превращая продукт в конструктор процессов.

## 3. Что проектируем (в порядке приоритета)

1. **Исходящие вебхуки и API-токены.**
   События: задача создана/изменена/сменила статус/назначена/прокомментирована, наступил срок.
   Нужны: подписки на уровне проекта, подпись запросов, ретраи с backoff, журнал доставок, ручной повтор, отключение подписки после серии отказов, защита от SSRF.
   API-токены: персональные и сервисные, область действия, срок жизни, отзыв, хранение только хеша.
2. **Повторяющиеся задачи.**
   Расписание создаёт задачи из существующих шаблонов (`issue_templates`).
   Нужны: формат расписания, часовой пояс, поведение при простое сервера, защита от дублей, права, история.
3. **Единый экран состояния для администратора + регулярная репетиция восстановления.**
   Экран собирает то, что уже есть: `/ready`, метрики фоновых заданий, хранилище, почта, последний бэкап.
   Репетиция восстановления запускается по расписанию и сообщает результат.
4. **Автоматизации по правилам (только проектирование, без реализации в этом треке).**
   Опиши, как они ляжут на вебхуки и события из п. 1, и предложи минимальный набор готовых правил вместо языка правил.

## 4. Жёсткие ограничения (из текущей архитектуры)

- Один обслуживающий API-процесс на БД (ADR-0024). Фоновые задания не должны полагаться на многореплика-координацию.
- Права: источник истины — `shared/permissions.matrix.json`. Новые права добавляются только через него; нужно обоснование каждого `PermId` или решение переиспользовать существующий.
- Контракты запросов и ответов — в `server/src/contract.ts` (zod как источник типов); лимиты зеркалятся в `src/validation.ts`.
- Миграции — по `docs/MIGRATIONS.md`: файлы с timestamp-префиксом, expand/contract, без неразмеченных destructive-операций.
- История задач — данные, не текст: новое событие = член union `ActivityEvent` + ключи i18n.
- UI двуязычный (RU/EN), цвета только токенами, CSP запрещает inline-стили, попапы только `ds` `Menu`/`Popover`.
- Серверный текст локализуется на клиенте по коду ошибки; новые коды ошибок получают ключи `apiError.*`.
- Секреты не хранятся в открытом виде и не попадают в логи, аудит и экспорт.
- Развёртывание локальное (docker-compose, без облака); внешних сервисов без явной необходимости не добавлять.

## 5. Что должно быть в результате

1. **ADR** (по `docs/adr/TEMPLATE.md`, следующий свободный номер): контекст, рассмотренные варианты (минимум 2 на каждое ключевое решение), принятое решение, последствия. Если решение меняет прежний ADR, указать `Supersedes ADR-NNNN`, не редактируя старый.
2. **Модель данных**: таблицы, поля, индексы, связи, политика хранения и очистки журналов. Для каждой таблицы — описание миграции (expand/contract).
3. **API**: маршруты, схемы запросов и ответов, коды ошибок, права для каждого маршрута.
4. **Схема доставки событий**: откуда берутся события, как гарантируется «не потерять и не задублировать» при падении процесса, формат полезной нагрузки, версионирование.
5. **Безопасность**: модель угроз для вебхуков и токенов (SSRF, утечка секрета, повтор запроса, перебор, эскалация прав), что и как проверяется.
6. **Клиент**: экраны, где они живут в IA (`docs/design/IA.md`), состояния загрузки/пусто/ошибка, i18n-ключи, доступность.
7. **Наблюдаемость**: метрики `taskira_*`, записи аудита, что видно администратору.
8. **Производительность**: оценка нагрузки (сколько событий в секунду, сколько подписок), влияние на горячие пути (`PATCH issue`, `transition`), что измерять.
9. **Документация**: какие файлы обновить (`server/README.md`, `CLAUDE.md`, `docs/OPERATIONS.md`, `docs/SECURITY_OVERVIEW.md`, `docs/PERMISSIONS.md` — генерируется).

## 6. Трек и тикеты

Оформи трек в `docs/tracks/` по образцу существующих. Тикеты — в формате `docs/tickets/`.
Каждый тикет обязан содержать:
- цель одной фразой;
- точный список файлов, которые менять и создавать;
- зависимости от других тикетов и порядок;
- критерии приёмки, проверяемые командами (`npm run typecheck`, `npm test`, `npm run build`, `server: npm test`, `permissions:check`, `docs:generate` и т. д.);
- какие тесты написать (особенно: тест гонок, тест прав, тест дублей, тест SSRF);
- что явно **не** входит в тикет;
- риски и точки отката.

Размер тикета — один PR, который можно проверить за один заход. Порядок: сначала миграции и ядро, потом API, потом клиент, потом документация.

## 7. Чего делать нельзя

- Не предлагать новую инфраструктуру (очереди, Redis, внешние планировщики), если задачу можно решить в PostgreSQL и текущем процессе. Если без неё нельзя — обосновать и учесть ADR-0024.
- Не вводить язык правил и визуальный конструктор.
- Не менять существующие миграции и ADR.
- Не оставлять «решим при реализации»: каждый открытый вопрос должен быть либо решён, либо вынесен в раздел «Открытые вопросы» с рекомендованным вариантом.

## 8. Формат ответа

Сначала краткое резюме (до 15 строк): что решено и почему. Затем полный ADR, трек, тикеты. В конце — раздел «Открытые вопросы к владельцу продукта» и «Что исполнителю проверить вручную».
