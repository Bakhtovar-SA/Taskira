сделана — см. «Перепрогон 60 с после PERF-03».** Стенд: схема `taskira_perf`, 50 000 активных + 10 000 архивных задач в проекте PERF,

## Поиск на одном origin (без preflight)

Production-сборка без зашитого `VITE_API_URL`, Node-прокси на одном порту, реальный ввод, Resource Timing:

| Состояние | Сервер | Браузер |
|---|---|---|
| тёплое соединение, индексы есть | 3,9–6,7 мс | 9,5–11,8 мс |
| первый запрос после паузы ≥10 с (умолчание `pg`) | 107–411 мс | 114–418 мс |
| индексов нет (Seq Scan) | 78–158 мс на SQL | 117–418 мс |

Прежнее объяснение dev-цифры 149–167 мс («стоимость cross-origin и preflight») **неверно**: главные
статьи расхода — отсутствие триграммных индексов и холодное соединение с БД.

## Найденное по пути (все — не то, что искали)

1. **Пул `pg` без обработчика `error`** — обрыв простаивающего соединения (рестарт БД, failover) ронял бы
   процесс. Исправлено вместе с `idleTimeoutMillis: 0` (`6009945`). **Уровень MAINT-01, не тюнинг.**
2. **Холодное соединение с БД** — первый запрос после паузы дороже на 60–92 мс. Исправлено там же.
3. **Тесты молча удаляли триграммные индексы** (`pg_trgm` — общее для БД расширение, `DROP SCHEMA CASCADE`
   тестовой схемы удалял его и индексы чужих схем). Воспроизведено дважды. Тикет `TEST-01`, тесты переведены
   на отдельную БД.
4. **`GET …/issues/assignees` на порядок дороже остальных** (65 мс, Seq Scan) — кэш на процесс (`4e251ac`).
5. **`Data.seq`** — мёртвое поле давало неверную подсказку номера в окне создания. Исправлено (`80574ae`).
6. **`counts` уходит дважды при открытии доски** (Sidebar и Доска) — общий кэш счётчиков, решение уровня Трека 2.

## MAINT-01 на 515 403 задачах (21.09.2026, код `bb8148c`, временная копия БД)

Копия `CREATE DATABASE taskira_perf_maint TEMPLATE taskira` (схема `taskira_perf` лежит внутри БД `taskira`),
дозаливка 500 000 закрытых 40 дней назад задач (`performance-maint-seed.mjs`; вместе с уже подлежавшими — 515 402),
два процесса сервера с `MAINTENANCE_ENABLED=true`, `MAINTENANCE_MAX_PER_RUN=1000000` (один проход на всё), пачка 1 000,
пауза 50 мс. Копия удалена после замера; исходная `taskira_perf` не менялась (92 860 задач, 10 000 архивных).
Сводка: [`PERFORMANCE.maint-515k.summary.json`](../PERFORMANCE.maint-515k.summary.json) (сырой ряд замеров записи ~7 МБ
не хранится).

- **Проход:** 515 403 задачи за 144,9 с, 516 пачек (~280 мс на пачку с паузой), одна запись `maintenance.run` в
  `audit_log`. Из двух процессов работал один (метрика: `success` у 8082, `skipped` у 8081), счётчик
  `archived_issues_total` вырос только у исполнителя. Против расчёта 515 402 в проход попала 1 лишняя строка и
  1 подходящая осталась после — вероятно, задачи на границе 30-дневного порога; причину не проверял.
- **Задержка одной записи** (`performance-maint-probe.mjs`, прямой `UPDATE`, 4 потока на класс строк), мс:

| Фаза | строки, которые проход не трогает: p50 / p95 / p99 / max | строки под архивацию: p50 / p95 / p99 / max |
|---|---|---|
| до прохода, без нагрузки | 2,3 / 3,8 / 12,5 / 426 | 2,4 / 4,8 / 12,2 / 1 401 |
| проход, без нагрузки | 2,7 / 6,3 / 17,6 / 1 796 | 2,8 / 6,9 / 23,1 / 1 429 |
| проход + `load-lazy` 2×50 соединений без пауз | 3,5 / 25,6 / 59,2 / 7 396 | 4,4 / 33,4 / 67,7 / 8 312 |
| после прохода | 2,2 / 3,3 / 4,8 / 1 046 | 2,2 / 3,3 / 4,7 / 67 |

  Ошибок записи нет.
- **Нагрузка `mixed` (2×50 соединений):** без прохода 533 запр./с, p95 432–461 мс; во время прохода 208 запр./с,
  p95 1 011–1 206 мс, ошибок нет.

**Как это читать.** Пороговых значений p99 записи «согласованных» нет — замер даёт цифры, а не «прошёл/не прошёл».
Проход сам по себе поднимает p99 записи с 12 до 18–23 мс и не даёт пауз дольше ~1,8 с (на уровне единичных
выбросов до 1,4 с в фоне без прохода). Многосекундные паузы (до 8,3 с) случились только в окне «проход + насыщающая
нагрузка», причём **одинаково у строк, которых проход не блокирует** — то есть это не ожидание блокировки строки, а
конкуренция за диск/CPU одной 8-ядерной машины (клиент, два сервера, БД и запись 515 тыс. строк с 18 индексами).
Разделить вклад WAL/checkpoint и CPU этим замером нельзя. **Не измерено:** проход при штатном потолке 50 000 за
проход (оценка по пачкам — порядка 15 с на проход, это экстраполяция, не замер); раздувание таблицы и индексов
после массового `UPDATE` и работу autovacuum.

## Оговорки

- Замер на Node-прокси, а не nginx; функционально эквивалентно для устранения preflight, но не для
  настроек keep-alive/буферов nginx.
- Одна машина для сервера, БД и генератора: числа пессимистичны и не переносятся на прод-железо.
- Постоянные `PG_POOL_MAX × процессов` соединений после PERF-03 нужно учесть в `max_connections`.
