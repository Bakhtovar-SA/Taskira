# PERF-04 — перепрогон замера после PERF-05/06 (ЧЕРНОВИК)

**Статус: черновик. Все цифры получены ДО PERF-03 (несколько процессов сервера) и после него будут
пересобраны.** Стенд: схема `taskira_perf`, 50 000 активных + 10 000 архивных задач в проекте PERF,
9 дополнительных проектов; Postgres, сервер и генератор нагрузки на одной 8-ядерной Windows-машине;
не nginx (см. «Оговорки»).

## Что изменилось для пользователя

| Показатель | Было (PERF-00, bootstrap грузит проект целиком) | Стало |
|---|---|---|
| Запросов при входе на доску | ~250 (последовательный обход страниц по 200) | **16 к API** + WebSocket; три из них — списки колонок по 100 |
| Что грузит `bootstrap()` | все активные задачи проекта | ничего; задачи приходят наборами, по id и (Sprints) явно |
| Счётчик открытых задач, колонки | считались по загруженному массиву | `GET …/issues/counts` (один агрегат) |
| Быстрый поиск в Topbar | локально по всем задачам | сервер, топ-8, 250 мс дебаунс |

Полный список запросов холодного старта с временами — в `PERF-06-inventory.md` (по журналу сервера).

## Поиск на одном origin (без preflight)

Production-сборка без зашитого `VITE_API_URL`, Node-прокси на одном порту, реальный ввод, Resource Timing:

| Состояние | Сервер | Браузер |
|---|---|---|
| тёплое соединение, индексы есть | 3,9–6,7 мс | 9,5–11,8 мс |
| первый запрос после паузы ≥10 с (умолчание `pg`) | 107–411 мс | 114–418 мс |
| индексов нет (Seq Scan) | 78–158 мс на SQL | 117–418 мс |

Прежнее объяснение dev-цифры 149–167 мс («стоимость cross-origin и preflight») **неверно**: главные
статьи расхода — отсутствие триграммных индексов и холодное соединение с БД.

## Параллельная нагрузка (100 соединений без пауз, 15 с на сценарий)

| Запрос | запр./с до | среднее, мс до | после | среднее, мс после |
|---|---|---|---|---|
| `assignees?limit=24` | 44 | 2012 | 2765 (кэш 45 с) | 36 |
| холодный старт доски (6 запросов) | 181 (p95 1732 мс) | 563 | 503 (p95 319 мс) | 202 |
| смешанный (доска + поиск) | 316 (p95 1413 мс) | 320 | 623 (p95 331 мс, с индексами) | 170 |
| поиск с совпадениями | 634 | 160 | 599 | 170 |
| поиск без совпадений | 1411 | 71 | 1320 | 76 |

Прочее по одиночным запросам: `epics` 725 запр./с, `counts` 424, страницы колонок 356–412. Ошибок, таймаутов
и не-2xx нет. Это насыщение (каждое соединение шлёт запросы без пауз), а не пользовательская нагрузка.

## Найденное по пути (все — не то, что искали)

1. **Пул `pg` без обработчика `error`** — обрыв простаивающего соединения (рестарт БД, failover) ронял бы
   процесс. Исправлено вместе с `idleTimeoutMillis: 0` (`6009945`). **Уровень MAINT-01, не тюнинг.**
2. **Холодное соединение с БД** — первый запрос после паузы дороже на 60–92 мс. Исправлено там же.
3. **Тесты молча удаляли триграммные индексы** (`pg_trgm` — общее для БД расширение, `DROP SCHEMA CASCADE`
   тестовой схемы удалял его и индексы чужих схем). Воспроизведено дважды. Тикет `TEST-01`, тесты переведены
   на отдельную БД.
4. **`GET …/issues/assignees` на порядок дороже остальных** (65 мс, Seq Scan) — кэш на процесс (`4e251ac`).
5. **`Data.seq`** — мёртвое поле давало неверную подсказку номера в окне создания. Исправлено (`80574ae`).
6. **`counts` уходит дважды при открытии доски** (Sidebar и Доска) — общий кэш счётчиков, решение уровня Трека 2.

## Оговорки

- Замер на Node-прокси, а не nginx; функционально эквивалентно для устранения preflight, но не для
  настроек keep-alive/буферов nginx.
- Одна машина для сервера, БД и генератора: числа пессимистичны и не переносятся на прод-железо.
- Постоянные `PG_POOL_MAX × процессов` соединений после PERF-03 нужно учесть в `max_connections`.
