# PERF-05, шаги 2–3 — ленивая загрузка на клиенте: список задач и доска

Статус: выполнено 20 сентября 2026 года. Серверная часть — см.
[PERF-05-step1-server-filters.md](PERF-05-step1-server-filters.md).

## Что сделано

**Механизм** (`src/issuePages.ts`, вне `store.tsx`, чтобы не конфликтовать с
Треком 2):

- `useIssueSet(query, {withCounts})` — постраничный набор: первая страница,
  подгрузка по курсору, состояние `items / hasMore / loading / loadingMore /
  error`. Ключ набора — проект + фильтры + сортировка; смена любого элемента
  сбрасывает набор. Ответы устаревших запросов отбрасываются по поколению.
  Страницы дописываются в конец без пересортировки и дедуплицируются по id.
  Курсор живёт только в состоянии обхода — ни в URL, ни в сохранённых фильтрах.
  Синхронная защёлка `moreInFlight`: два `loadMore()` в одном тике (скролл +
  клик) не порождают два запроса.
- `useIssueCounts(projectId, filters, revision)` — один запрос счётчика на набор
  фильтров, не на страницу и не на рендер.
- `useLoadMoreSentinel` — подгрузка при прокрутке (IntersectionObserver) с
  кнопкой «Показать ещё» как обязательным запасным путём.
- `useDebounced`, `useIssuesRevision`, `useOnRevision`, `freshRows` — общие части.

**Список задач (Backlog)** — шаг 2: серверные фильтры, сортировка и поиск (с
задержкой 250 мс), общий счётчик из `counts`.

**Доска** — шаг 3: у каждой колонки свой независимый набор
(`ColumnCards` → `useIssueSet` с `status=<колонка>`, сортировка `rank`).

- Счётчик колонки — реальный, из `counts` (требование ТЗ 5.2). Считается одним
  запросом на все колонки (`byStatus`), а не по запросу на колонку.
- Окно «Готово»: колонка грузит `closed=recent&closedDays=14`; число в строке
  «Ранее закрыто» — отдельный `counts` с `closed=older`. «Показать всё» снимает
  окно.
- Фильтры доски (аватар, чипы «Мои»/«Просрочено»/«Без исполнителя», поиск) —
  серверные. Аватар и чипы «Мои»/«Без исполнителя» раньше складывались через И
  над загруженным; у сервера один параметр `assignee`, поэтому они сводятся к
  одному значению (`effectiveAssignee`), а противоречащие (чужой аватар + «Мои»)
  дают пустой набор через несуществующий id — как и прежнее И.
- Полоска аватаров-фильтров раньше строилась по исполнителям всех загруженных
  задач; теперь — новый `GET …/issues/assignees` (до 24 самых загруженных, плюс
  выбранный). Это видимое изменение: на проекте с сотнями исполнителей полоска
  показывает самых загруженных, а не всех.
- Плашка «показано N из M» (`issuesTruncated`) убрана — она была мертва после
  `listAllIssues` и теряет смысл при постраничных колонках.
- Сервер: `GET /api/projects/:projectId/issues/assignees?limit` (тест + замер:
  25 мс на PERF-проекте из 50 000 задач, один раз при открытии доски).

## Проверки

- Клиентские тесты: 143 (стало 116): хук набора, счётчиков, `freshRows`,
  чистая логика доски (`boardFilters.test.ts`: сведение фильтров, окно «Готово»,
  арифметика счётчиков, null до ответа сервера), подгрузка по прокрутке на
  подменённом `IntersectionObserver` (`loadMoreSentinel.test.tsx`).
- Тесты нашли реальный дефект: три `loadMore()` в одном тике слали три запроса.
- В браузере на стенде из 50 000 задач (`taskira_perf`, вход под `perf_001`):
  - колонки: 100 карточек в каждой, счётчики 1500 / 36375 / «Готово» 1410 +
    «Ранее закрыто: 10715» — совпали с SQL до единицы;
  - «Без исполнителя»: 458 / 10807 / 450 (+3232 ранее), «14947 из 50000» —
    совпало с SQL;
  - аватар + «Мои» противоречивы → 0 / 0 / 0, «0 из 50000»;
  - «Ранее закрыто» → «Готово» 12 125, сворачивание возвращает окно;
  - перемещение карточки в другую колонку: 1500→1499, 36375→36376, колонка
    осталась заполненной (после ревалидации подтянулась следующая карточка);
  - «Показать ещё» в «В работе»: 100 → 200 карточек, запрос
    `status=…&sort=rank&limit=100&cursor=…`.
- Список задач ранее: подгрузка прокруткой 100 → 400 без дублей; фильтр
  «редкий исполнитель» находит задачи за пределами первых страниц (72 из 72);
  поиск из 10 символов — один запрос страницы и один `counts`.

## Что НЕ достигнуто и почему

- **Открытие проекта по-прежнему дочитывает все страницы** (~250 запросов по 200
  на 50 000 активных задач; на стенде главный поток занят загрузкой десятки секунд). Ленивыми
  стали только список и колонки доски; `store.tsx` при `bootstrap()` по-прежнему
  вызывает `listAllIssues`, потому что `data.issues` читают Timeline, Sprints,
  Sidebar, модалки (подзадачи, эпики, связи, `CreateIssueModal`) и `idx`.
  Критерий ТЗ «не более 3 запросов списка при открытии» выполнится только когда
  эти потребители перейдут на собственные запросы — отдельное ТЗ, затрагивающее
  `store.tsx` (совместно с Треком 2).
- **Автоподгрузка на доске по прокрутке в браузере не проверена.** Вкладка,
  которой управляла автоматизация, была фоновой (`document.hidden = true`), а в
  фоновой вкладке колбэки `IntersectionObserver` не приходят (мой собственный
  контрольный наблюдатель тоже молчал). Логика хука проверена юнит-тестом;
  кнопка «Показать ещё» в браузере работает; в Списке задач прокрутка работала
  (видимость вкладки тогда я не проверял, предположительно она была на переднем плане).
- **Пункт 6 ТЗ (WS-события задач)** не применим: WS передаёт только `notify`.
- Не проверено: поиск на доске вводом с клавиатуры (тот же хук `useDebounced`,
  что в Списке), перетаскивание мышью (проверено перемещение через меню
  карточки; путь `moveStatus` общий), мобильная вёрстка.
- Стенд: на нём тестовая задача `PERF-1` перемещалась и возвращена SQL-запросом
  (статус, ранг, `updated_at`), запись `activity` удалена; строка `audit_log` о
  переходе осталась.
