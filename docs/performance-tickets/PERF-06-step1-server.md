# PERF-06, серверный PR — узкие точки доступа вместо обхода всех задач

Статус: выполнено 20 сентября 2026 года. Клиент не менялся. Решения из
[PERF-06-inventory.md](PERF-06-inventory.md), пункты C1–C4 (C5 — Sprints — без
серверных изменений).

## Что добавлено (только аддитивно; форматы PERF-05 не менялись)

| Что | Для кого | Контракт |
|---|---|---|
| Параметр `parentId` (uuid) в `IssueFilterQuery` | подзадачи в карточке | Работает в `GET …/issues` и `…/issues/counts`: те же пагинация, сортировка, курсоры и права. Архивные скрыты, `archived=all` возвращает их |
| Параметр `epicId` (uuid) в `IssueFilterQuery` | дети направления (Timeline, раскрытый узел) | То же |
| `GET …/issues/epics?limit=` (1–500, по умолчанию 200) | Timeline, справочник направлений Доски и Списка | `{items:[{id,key,title,color,tStart,tSpan,childTotal,childDone}], truncated}` — активные направления с агрегатом по активным детям; `childDone` по категории статуса `done`; порядок `rank, id`, как в списке |
| `epicChildrenCount` в детальном ответе `GET …/issues/:id` | признак «сама является направлением» | Число активных задач с `epic_id` = эта. В списке поля нет |

Решения, которые стоит знать:

- **`epicChildrenCount` считает только активных детей.** Так работала прежняя
  клиентская проверка (она видела только активный набор): поведение карточки не
  меняется. `subtasksSummary` при этом считает всех, включая архивных, и это
  осознанное различие двух счётчиков.
- **Фильтры, а не новые пути** (согласовано): подзадачи и дети направления
  переиспользуют пагинацию, сортировку и проверку прав основного списка.
- **Размер `epics` — число направлений, а не задач**; жёсткий потолок 500 с
  флагом `truncated`, как у `assigned-to-me`.

## Замеры (стенд `taskira_perf`, 5 холостых + 10 замеров, медиана)

Стенд дополнен направлениями (`performance-seed-topology.mjs`: до 60 на проект,
~8% активных задач ссылаются на них; в PERF — 60 направлений, 3 977 детей).

| Запрос | Время | План |
|---|---:|---|
| `epics`, PERF (3 977 детей) | 4,3 мс | Bitmap `idx_issues_epic` → HashAggregate → join к `issues_pkey` |
| `epics`, PX01 (1 540 детей) | 3,6 мс | то же |
| `epics`, PX03 / PX05 | 2,0 / 1,5 мс | то же |
| Страница `epicId` (87 детей) | 2,3 мс | Bitmap `idx_issues_epic` |
| `counts` с `epicId` | 0,6 мс | Bitmap `idx_issues_epic` |
| Страница `parentId` | 0,8 мс | Index Scan `idx_issues_parent` |
| `epicChildrenCount` | 0,5 мс | Bitmap `idx_issues_epic` |

**Индексы и миграции не нужны:** `idx_issues_epic` (001) и `idx_issues_parent`
(021) уже покрывают запросы; охранник миграций не задействован. Не измерено:
`epics` на проекте, где ссылаются на направления заметно больше 8% задач
(стоимость растёт с числом детей направлений, а не задач проекта); замеры на
одном клиенте, без параллельной нагрузки (PERF-04).

## Проверки

- `server/test/issueChildren.test.ts` (16 тестов): дети только этой задачи;
  архивные скрыты и возвращаются по `archived=all`; пагинация курсором, сортировка
  и счётчик по тому же набору; комбинация со статусом; не-uuid → 400; задача
  другого проекта ничего не возвращает; `epics`: агрегат `total/done` по
  категории статуса, архивные дети и архивные направления не учитываются,
  порядок совпадает со списком, `limit`/`truncated`, изоляция проектов, право
  `browse`; `epicChildrenCount`: активные дети, 0 у обычной задачи, подзадачи не
  делают задачу направлением, в списке поля нет.
- Мутационная проверка: убрать фильтр `epicId` и условие «не архивные» в `epics`
  — тесты падают (5 из 16).
- Полный серверный прогон и `tsc` — зелёные (см. коммит).

## Открытые пункты (не забыть к финальному перепрогону PERF-04)

1. **Доля задач, привязанных к направлениям.** Замер на PERF-проекте (50 000
   задач, 60 направлений) в транзакции с откатом, поэтому цифры слегка завышены
   (при 8% там 9 мс против 4,3 мс на закоммиченных данных):

   | Доля активных задач с `epic_id` | Детей | `GET …/issues/epics` | План |
   |---:|---:|---:|---|
   | 8% | ~4 000 | 9,0 мс | Bitmap `idx_issues_epic` |
   | 30% | ~15 200 | 21,4 мс | Bitmap `idx_issues_epic` |
   | 60% | ~30 000 | 67,9 мс | **Seq Scan** по `issues` |

   Стоимость растёт линейно с числом детей направлений, а не задач. Вывод для
   клиента: справочник направлений нужно грузить **один раз на открытие
   экрана** и обновлять по явному сигналу, а не на каждую ревалидацию наборов;
   при доле > ~30% рассмотреть материализованные счётчики (по образцу
   `has_assignee`, триггер на `issues.epic_id`) — решать после PERF-04 по
   реальному профилю, а не заранее.
2. **Параллельная нагрузка** на новые запросы — вместе с PERF-04.
