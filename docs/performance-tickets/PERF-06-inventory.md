# PERF-06, шаг 0 — инвентаризация чтения `data.issues`

Статус: **на согласовании**. Код не менялся. Шаг 1 не начат: масштаб работы ясен
только после этой таблицы, и он больше одного PR (см. «Порядок и объём»).

Метод: `grep` по всему `src/` (не только по списку из ТЗ) на `data.issues`,
`idx.issues`, `dataRef.current.issues`, `prev.issues`, `listAllIssues`, плюс
чтение кода каждого места. Тесты (`store.*.test.tsx`) в таблицу не входят, но их

## Исходное состояние (измерено)

`bootstrap()` (`store.tsx:697`, повтор в `refreshIssues`, `store.tsx:1033`) вызывает
`listAllIssues` — последовательный обход всех страниц по 200. На стенде из
50 000 активных задач это **~250 запросов** (в сетевом инспекторе видно первые
100 записей + счётчик 212 в буфере resource-timing, который ограничен 250) и
десятки секунд занятого главного потока. Результат кладётся в `data.issues`, и
от него зависят все места ниже.

## Порядок и объём

Порядок — от простых точечных к сложным; **каждый потребитель — отдельный коммит
и своя проверка в браузере на стенде 50 000 задач**:

1. **Сервер (C1–C4)** + тесты и замер `EXPLAIN`. Один PR, без изменений клиента.
2. **Срез стора `issues-lookup`** (кэш «id → задача», счётчик ревизии, фасад
   `data.issues`), bootstrap **пока грузит всё** — чистый рефакторинг под тестами
   (B1–B4, B7, A16). Второй PR; это же часть Трека 2 (ТЗ 2.3).
3. **Агрегаты:** A1 (WorkflowView), A2 (Sidebar). Малый риск.
4. **Модалки:** A4→A5→A8→A6 (уже готов)→A10, затем пикеры A7/A9/A11 (общий
   компонент серверного поиска). Самая объёмная часть.
5. **Topbar (A3), Board/Backlog справочник направлений (A12, A13).**
6. **Timeline (A14).**
7. **Sprints (A15)** — обёртка; затем **удаление `listAllIssues` из `bootstrap`**
   и проверка: заход на Доску ≤ 3 запросов списка, модалка с подзадачами без
   предзагрузки, тесты зелёные, охранник миграций, PERF-04 — нет цепочки ~250.

Ожидаемо это **пять–семь PR**, а не один: пункты 1, 2, 4 и 6 — самостоятельные
и объёмные.

## Изменения поведения (задокументированы намеренно)

| Что изменилось | Раньше | Теперь | Почему |
|---|---|---|---|
| **Удалённая карточка на Доске и в Списке исчезает после ревалидации, а не мгновенно** | `freshRows` отбрасывал строки, которых нет в сторе, и удалённая задача пропадала в тот же кадр | строка остаётся до перечитывания набора (`issuesRevision` растёт при удалении; один запрос страницы, десятки миллисекунд) | стор перестаёт держать весь проект: «нет в сторе» больше не значит «удалена» (подзадача, пришедшая с сервера, стору неизвестна и обязана показываться). Мгновенное исчезновение вернёт явный набор удалённых id в сторе, если это потребуется |
| Мутации по задаче, которой нет в сторе | молча выходили (`updateIssue`, `moveStatus`) или проверяли права без объекта | подтягивают задачу `GET /:id`, права применяются к ней; недоступна — явная ошибка | см. `PERF-06-step2-store-slice.md` |
| Пикеры связей и направлений | плоский `<select>` на весь проект | поиск по вводу, «недавно обновлённые» при пустом поле | `<select>` нежизнеспособен на 50 000 задач |
| Быстрый поиск в Topbar («в этом проекте») | мгновенный, локальный по всем загруженным задачам | запрос на сервер через 250 мс, топ-8, «Поиск…» и скелет пока идёт запрос, ошибка с «Повторить». Гибрид «сразу локально, потом с сервера» сознательно не делался: два источника для одного списка дают дубли и пропуски в переходный период | стор перестаёт держать весь проект |
| Выбор цели связи | выбор в списке + кнопка «Связать» | выбор строки сразу создаёт связь | один шаг вместо двух |

## Реестр риска «нет в сторе ≠ не существует»

Три найденных случая подряд (проверка прав, `freshRows`, ослабление проверки в
кэше) — один системный класс ошибок перехода «всё в памяти → частично». Места,
где отсутствие в `data.issues`/`idx.issues` сейчас читается как отсутствие сущности
(проверено `grep` по `find/get/some/has/length`), и их статус:

| Место | Как читает отсутствие | Последствие при частичном сторе | Статус |
|---|---|---|---|
| `Backlog.tsx:29`, `Board.tsx:628` — эпик в строке/на карточке | `idx.issues.get(epicId)`; нет → бейдж скрыт | бейдж эпика пропадает у задач, чьё направление не загружено | **впереди** (A12–A13: справочник направлений) |
| `Board.tsx:457` — `dragged` | `issuesById.get(dragId) ?? null`; нет → подсказки «переход запрещён» и `canDropTo` перестают работать | при перетаскивании карточки, не попавшей в стор, все колонки выглядят допустимыми | **впереди**: брать перетаскиваемую задачу из загруженных страниц колонок |
| `TimelineView.tsx:59–73,127` — «направления» и дети | `epicIds` выводится из `epicId` **загруженных** задач; `done/total` — по загруженным детям | пустой Timeline или неверные счётчики | **впереди** (A14: `GET …/issues/epics` с `childTotal/childDone`) |
| `store.tsx` — `deleteIssue` (побочные эффекты) | `iss` из стора; нет → не правится `subtasksSummary` родителя | счётчик подзадач родителя может остаться прежним до перечитывания | принято: побочный эффект необязателен, карточка родителя перезапрашивается при открытии; проверить в шаге Timeline |
| `store.tsx` — каскады B3 (удаление обнуляет `parentId`/`epicId` у детей, завершение спринта — `sprintId`) | меняют только известные стору задачи | неизвестные дети подтянутся уже с актуальными значениями сервера | принято |
| `IssueModal.tsx:588` — открытая задача | `find(selectedIssueId)`; нет → модалка не рисуется | между кликом и ответом `GET /:id` модалка пуста, если задачи не было в сторе | принято: `openIssue` кладёт задачу в стор сразу после ответа |
| `useIssue` (`issuePages.ts`), `withIssue`/`resolveIssue` (`store.tsx`) | нет → точечный `GET`; только 404/403 — «недоступна» | — | **сделано** (отсутствие ≠ несуществование) |

При переводе каждого следующего потребителя этот реестр проверяется первым.

## Открытые пункты для перепрогона PERF-04

Не факты, а обязательства: цифры ниже пока получены на стенде разработчика и в
dev-сборке, и «обещанные» значения не должны потеряться среди прочего.

1. **Задержка поиска на одном origin через nginx.** В браузере (dev, cross-origin
   :3001 → :8081, с CORS-preflight на каждый запрос) поиск Topbar занял 149–167 мс.
   Это стоимость окружения, а не сервера: SQL-уровень — 2,5–10 мс на триграммных
   индексах. Замерить сквозную задержку `?q=&limit=8` на прод-подобном деплое
   (один origin, nginx, без preflight), включая случаи «удачный ввод» и «нет
   совпадений», и только эту цифру сообщать клиенту.
2. **`GET …/issues/epics` при доле направлений 30–60%** (9 → 21 → 68 мс) — см.
   `PERF-06-step1-server.md` и тикет EPIC-01.
3. **Параллельная нагрузка** на `issues`, `counts`, `epics`, `assignees` и поиск.
4. **Цепочка ~250 запросов при открытии проекта** должна исчезнуть из трассировки
   после удаления `listAllIssues` из `bootstrap` (последний шаг PERF-06).
