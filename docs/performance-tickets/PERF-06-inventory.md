# PERF-06, шаг 0 — инвентаризация чтения `data.issues`

Статус: **на согласовании**. Код не менялся. Шаг 1 не начат: масштаб работы ясен
только после этой таблицы, и он больше одного PR (см. «Порядок и объём»).

Метод: `grep` по всему `src/` (не только по списку из ТЗ) на `data.issues`,
`idx.issues`, `dataRef.current.issues`, `prev.issues`, `listAllIssues`, плюс
чтение кода каждого места. Тесты (`store.*.test.tsx`) в таблицу не входят, но их
затронет любое изменение стора — они перечислены отдельно.

## Исходное состояние (измерено)

`bootstrap()` (`store.tsx:697`, повтор в `refreshIssues`, `store.tsx:1033`) вызывает
`listAllIssues` — последовательный обход всех страниц по 200. На стенде из
50 000 активных задач это **~250 запросов** (в сетевом инспекторе видно первые
100 записей + счётчик 212 в буфере resource-timing, который ограничен 250) и
десятки секунд занятого главного потока. Результат кладётся в `data.issues`, и
от него зависят все места ниже.

## Порядок и объём

Порядок — от простых точечных к сложным; **каждый потребитель — отдельный коммит
и своя проверка в браузере на стенде 50 000 задач**:

1. **Сервер (C1–C4)** + тесты и замер `EXPLAIN`. Один PR, без изменений клиента.
2. **Срез стора `issues-lookup`** (кэш «id → задача», счётчик ревизии, фасад
   `data.issues`), bootstrap **пока грузит всё** — чистый рефакторинг под тестами
   (B1–B4, B7, A16). Второй PR; это же часть Трека 2 (ТЗ 2.3).
3. **Агрегаты:** A1 (WorkflowView), A2 (Sidebar). Малый риск.
4. **Модалки:** A4→A5→A8→A6 (уже готов)→A10, затем пикеры A7/A9/A11 (общий
   компонент серверного поиска). Самая объёмная часть.
5. **Topbar (A3), Board/Backlog справочник направлений (A12, A13).**
6. **Timeline (A14).**
7. **Sprints (A15)** — обёртка; затем **удаление `listAllIssues` из `bootstrap`**
   и проверка: заход на Доску ≤ 3 запросов списка, модалка с подзадачами без
   предзагрузки, тесты зелёные, охранник миграций, PERF-04 — нет цепочки ~250.

Ожидаемо это **пять–семь PR**, а не один: пункты 1, 2, 4 и 6 — самостоятельные
и объёмные.
