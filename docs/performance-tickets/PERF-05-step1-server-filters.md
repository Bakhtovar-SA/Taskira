# PERF-05, шаг 1 — фильтры, сортировка и счётчики списка задач на сервере

Статус: серверная часть выполнена 20 сентября 2026 года. Клиент не менялся: он
по-прежнему грузит весь набор (`listAllIssues`) — ленивая загрузка это шаги 2–3.

## Основание

До этого шага фильтры, сортировка и поиск выполнялись на клиенте по уже
загруженному набору (`Backlog.tsx`, `Board.tsx`). Ленивая загрузка без переноса
этих операций на сервер молча ограничила бы их первыми 200 задачами. Поэтому
перенос — первый шаг, до правок загрузки.

## Что изменилось в контракте

- `IssueFilterQuery` (`contract.ts`) — общий набор фильтров страницы и счётчиков:
  `status`, `assignee` (uuid или `none`), `type`, `q`, `dueFrom`, `dueTo`,
  `overdue`, `archived`, новые `closed=hide|recent|older` + `closedDays` (14).
  «Свежая» закрытая задача — `done_at` не старше `closedDays`; задачи без
  `done_at` (закрытые до миграции 016) считаются свежими, как в прежнем окне доски.
- `IssueQuery` дополнен `sort=rank|priority|due|updated|key` и `dir=asc|desc`.
  Тай-брейк — `num` **в том же направлении, что `dir`**. Это отличие от прежнего
  клиента (там при `desc` номер шёл по возрастанию): единый направленный порядок
  позволяет одному индексу читаться вперёд и назад.
- Курсор v2 (`issueListCursor.ts`): `(sort, dir, значение, num)`, подписан HMAC
  отдельным контекстом. Курсор другой сортировки или направления — HTTP 400.
  Курсор `rank` (v1) не менялся; `offset` сохранён.
- Новый `GET /api/projects/:projectId/issues/counts` — `{total, byStatus}` по тем же
  фильтрам, только активные задачи. `JOIN workflow_statuses` подключается лишь
  для `overdue`/`closed`.
- Старое поле `issueCounts` в `GET …/workflow` не менялось (считает и архив,
  клиент его не читает); решать его судьбу — отдельная задача.

## Индексы (expand-миграции, `CREATE INDEX CONCURRENTLY`)

Три файла — по одному индексу на файл: `CONCURRENTLY` нельзя выполнять в
составе нескольких команд одного запроса.

| Миграция | Индекс |
|---|---|
| `20260920T1400_index_issues_sort_priority` | `(project_id, <priority>, num) WHERE archived_at IS NULL` |
| `20260920T1401_index_issues_sort_due` | `(project_id, <due>, num) WHERE archived_at IS NULL` |
| `20260920T1402_index_issues_sort_updated` | `(project_id, <updated>, num) WHERE archived_at IS NULL` |

Отличие от схемы «(project_id, поле, id)»: хвостом стоит `num`, а не `id`, — он
уникален в проекте и совпадает с `ORDER BY`. Для `key` отдельный индекс не нужен:
`ORDER BY i.num` использует существующий `issues_project_id_num_key`.
Выражения в индексах должны быть IMMUTABLE, поэтому `updated` берётся через
`AT TIME ZONE 'UTC'`. Выражения продублированы в `SORT_EXPR`
(`services/issueFilters.ts`); тест `индексы сортировок` падает, если они
разойдутся (проверено мутацией).

Ключевая деталь глубоких страниц: позиция курсора задаётся сравнением строк
`(ключ, num) > ($v, $n)`, а не `a > x OR (a = x AND b > y)`. Вторая форма не
становится условием индекса, и глубокая страница читала весь хвост
(74–136 мс для `updated`).

## `has_assignee` — фильтр «без исполнителя» (миграции 1410, 1411)

- `20260920T1410_issue_has_assignee` (транзакционная, expand): колонка
  `issues.has_assignee boolean NOT NULL DEFAULT false`, триггер
  `trg_issue_assignees_sync_flag` на `issue_assignees` (AFTER INSERT/DELETE) и
  идемпотентный backfill. Флаг ведёт триггер, а не код приложения: он верен для
  replace-списка в PATCH (DELETE+INSERT), каскада удаления, ручного SQL и будущих
  импортов. Логика приложения не менялась, кроме `assignee=none` →
  `i.has_assignee = false`.
- `20260920T1411_index_issues_unassigned` (`CONCURRENTLY`):
  `(project_id, status_id, rank) WHERE archived_at IS NULL AND has_assignee = false`.
- Стоимость: backfill на стенде (60 000 строк, 35 000 обновлённых) — 7,8 с в одной
  транзакции, плюс раздувание таблицы от 35 000 новых версий строк. На установке с
  миллионом задач запускать в окно обслуживания и сделать `VACUUM (ANALYZE) issues`
  после миграции; при необходимости — переписать backfill батчами (не делалось: на
  тестируемых размерах не нужно). Накладные расходы триггера на запись отдельно не
  измерялись; на 200 заменах исполнителя (400 операций) — 373 мс вместе с
  round-trip'ами.
- Тесты: флаг совпадает с `EXISTS` после PATCH, прямого SQL-INSERT/DELETE и
  повторного применения миграции после сброса флага; `assignee=none` и его счётчик
  согласованы.

## Замеры (стенд `taskira_perf`, PostgreSQL 18.6, 5 холостых + 10 замеров, медиана)

Топология после досева `scripts/performance-seed-topology.mjs`: PERF — 50 000
активных + 10 000 архивных, ещё 9 проектов (20 000 … 10 задач); распределения
priority/due/updated/done_at неравномерные; исполнители у ~70% задач, выборка
смещена степенью 3 (`perf_001` — 5 998 задач, 14 947 без исполнителя), у 15% второй
исполнитель.

Страница `limit=200`, любой проект и любая сортировка (PERF, PX01, PX05, PX09):
**0,8–3,7 мс**, план — Index Scan по соответствующему индексу.

| Сортировка PERF (первая страница) | Было (стенд до досева, без индексов) | Стало (после досева) |
|---|---:|---:|
| priority / due / updated | 83–99 мс | 3,7 / 3,1 / 2,8 мс |
| key | 82 мс | 2,5 мс |
| rank (для сравнения, PERF-01) | 14 мс | 3,4 мс |

Глубокие страницы (позиция 49 800, оба направления): 2,1–3,4 мс.
Прежние 14 мс для `rank` из PERF-01 — другой момент замера (стенд без досева и
с другим прогревом), сравнивать напрямую нельзя.

Фильтр по исполнителю (PERF, rank-страница): частый (5 998 строк) 7,8 мс,
редкий (82 строки) 3,6 мс, `assignee=none` 4,2 мс.

### Счётчики

| Набор | Время | План |
|---|---:|---|
| PX01 (20 000), PX03, PX05 | 3,4 / 1,3 / 0,9 мс | Index Only Scan `idx_issues_active` |
| PERF (50 000 из ~70 000 строк таблицы), `random_page_cost=4` | 19–24 мс | Seq Scan |
| PERF, `random_page_cost=1,1` | **6,9 мс** | Index Only Scan `idx_issues_active` |
| PERF, исполнитель `perf_001` (частый) | 22–27 мс | Seq Scan + hash join |
| PERF, редкий исполнитель | 1,2 мс | Index/Bitmap Scan |
| PERF, `assignee=none` до `has_assignee` | 33–53 мс (83 мс при `random_page_cost=1,1`) | Seq Scan + anti join |
| PERF, `assignee=none` после `has_assignee` | **8,9 мс**, после VACUUM **3,2 мс** | Bitmap → Index Only Scan `idx_issues_active_unassigned` |

Выводы:
- Второй индекс для счётчика не нужен: `idx_issues_active` (миграция 016)
  покрывает `GROUP BY status_id`; Seq Scan на самом большом проекте — следствие
  стоимости произвольного чтения по умолчанию (`random_page_cost=4`, рассчитано
  на HDD), а не отсутствия индекса. Для SSD рекомендуется `random_page_cost=1.1`
  (19 → 7 мс на большом проекте). В deploy-документации пока не отражено.
- Переписывание `EXISTS` на `JOIN` для счётчика по исполнителю выигрыша не дало.
- `assignee=none` был самым дорогим счётчиком (anti join по 50 000 задач) и, по
  логике продукта, частым («нераспределённые задачи»). Решено в этом же шаге
  денормализованным флагом — см. следующий раздел.
- Оценки шумные: на этой машине повторные замеры одного плана расходятся до 1,5–2×;
  заметная разница между вариантами — от ~2×.
- Не проверено: несколько параллельных клиентов (нагрузочный прогон — PERF-04).

## Проверки

`server/test/issueFilters.test.ts` (15 тестов): фильтр по исполнителю находит
задачу за пределами первой страницы; `assignee=none`; `closed=hide|recent|older`;
обход курсором для каждой сортировки в обе стороны без потерь и дублей; отказ на
курсоре чужой сортировки/направления; `counts` совпадает с `includeTotal` списка и
не учитывает архив; право `browse`; возможность использования индексов.

### Найденный и исправленный красный тест

В одном из полных прогонов упал `lifecycle > повреждённый курсор отклоняется`.
Причина воспроизведена: тест портил курсор заменой последнего символа на `A`/`B`, но
курсор — 41 байт = 55 символов base64url, и в хвосте 2 неиспользуемых бита.
Символы `Q,R,S,T` декодируются в те же байты, поэтому в ~1/16 случаев (когда
исходный последний символ в той же четвёрке, что `A`/`B`) курсор оставался
валидным и сервер отвечал 200. Найдено повтором 20 прогонов (упал №8).
Это дефект теста, унаследованный от PERF-01 (тот же приём в `issueListCursor.test.ts`),
а также слабость декодера. Исправлено: декодер отвергает неканоническую запись
(`bytes.toString("base64url") !== cursor`), тесты меняют биты внутри данных, а
регрессионный тест перебирает все 64 варианта последнего символа и требует, чтобы
допустим был ровно один (проверен мутацией: без канонической проверки падает).
