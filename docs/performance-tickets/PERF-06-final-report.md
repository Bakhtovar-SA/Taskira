# PERF-06 — итог: `bootstrap()` больше не грузит все задачи проекта

**Статус: закрыт.** Чек-лист инвентаря (`PERF-06-inventory.md`) сверен построчно: все потребители A1–A16 и группы B1–B7
переведены или осознанно приняты, реестр риска «нет в сторе ≠ не существует» закрыт, три мёртвых поля Data убраны.
Ниже — что подтверждено как, потому что «проверено» бывает разным.

## Результат

| | Было | Стало |
|---|---|---|
| Запросов при входе на доску | ~250 (последовательный обход страниц по 200) | 16 к API + WebSocket; три из них — списки колонок |
| Что грузит `bootstrap()` | все активные задачи проекта | ничего; наборы, точечные запросы по id, `ensureAllIssues` только для Sprints |
| Поиск в Topbar | локально по загруженным | сервер, топ-8; ≈ 10 мс сквозно в тёплом состоянии на одном origin |

## Что подтверждено и чем

**В браузере, итоговый режим (умолчание сменено, флага нет):** холодный старт доски (16 запросов, 300 карточек,
3 списка); `canDropTo` («Готово» — запрещено, «В работе» — разрешено) и реальный сброс карточки (GET → transition →
перечитывание, счётчики 1500→1499 и 36375→36376); открытие карточки из результата поиска Topbar при пустом сторе;
создание подзадачи с направлением, которого не было в кэше (в БД `epic_id` и `parent_id` верны); Workflow (счётчики
от сервера). Перетаскивание — событиями HTML5 DnD на элементах, не живой мышью (ограничение инструмента).

**В браузере, но с флагом «без предзагрузки» (репетиция до смены умолчания):** Список задач (100 строк), Таймлайн
(60 направлений, постраничное раскрытие). После удаления флага эти экраны заново не обходились: код тот же, но это
не «проверено в итоговом режиме».

**Только тестами (клиент 199, сервер 325 + 21 пропущен по env):** удаление задачи вне стора (`deleteIssue`,
мутационно), Sprints (модуль по умолчанию выключен; `ensureAllIssues`, скелет и подпись), модалка с эпиком и
родителем вне стора, `freshRows`, ревизии. **Не проверено вживую:** сценарий «удалённая карточка исчезает после
перечитывания» (изменение поведения задокументировано), CI-джобы (ни один не запускался отсюда).

## Находки, которых не было в ТЗ (по отдельности, не растворяя)

1. **Клиентская проверка прав тихо ослаблялась при промахе кэша** — сформулировано точно в
   `PERF-06-step2-store-slice.md`: не эксплуатируемая уязвимость (сервер повторно проверяет каждую мутацию), в
   проде дефекта не было (до ленивой загрузки промах был невозможен); исправлено подтягиванием задачи по id.
2. **Пул `pg` без обработчика `error`: обрыв простаивающего соединения ронял бы процесс.** Уровень MAINT-01, не тюнинг:
   «сервер упал ночью без причины». Исправлено вместе с `idleTimeoutMillis: 0` (`6009945`).
3. **Тесты молча удаляли триграммные индексы поиска** (`DROP SCHEMA CASCADE` тестовой схемы уносил общее для БД
   расширение). Воспроизведено дважды; тесты и скрипты снимков переведены на отдельные БД (TEST-01).
4. **Снимок обновления на границе новее триграммной миграции не загружался** — латентный дефект `create-db-snapshot`;
   CI был зелёным только потому, что нынешние снимки старше миграции.
5. **`Data.seq` — неверная подсказка номера в окне создания** с 2026-09-06 (вреда данным нет: ключ назначает сервер).
6. **`GET …/issues/assignees` — 65 мс и Seq Scan, единственный запрос, уходивший в секунды под нагрузкой** — кэш на процесс.
7. **Дубли писем, гонка сида при старте, джобы в каждом процессе, лимит входа по IP в памяти** — RESTART-SAFETY.
8. **Предупреждение в `/ready` о пропавших индексах поиска** (деградация без ошибки стала видна).

Гипотезы, которые не подтвердились и были исправлены по ходу: «BLOCKED в инспекторе — очередь браузера» (это
редактирование выдачи инструментом; журнал сервера показал все запросы), «`upgrade.sh` даёт два живых контейнера»
(нет, `compose down` предшествует `up`), «`test-concurrent-index-recovery` — тот же класс» (расширений не создаёт).
