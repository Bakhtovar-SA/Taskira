# SEC-FILE-01 — загрузка файлов: нет антивирусной проверки, содержимое сверяется не для всех типов, мягкий лимит вложений

**Статус: открыт.** **Severity: low** (было medium; понижено при пересмотре 2026-10-06, см. «Почему важно»). Найдено в SEC-ASVS-01 (самопроверка ASVS 5.0 L2, 2026-10-06; [docs/security/ASVS-L2.md](../security/ASVS-L2.md)).

- **Требования:** ASVS 5.0: V5.2.2, V5.4.3, V2.3.2 (дополнительная глава V5 — вне перечня тикета, но релевантна загрузке).
- **Факт:**
  - `checkUpload` (`services/fileGuard.ts:208-235`) — центральный барьер загрузки — **покрыт тестами маршрута** `server/test/access.attachments.test.ts`: блок-список (`.exe` → 400), исполняемая сигнатура под безобидным расширением (PE под `.jpg` → 400), несовпадение расширения и сигнатуры (PDF под `.png` → 400), нормализация типа (PNG → 201) — строки 53-93; `Content-Disposition: attachment` + `nosniff` + `octet-stream` для SVG — 186-199; 413 по размеру, 400 на пустой файл, 409 на превышение лимита вложений — 201-230. Первая редакция ошибочно утверждала обратное (поиск по `checkUpload`/`ATTACHMENT_REJECTED` в тестах пуст, потому что тесты проверяют статус и текст причины).
  - Автотестами **не покрыты** ветки guard: сигнатуры ELF/Mach-O, `#!` и `<?php`, SVG/XML с BOM, регистр расширения (`.EXE`), замыкающая точка (`a.exe.`), путь/CRLF/управляющие символы и зарезервированные имена Windows в `sanitizeFilename` (`fileGuard.ts:37-55`). Проба 2026-10-06 подтвердила их поведение вручную.
  - Содержимое сверяется с расширением только для форматов из `EXT_EXPECT` (`fileGuard.ts:135-153`); для `txt`, `csv`, `doc`, `xls` и неизвестных расширений действует только блок-список (`config.ts:300-302`), а не список ожидаемых расширений (V5.2.2 L2 требует проверки для всех файлов). В блок-списке нет `php`, `asp`, `jsp`, `html`; проверяется только последнее расширение (`shell.php.jpg` с настоящим JPEG принимается).
  - Антивирусной проверки и точки подключения внешнего сканера нет (V5.4.3); в `FILES_MIGRATION.md` ClamAV отнесён к Фазе 6.
  - Лимит вложений на задачу — мягкий: `count → insert` не атомарен (`services/attachments.ts:147-152`), две параллельные загрузки у потолка дают `maxPerIssue + 1`; сам лимит проверен тестом (409 на шестое вложение).
- **Почему важно:** загрузка файлов — главная поверхность атаки. Severity понижена до low, потому что базовые барьеры под тестами, файлы хранятся вне веб-корня и никогда не исполняются сервером (V5.3.1), отдаются только после проверки прав как `attachment` с `nosniff`, а активные типы — как `application/octet-stream`. Оставшееся — эшелонированная защита: заражённый документ без сканера дойдёт до рабочей станции, где его должен поймать антивирус клиента.
- **Что сделать:**
  1. Юнит-тесты `server/test/fileGuard.test.ts` на непокрытые ветки: ELF/Mach-O, `#!`, `<?php`, BOM-SVG/XML, `.EXE`, `a.exe.`, путь и CRLF в имени, `CON.txt`. Тесты маршрута на 400/413/409 и заголовки скачивания уже есть — не дублировать.
  2. Проверять все сегменты расширения по блок-списку (`a.php.jpg`) и добавить в него серверные скрипты (`php`, `phtml`, `asp`, `aspx`, `jsp`, `cgi`) либо явно записать в `FILES_MIGRATION.md` D3, что исполнение исключено отдачей `attachment` + `octet-stream`; для L2 — решить, нужен ли allowlist расширений (настраиваемый `ATTACH_ALLOW_EXT`, пустой = выключен).
  3. Хук `ATTACH_SCAN_COMMAND`/ICAP/clamd: файл не становится доступным, пока сканер не вернул «чисто»; режим «выключено» остаётся по умолчанию; поведение при отказе сканера (fail-closed/fail-open) — настройкой; описание в `STORAGE_SETUP.md`.
  4. Атомарный лимит вложений (advisory lock по задаче) либо оставить мягким и записать это в документ лимитов (SEC-DOC-01).
- **Критерий готовности:** тесты в CI; описание сканера и выбора поведения при его отказе; строки V5.2.2, V5.4.3, V2.3.2 пересмотрены.
- **Не сделано:** ничего из перечисленного.
