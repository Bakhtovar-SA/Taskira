# PROV-01: ТЗ 4.2 — provisioning новой инсталляции реализовано без нового скрипта

Дата: 22 сентября 2026 года. ТЗ 4.2 (план v2, Трек 4) просило скрипт, автоматизирующий
разворачивание новой инсталляции (создать БД, прогнать миграции, засеять админа и, с ТЗ 4.1,
строку `instance`), с тремя оговорками: сидировать `instance`, а не будущую `organizations`;
переиспользовать существующий миграционный раннер и seed-логику, не дублировать их; согласовать с
ТЗ 1.1 (`install.sh`) — provisioning должен быть шагом внутри установки из релизного артефакта, а
не отдельным путём.

## Диагностика: что уже делает `install.sh --start`

`scripts/release/install.sh --start` (ТЗ 1.1) проверяет контрольные суммы, загружает офлайн-образы,
валидирует `.env` и поднимает `docker compose up -d`. Это стартует контейнер `server`, чей
единственный вход — `server/src/index.ts`:

```
initConfig() → initPool() → migrate() → runStartupSeeds() → buildApp() → listen()
```

`migrate()` (`server/src/db.ts`) — тот самый миграционный раннер, применяющий `server/migrations/*.sql`
по порядку, идемпотентно (таблица `schema_migrations`). `runStartupSeeds()` (`server/src/seedStartup.ts`)
— та же seed-логика, что использует `npm run dev`/`npm run seed` локально: `seedAdmin()` →
`seedProject()` → `seedInstance()` (ТЗ 4.1), каждая — «проверить, что пусто, затем вставить», под
общим `taskira:seed` advisory-локом.

Другими словами: **провижининг новой инсталляции уже происходит на первом `install.sh --start`**,
тем же кодом, что использует локальная разработка — ничего не дублируется, потому что дублировать
нечего. Ручных шагов «создать БД / прогнать миграции / засеять админа», которые старое ТЗ 2/4
(предыдущий роадмап) предлагало обернуть в отдельный скрипт, в текущей архитектуре просто нет —
их устранил сам docker-compose + автостарт-сиды, ещё до этого ТЗ.

## Решение: не писать `provision-tenant.ts`/`.sh`

Отдельный provisioning-скрипт **не создаётся** — это не пропуск ТЗ, а результат диагностики: он
дублировал бы `migrate()` + `runStartupSeeds()`, которые и так выполняются на каждом старте сервера.
Ровно это и предупреждает сама формулировка ТЗ 4.2 («не дублировать»). Единственная работа,
оставшаяся после диагностики:

1. **Параметризация под конкретного клиента.** `INSTANCE_NAME`/`INSTANCE_PLAN` добавлены в
   `scripts/render-compose.sh` (→ `docker-compose.yml`), корневой `.env.example` и
   `server/.env.example` — тем же путём, что `ADMIN_NAME`/`ADMIN_USERNAME`/`PROJECT_KEY` уже шли.
   Оператор задаёт название инсталляции в `.env` перед первым `install.sh --start` — оно сеется
   в `instance.name` вместе с админом и проектом.
2. **Документация** (`scripts/release/README_INSTALL.md.in`, §3–4): явно сказано, что провижининг —
   это первый `install.sh --start`, не отдельная команда, и что повторный запуск безопасен.
3. **Тест идемпотентности** (ТЗ 4.2, явное требование проверки): `server/test/restartSafety.test.ts`,
   «повторный запуск на готовой инсталляции не дублирует админа/проект/instance» — последовательный
   (не конкурентный, в отличие от уже существовавшего теста двух одновременных стартов) повторный
   вызов `runStartupSeeds()`, сверяющий, что id всех трёх строк не меняются.

## Источники

- `scripts/release/install.sh`, `server/src/index.ts`, `server/src/seedStartup.ts` — фактическая
  цепочка провижининга.
- `server/test/restartSafety.test.ts` — идемпотентность (конкурентный и последовательный повтор).
- `docs/adr/0009-database-per-tenant.md` — почему `instance`, а не `organizations`.
- Старый роадмап (`TASKIRA_ROADMAP (1).md`, ТЗ 2/4) — исходная формулировка, от которой план v2
  явно отталкивается тремя правками (см. `TASKIRA_PLAN_V2.md`, ТЗ 4.2).
