# SEC-01 — запоздавшие ответы после logout воскрешают данные предыдущего пользователя в UI

**Статус: ИСПРАВЛЕНО (кроме остатков внизу). Уровень безопасности.** Подтверждён тестами 2026-09-21 на `main` @ `82453a7`
(шаг 6 ТЗ 2.3; поведение НЕ менялось рефакторингом, оно старше). Класс — как ослабление проверки прав из PERF-06:
защита не работает на границе перехода состояния.

## Что происходит

`logout()` (`src/store.tsx`) стирает данные (`setData(emptyData())`, `bootStatus = "unauthenticated"`), но **не отменяет
запросы, начатые до выхода**, и не увеличивает `switchSeqRef`. Поэтому:

1. **`switchProject`, ответивший после `logout`**, проходит проверку `seq !== switchSeqRef.current` как «актуальный»,
   выполняет `setData(next)` и `setBootStatus("ready")` — **UI снова показывает данные проекта** (пользователи,
   задачи-набор, workflow) уже после выхода. Тест: `store.bootNav.test.tsx` «НАХОДКА (SEC): switchProject, ответивший
   ПОСЛЕ logout, воскрешает данные».
2. **`bootstrap`, начатый до `logout` и завершившийся после**, делает то же: статус уходит из `unauthenticated`,
   `data.currentUserId` снова заполнен. Тест: «НАХОДКА (SEC): bootstrap, запущенный до logout…».
3. **`openIssue` после `logout`** (клик по устаревшему элементу): `pid()` пустая строка, запрос уходит с пустым id
   проекта, а guard «проект не сменился» сравнивает `"" === ""` и пропускает ответ — задача попадает в сброшенный стор.
   На реальном сервере такой запрос получил бы 401 (токен отозван), поэтому это слабее пп. 1–2, но защита не работает.

## Почему это важно

Корпоративный клиент часто запускается на общем/незаблокированном компьютере: человек нажимает «Выйти» и уходит, а
запрос, отправленный за долю секунды до этого (переключение проекта, загрузка при входе), завершается **после**
выхода. Следующий человек за тем же браузером может увидеть данные предыдущего пользователя на экране. Окно короткое
(время жизни запроса, обычно сотни миллисекунд, при плохой сети — секунды), но условие срабатывает без участия
атакующего. Токены на сервере отзываются (`POST /api/auth/logout`), так что дальнейшие запросы уже не пройдут; дело именно
в данных, уже находящихся в пути.

## Направление исправления (не реализовано, сначала — отдельным PR, не в рефакторинге)

- `logout()` должен «поколением» отсекать все запоздавшие ответы: увеличивать `switchSeqRef`, ввести такое же поколение
  сессии для `bootstrap`, и проверять его во всех `setData` после `await` (или общий «эпохальный» счётчик сессии).
- guard «проект не сменился» не должен пропускать пустой `currentProjectId` (`""` = нет сессии/проекта).
- Проверка: в тестах `store.bootNav.test.tsx` три теста «НАХОДКА»/«после logout» фиксируют **текущее** поведение — при
  исправлении их ожидания инвертируются (данные не возвращаются, `bootStatus` остаётся `unauthenticated`).

## Что НЕ сделано

Исправление; проверка других мест с `await` + `setData` без поколения (кандидаты: `refreshNotifications`,
`refreshCollaborations`, `refreshAssignedToMe`, `resolveIssue`, действия из `src/store/*` — многие защищены только
сравнением `currentProjectId`, которое после `logout` равно `""` у всех); реальное воспроизведение в браузере.

## Исправление (2026-09-21, отдельный PR сразу после переноса шага 6)

- `sessionEpochRef` в провайдере: растёт в `logout()` и при сбросе сессии по 401 (`handleApiError`). `bootstrap` запоминает
  эпоху и после каждого `await` (и в `catch`) выходит без записи, если она сменилась; `switchProject` сверяет эпоху
  вместе с `switchSeqRef`.
- `openIssue` и `resolveIssue` без проекта (`pid() === ""`, то есть нет сессии) ничего не запрашивают — guard `"" === ""` больше
  не пропускает ответ.
- Тесты `store.bootNav.test.tsx`: три теста «фиксирую баг» инвертированы (данные не возвращаются, `bootStatus` остаётся
  `unauthenticated`), добавлены: запоздавший `bootstrap` (ветки home и «один проект», и при ошибке), сброс сессии по 401,
  `lookupIssue` после выхода, новый вход сразу после выхода. Мутации: снять инкремент в `logout`, проверки в
  `bootstrap` (после home-запроса, после загрузки проекта, в `catch`), в `switchProject`, guard'ы `openIssue`/
  `resolveIssue`, инкремент по 401 — каждая проваливает свой тест. Проверки сразу после `authApi.me()` и после списка
  проектов оставлены как намеренно избыточные (глубокая защита): их снятие поведение не меняет, потому что следующие
  проверки цепочки ловят то же.

## Остатки (не сделано)

Записи в стор после `await`, защищённые только сравнением `currentProjectId`: `refreshNotifications`,
`refreshCollaborations`, `refreshAssignedToMe` пишут в уже сброшенный стор данные предыдущего пользователя (это не
воскрешает интерфейс — экран входа их не показывает, а следующий `bootstrap` заменяет `data` целиком, но в памяти они
до этого лежат); действия из `src/store/*` защищены сравнением `currentProjectId`, которое после выхода равно `""` у
всех, а права проверяются до запроса. Реальное воспроизведение в браузере не делалось.
