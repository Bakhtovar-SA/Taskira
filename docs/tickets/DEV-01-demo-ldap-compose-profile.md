# DEV-01 — демо-установка с тестовым LDAP одной командой

**Приоритет:** низкий, ничего не блокирует. **Статус:** открыт; отделён от CLEAN-01, потому что требует
машины с Docker для проверки.

## Зачем

CLEAN-01 п. 5: разработка и демо должны идти на тестовом LDAP с выдуманными людьми, а не на корпоративном AD.

## Что уже есть

- `server/docker-compose.ldap.yml` (`osixia/openldap`) и `server/test/ldap/bootstrap.ldif` («Тест Админ» и др.,
  домен `taskira.test`) — отдельный файл, в релизный архив не попадает (`scripts/build-release.sh` его не копирует).

## Чего нет и почему это отдельная задача

- Корневой `docker-compose.yml` **генерируется** `scripts/render-compose.sh` и разворачивается релизным
  инсталлятором; сервис `server` в нём не получает ни одной `LDAP_*`-переменной. Профиль `dev` со вторым сервисом
  недостаточен: серверу нужен `AUTH_MODE=ldap` и адрес LDAP, а прод-конфигурация не должна их получать.

## Что сделать

1. Профиль `dev-ldap` в генераторе: сервис `openldap` (`profiles: ["dev-ldap"]`), монтирование
   `server/test/ldap`, загрузка LDIF, healthcheck.
2. Отдельный оверрайд/переменные для `server` в этом профиле (`AUTH_MODE`, `LDAP_URL`, `LDAP_BIND_DN`, …).
3. Убедиться, что релизный дистрибутив по-прежнему не содержит профиль и тестовые LDIF
   (`scripts/test-release-scripts.sh`).
4. Документ: одна команда для демо и список выдуманных пользователей.

## Проверка

На машине с Docker: `docker compose --profile dev-ldap up`, вход под `t.manager`; `docker compose config` без
профиля не содержит LDAP-сервиса; релизный архив собирается и не содержит `test/ldap`.
**Нельзя закрыть без запуска Docker** — на машине разработки его нет.
