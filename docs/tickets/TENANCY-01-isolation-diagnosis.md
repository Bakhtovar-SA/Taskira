# TENANCY-01: как сегодня физически устроена изоляция данных

Дата диагностики: 22 сентября 2026 года. Предшествует ADR о database-per-tenant (Трек 4,
ТЗ 4.1 плана v2) и ему же служит источником фактов — сам ADR фактов не пересказывает, только
решение и его последствия.

Цель — ответить на один вопрос, поставленный перед ТЗ 4.1: физически в репозитории и в деплое
сейчас одна БД на инсталляцию, или общий инстанс с несколькими БД/схемами на клиента? Ответ ниже
получен чтением кода и конфигурации деплоя, не из документов, которые сами могут быть неточны
(см. находку о `CLAUDE.md` в конце).

## Итог

| Вопрос | Ответ | Основание |
|---|---|---|
| Есть ли в схеме таблица/колонка `organization_id`/`tenant_id`? | Нет, нигде | `grep -rn "organization\|tenant" server/migrations server/src ARCHITECTURE.md SCOPE.md README.md server/README.md` — ноль совпадений |
| Сколько БД на один процесс сервера? | Ровно одна | `config.ts:424-425` — один обязательный `DATABASE_URL`, без альтернативного механизма выбора БД по запросу |

## Multi-project (внутри инсталляции) — это не мультитенантность

`server/src/services/project.ts` резолвит проект по `:projectId` из роута (комментарий в файле:
«Multi-project (миграция 007) — проект берётся из :projectId роута, не «единственный»»).
Миграция `007_departments.sql` ввела `departments` + `projects.department_id` +
`projects.is_shared` именно для того, чтобы **несколько проектов одной организации** жили в одной
БД и были видны по департаменту/членству — это стоит между "один проект на инсталляцию" (чего уже
нет) и "несколько независимых организаций в одной БД" (чего никогда не было). Ни одна из ролевых
таблиц (`project_members`, `workflow_*`, `issues`, `project_counters`, `departments`) не несёт
`organization_id` — потому что делить в этой БД нечего: департаменты и проекты в ней по
определению принадлежат одной организации.

## Находка: `CLAUDE.md` устарел в этой самой точке

`CLAUDE.md:263` всё ещё пишет: `` project.ts` (`currentProject()`, cached — **single project, no
multi-tenant**) ``. Функции `currentProject()` в `project.ts` нет — она резолвится по `:projectId`
(см. выше), начиная с миграции 007. Формулировка «no multi-tenant» как факт о коде остаётся верной
(мультитенантности физически нет — см. таблицу выше), но «single project» неверна уже давно и,
судя по всему, не была обновлена после миграции 007/multi-project. Это ровно тот случай, который
`docs/adr/README.md` уже описывает по-другому: множественность проектов реализована, но нигде не
зафиксирована как решение — а *документ* про то, что проектов один, попросту не синхронизирован с
кодом. Строка требует правки отдельным маленьким PR (не входит в объём ТЗ 4.1) — записано, чтобы
не потерялось.

## Вывод для ТЗ 4.1

Физическая изоляция сегодня — «один процесс сервера = один `DATABASE_URL` = одна физическая база
Postgres = один деплой одним docker-compose стеком», без единого байта кода, различающего
организации внутри одной БД. Это уже, по факту, database-per-tenant **как побочный эффект того,
что мультитенантность никогда не проектировалась**, а не как спроектированное решение. Именно
поэтому нужен ADR, а не код в ТЗ 4.1 первым шагом: подтвердить эту физическую границу как
осознанный выбор и явно исключить будущий `organization_id`-в-одной-БД как альтернативу — это то
самое решение, которое `docs/adr/README.md` уже отметило как отсутствующее.
