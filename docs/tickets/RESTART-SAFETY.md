# RESTART-SAFETY — корректность при втором одновременно живом экземпляре

**Статус:** сделано (код `c317c13` + лимит входа по IP), проверено локально на стенде тестов; CI не запускался.
Выделено из инвентаря PERF-03 (`docs/performance-tickets/PERF-03-inventory.md`, пп. 6, 8, 9, 10): это не про
масштаб, а про то, что сервер не должен ломаться или вести себя иначе, если на той же БД оказался второй экземпляр.

## Уточнение мотива (предпосылка проверена по коду)

Изначально мотив звучал как «`upgrade.sh` при штатном апгрейде даёт секунду с двумя живыми контейнерами». **Это не
подтвердилось:** `scripts/upgrade.sh` делает `compose down` (ждёт остановки и удаления) до `compose up -d`, а
миграции идут одноразовым `compose run --rm --no-deps server node dist/migrate.js`, который приложение (уведомления,
сид, джобы) не запускает. Два живых экземпляра возможны в других случаях: staging или копия, смотрящие в ту же БД;
оркестратор с rolling-обновлением; забытый `NOTIFY_WORKER_ENABLED=false` при втором процессе (обходной путь из
комментария в коде держался на ручной настройке); в будущем — многопроцессность (PERF-03, отложена). Защита от
этого дешёвая и не зависит от PERF-03, но приоритет ниже, чем звучало.

## Что исправлено (каждое воспроизведено на прежнем коде)

| Проблема | Воспроизведение | Исправление |
|---|---|---|
| Письма дублировались: выборка `pending` без захвата строк | два одновременных тика → отправлено 2 письма вместо 1 | `runNotifierTick`: advisory-лок на тик (`withAdvisoryLock`, `wait:false`), проигравший пропускает тик |
| Фоновые джобы (архив+аудит, sweeper хранилища, LDAP-ресинк) шли в каждом процессе | по коду; LDAP-ресинк — N полных обходов каталога | `runJobLocked`: лидер на каждый джоб (`taskira:job:<имя>`) |
| Стартовый сид «проверить → вставить»: второй экземпляр падал | одновременный старт на пустой БД → `projects_key_key` (3 из 3 прогонов) | `runStartupSeeds` под блокирующим локом `taskira:seed` |
| Лимит попыток входа по IP — `Map` в памяти: лимит ×N и сброс при рестарте | по коду (состояние процесса) | таблица `login_attempts` (миграция `20260921T1000`, expand-only), проверка и запись в транзакции под advisory-локом на IP, время — `now()` БД |

Блокировка по **аккаунту** (`failed_login_attempts`, `locked_until`) уже была атомарной в БД — теперь и лимит по IP
устроен так же.

## Проверка

Тесты `test/restartSafety.test.ts` (6) и `test/loginRateLimit.test.ts` (5); мутационно: без лока падают тесты
уведомлений, джобов и сида, а при «всегда пропускать» — все тесты лимитера. Полный серверный набор: 325 из 325
(21 пропущен по env). Реального второго процесса и CI-прогона не было — только конкурентные вызовы в одном процессе
на общей БД.

## Остаётся как есть

- Окно «отправили письмо, упали до `UPDATE`» — повторная отправка при перезапуске (было задокументировано в §5
  уведомлений и не менялось).
- `@fastify/rate-limit` (общий лимит 600/окно) — по-прежнему в памяти процесса (PERF-03, п. 7).
- Остальное из инвентаря PERF-03 (WS-push, кэши свежести, пул, метрики) — не тронуто, отложено осознанно.
