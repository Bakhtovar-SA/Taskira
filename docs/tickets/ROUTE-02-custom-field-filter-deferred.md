# ROUTE-02 — фильтр по кастомному полю не входит в ТЗ 3.2 (сохранённые вьюхи)

**Статус: открыт, не блокирует остальную часть ТЗ 3.2.** Найдено при реализации ТЗ 3.2 (план v2
Трек 3), 2026-09-22.

- **Что сделано вместо этого:** `IssueFilterQuery`/`SavedViewFilter` (`server/src/contract.ts`) и
  `buildIssueFilter` (`server/src/services/issueFilters.ts`) получили `priority`/`label`/
  `sprintId` — те же условия конструктора, что и `status`/`assignee`/`type`, уже
  существовавшие. Фильтра по кастомному полю среди них нет.
- **Почему отдельно:** `custom_field_values` хранит всё как `text` независимо от типа поля
  (`text | number | select | checkbox | date`); парсинг/сравнение зависит от того, какое это
  поле (`validateValueForField` в `services/customFields.ts` — единственное место, которое уже
  знает, как читать значение конкретного типа). Фильтр `WHERE` по такому значению — не одна
  строка `i.custom_field_x = ?`, а JOIN на `custom_field_values` по конкретному `field_id` +
  сравнение, зависящее от типа (точное совпадение для text/select, диапазон для number/date,
  булево для checkbox) — материально более глубокая задача, чем priority/label/sprintId.
- **Не блокирует:** визуальный конструктор и сохранённые вьюхи работают без этого условия;
  `SavedViewFilter.strict()` явно отклоняет неизвестные поля, а не молча их теряет — так что
  добавление `customField` позже расширяет схему без миграции данных.
- **Проверка после реализации:** сохранённая вьюха с условием по кастомному полю `select`-типа
  фильтрует список задач; фильтр по `number`-полю поддерживает диапазон, не только точное
  совпадение; PATCH/DELETE самого поля (`custom-fields`) корректно ведёт себя, если на него
  ссылается сохранённая вьюха (значение по умолчанию — оставить условие как есть, оно просто
  перестанет что-либо находить, как и сейчас с уже удалённым статусом/меткой).
