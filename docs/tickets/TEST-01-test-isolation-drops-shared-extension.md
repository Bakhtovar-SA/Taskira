# TEST-01 — прогон тестов молча уничтожает объекты, общие для всей БД (pg_trgm и его индексы)

**Приоритет:** высокий. **Статус:** п. 1 (отдельная БД для тестов) реализован и проверен прогоном; п. 4 (индексы в readiness) реализован; скрипты со своими схемами (ниже) и перенос расширения суперпользователем — не сделаны.

## Что происходит

`server/test/global-setup.ts` перед каждым прогоном делает `DROP SCHEMA <схема тестов> CASCADE`. По
умолчанию схема тестов — `taskira_test` **внутри той же БД**, где живёт разработческая или иная схема
(`test/env.ts`: `…/taskira?options=-csearch_path=taskira_test,public`). Но `pg_trgm` — расширение
уровня **базы**, а не схемы: оно одно, и его схему определяет тот, кто создал его первым. Если первым
его создал прогон тестов (миграция `CREATE EXTENSION IF NOT EXISTS pg_trgm` без `SCHEMA` кладёт его в
первую схему `search_path`), расширение лежит в `taskira_test`. Следующий `DROP SCHEMA … CASCADE`
удаляет расширение, а вместе с ним — **каждый объект в любой схеме этой БД, зависящий от его класса
операторов**: триграммные индексы `idx_issues_active_{title,key}_trgm` (миграция `20260920T1420`).

Последствия молчаливые: ни ошибки, ни падения, миграция записана применённой и повторно индексы не
создаст; поиск по `q` продолжает работать, но деградирует до Seq Scan (78–158 мс на 93 тыс. задач вместо
0,06–3,4 мс).

## Воспроизведено (не только выведено по коду)

Стенд `taskira_perf` в той же БД. Расширение находилось в `taskira_test`; я пересоздал индексы стенда
и запустил `npx vitest run test/dbPool.test.ts` (любой прогон запускает `global-setup`). После него
индексов в `taskira_perf` нет, в БД остались только `taskira_test.idx_issues_active_*_trgm`
(созданные тем же прогоном заново). Это случилось дважды за трек.

## Насколько это касается прода — точно

- **Не срабатывает**, если расширение изначально создало приложение в рабочей схеме (порядок: сначала
  миграции прод-схемы, потом тесты): тогда оно живёт там, и удаление `taskira_test` его не трогает.
- **Срабатывает**, если на одной БД тесты когда-либо шли *раньше* миграций рабочей схемы, либо схему
  переносили/пересоздавали при существующем расширении в тестовой схеме. Для маленькой self-hosted
  установки с одной БД и запуском `npm test` «на месте» это реалистичный порядок, но требует запуска
  набора тестов на боевой БД — против этого есть защита `test/env.ts` (URL должен содержать
  `taskira_test`), которая, однако, не спасает случай «схема `taskira_test` в боевой БД».
- Отдельно: `test/searchIndex.test.ts` делает `DROP EXTENSION pg_trgm` внутри откатываемой транзакции;
  при живых зависимых индексах в другой схеме этот `DROP` (без `CASCADE`) упадёт. Набор проходил только
  потому, что индексы стенда к тому моменту уже были уничтожены.
- CI не затронут: там отдельная БД, схема `public`.

## Предлагаемое решение

1. **Рекомендуется — отдельная БД для тестов, не схема.** `test/global-setup.ts` подключается к
   служебной БД, создаёт `taskira_test` (`CREATE DATABASE`, если роли хватает `CREATEDB`), а `DROP` делает
   для **БД**, не для схемы. Тогда `pg_trgm`, `pgcrypto` и всё расширение-уровня принадлежит тестовой БД
   и не пересекается ни с рабочей схемой, ни со стендом. CI уже так работает; проверка `taskira_test` в
   `env.ts` остаётся. Если у роли нет `CREATEDB` — запасной путь, см. п. 2.
2. **Запасной путь и защита до перехода:** перед `DROP SCHEMA` в `global-setup` для каждого расширения,
   лежащего в удаляемой схеме, выполнять `ALTER EXTENSION … SET SCHEMA public` (`pg_trgm` переносимо),
   а если не вышло или есть зависимые объекты в других схемах — **падать с понятным сообщением**, а не
   удалять. Тест `searchIndex` с `DROP EXTENSION` в таком режиме нужно переделать на имитацию
   (проверка по плану, а не физический `DROP`), иначе он остаётся хрупким на общей БД.
3. **Не менять** миграцию `20260920T1420` (неизменяемая по `docs/MIGRATIONS.md`); принудительный
   `CREATE EXTENSION … SCHEMA public` в ней сломает установки без `CREATE` на `public` (PostgreSQL 15+).
4. **Обнаружение на любой установке (отдельно от фикса):** проверка здоровья, что индексы
   `idx_issues_active_*_trgm` существуют, если `pg_trgm` доступен, — чтобы молчаливая деградация
   становилась заметной. Кандидат в `GET /api/health` (`checks`) или в диагностический бандл.

## Реализация (п. 1) и что осталось

- `test/env.ts`: БД по умолчанию `taskira_test`; защита проверяет **имя БД** (не подстроку URL); `options`
  (search_path) в URL отвергается с объяснением. `test/global-setup.ts`: создаёт БД при отсутствии
  (нет права — понятная ошибка с командой), сбрасывает в ней схему `public`. Проверено: без права
  `CREATEDB` набор останавливается с сообщением и ничего в рабочей БД не трогает.
- **Не сделано:** `scripts/upgrade-snapshot-smoke.mjs`, `test-concurrent-index-recovery.mjs` и
  `create-db-snapshot.mjs` тоже создают свои схемы внутри рабочей БД и делают `DROP SCHEMA … CASCADE` —
  тот же класс риска, если такая схема первой создаст расширение. Их нужно перевести на отдельную БД так же.
- `test/searchIndex.test.ts` (`DROP EXTENSION` без `CASCADE`) в отдельной БД безопасен: зависимых индексов
  чужих схем там нет.
- **Проверено прогоном:** после выдачи `CREATEDB` полный серверный набор — 310 из 310 (21 пропущен по env),
  БД `taskira_test` создалась сама, триграммные индексы стенда до и после прогона на месте (2 и 2). Раньше
  один прогон их стирал.
- **Хвост на локальной машине:** старая схема `taskira_test` в рабочей БД `taskira` всё ещё владеет
  расширением `pg_trgm` (его когда-то создал прогон тестов). **Не удаляйте её:** это снесёт расширение и
  индексы стенда. Перенести расширение ролью `taskira` нельзя (`нужно быть владельцем функции set_limit`),
  это делает суперпользователь: `ALTER EXTENSION pg_trgm SET SCHEMA public;`, после чего схему можно
  удалить. Тесты её больше не используют.
