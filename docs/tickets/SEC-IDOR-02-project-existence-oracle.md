# SEC-IDOR-02 — по UUID проекта или задачи можно узнать, что они существуют

**Статус: открыт. Severity: низкая.** Найдено 2026-10-06 при SEC-IDOR-01 (матрица доступа по всем маршрутам).

- **Факт:** `requirePerm` / `requireIssuePerm` (`server/src/middleware.ts`) сначала ищут проект (и задачу) и только потом
  проверяют членство. Для постороннего: существующий проект отвечает 403, несуществующий 404; существующая задача
  существующего проекта 403, несуществующая 404. Правило «не раскрывать существование чужого ресурса»
  (`docs/SECURITY_OVERVIEW.md`, «Правило 404 / 403») здесь не выполняется.
- **Почему низкая:** идентификаторы UUIDv4 (122 бита), перебор нереален; id попадают только к тем, кто уже видел ресурс.
  Утечка возможна лишь если UUID известен из другого источника (письмо, лог, чужая ссылка), и даёт один бит:
  «такой объект есть».
- **Как исправить:** в `requirePerm` / `requireIssuePerm` отвечать 404 (то же тело, что у несуществующего), когда у
  вызывающего нет даже `browse` и он не приглашённый к задаче; 403 оставить, когда проект ему виден, а прав на действие
  не хватает. Клиент (`store.tsx`, `denialReason`) сейчас различает 403 и 404 в тостах: проверить тексты.
  Затронуты `server/test/access.*.test.ts` (ожидают 403 для постороннего), `accessMatrix.test.ts` (политики
  `projectMember`, `projectPrivileged`, `issueMember`, `issueOwnerOnly`: колонки outsider, collabOther, tokenOutOfScope)
  и тест «ИЗВЕСТНО: существование проекта и задачи по UUID различимо».
- **Не сделано:** изменение сознательно не вошло в SEC-IDOR-01: оно меняет контракт ответов на десятках маршрутов и
  существующие тесты, а риск низкий. Решение по срокам за владельцем.
