# SEARCH-01 — индекс для текстового поиска по задачам (`q`)

Статус: заведён 20 сентября 2026 года. Найден при замере серверного поиска для
пикеров (PERF-06). **Приоритет: средний — сделать до перевода поиска Topbar
(A3 в PERF-06) на сервер, потому что он вызывает этот же запрос на каждую паузу
в наборе.** Решение по расширению БД — за владельцем продукта, поэтому не
принималось молча.

## Проблема

Фильтр `q` в `GET …/issues` (`issueFilters.ts`) делает
`(i.title ILIKE '%…%' OR i.key ILIKE '%…%')`. Подстрочный `ILIKE` не может
использовать btree-индексы: план — Seq Scan по `issues` + top-N сортировка.
Стоимость растёт с размером **таблицы**, а не проекта, и особенно плоха, когда
совпадений нет (приходится просмотреть всё).

Замер на стенде (PostgreSQL 18.6, 60 000 строк `issues`, проект PERF — 50 000
активных; 5 холостых + 10 замеров, медиана):

| Ввод | Время | План |
|---|---:|---|
| `PERF-4999` (ключ) | 67 мс | Seq Scan + Sort |
| `issue 4999` (часть названия) | 61 мс | Seq Scan + Sort |
| Нет совпадений (`опечаткаа`) | 107–232 мс (шумно) | Seq Scan + Sort |
| Частый фрагмент (`a`, `issue 1`) | 1,5 мс | Index Scan по rank (набор быстро набирается) |

Пустой ввод (недавние по `updated`) — 1,4 мс: идёт по индексу PERF-05.

Влияет на: Список задач (уже использует `q`), пикеры связей/направления,
будущий поиск в Topbar. Замер PERF-05 («поиск из 10 символов — один запрос»)
проверял число запросов, но не задержку — это пробел, закрытый здесь.

## Проверенный вариант

`pg_trgm` + два частичных GIN-индекса (в транзакции с откатом, данные стенда не
менялись):

```sql
CREATE EXTENSION IF NOT EXISTS pg_trgm;
CREATE INDEX CONCURRENTLY idx_issues_active_title_trgm
    ON issues USING gin (title gin_trgm_ops) WHERE archived_at IS NULL;
CREATE INDEX CONCURRENTLY idx_issues_active_key_trgm
    ON issues USING gin (key gin_trgm_ops) WHERE archived_at IS NULL;
```

| Ввод | Без индекса | С триграммами | План |
|---|---:|---:|---|
| `PERF-4999` | 67 мс | **3,7 мс** | BitmapOr по двум GIN |
| `issue 4999` | 61 мс | **5,4 мс** | BitmapOr по двум GIN |
| Нет совпадений | 107–232 мс | **1,1 мс** | BitmapOr по двум GIN |
| Частые фрагменты | 1,5 мс | 1,5 мс | без изменений (rank-индекс) |

Создание двух индексов на 60 000 строк — 0,9 с (в проде — `CONCURRENTLY`, один
оператор на файл, по правилам охранника).

## Что нужно решить

1. **Расширение `pg_trgm`.** Оно есть в стандартной поставке PostgreSQL (`contrib`,
   образ `postgres:16-alpine` из `docker-compose.yml` его содержит) и помечено
   `trusted` (PostgreSQL ≥ 13): `CREATE EXTENSION` может выполнить владелец БД с
   правом `CREATE`, суперпользователь не нужен. Не проверено: managed-PostgreSQL
   и сборки без contrib у конкретного клиента — нужен вопрос в чек-лист
   развёртывания. Миграция `CREATE EXTENSION` в транзакционном файле допустима;
   индексы — отдельными нетранзакционными миграциями.
2. **Поведение без расширения.** Расширение — зависимость деплоя. Либо (а)
   миграция падает с понятным сообщением, если расширения нет, либо (б) миграция
   создаёт расширение «если возможно», а поиск остаётся работоспособным (как
   сейчас), только медленнее. Предпочтительнее (б): новая миграция не должна
   ломать установку клиента.
3. **Что не покрывает.** Слова короче трёх символов триграммы не индексируют
   (для них остаётся текущий план); поиск с опечатками/морфологией русского
   языка — отдельная задача (полнотекст), не эта.

## Критерии приёмки

- `EXPLAIN` на проекте из 50 000 задач для ключа, части названия и «нет
  совпадений» — BitmapOr по GIN, без Seq Scan по `issues`, время ≤ ~6 мс.
- Миграции проходят охранник (`check-migrations.sh`), индексы — `CONCURRENTLY`,
  один оператор на файл, с `-- recovery:`.
- Тест: результат поиска с индексом совпадает с результатом без него на
  фикстуре (регистр, спецсимволы `%` и `_` — `escLike`, кириллица).
- В `docs/OPERATIONS.md` и чек-листе развёртывания записано требование к
  расширению и что делать, если его нельзя установить.
