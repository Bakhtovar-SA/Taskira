# SEC-AUTH-02 — пути входа, блокировка аккаунта как DoS, имя администратора `admin` по умолчанию и привязка идентичности LDAP/локальный

**Статус: открыт.** **Severity: medium.** Найдено в SEC-ASVS-01 (самопроверка ASVS 5.0 L2, 2026-10-06; [docs/security/ASVS-L2.md](../security/ASVS-L2.md)).

- **Требования:** ASVS 5.0: V6.1.1, V6.1.3, V6.3.2, V6.3.4, V6.8.1.
- **Факт:**
  - Блокировка 5 ошибками/15 минут применима к любому известному логину (`routes/auth.ts:39-53`), включая break-glass администратора: злоумышленник с доступом к форме входа может держать его заблокированным. Защита от злонамеренной блокировки не описана (V6.1.1).
  - Имя первого администратора (он же break-glass в LDAP-режиме) по умолчанию — `admin`: `docker-compose.yml:31` (`${ADMIN_USERNAME:-admin}`, генерируется `scripts/render-compose.sh:61`), `.env.example:28`, `scripts/release/.env.example:10`, `server/.env.example:25`. `config.ts:485-492` принимает любое непустое имя, `seed.ts:26-29` создаёт учётку с `global_role='admin'`. Пароль по умолчанию отсутствует, но учётка с предсказуемым именем есть в каждой штатной установке и отключается только при наличии другого активного администратора (V6.3.2); вместе с первым пунктом это делает блокировку аварийного входа тривиальной.
  - Пути входа (пароль, LDAP, break-glass, `tsk_` Bearer, WS первым сообщением) описаны разрозненно, требуемая стойкость не нормирована (V6.1.3, V6.3.4).
  - Локальные и LDAP-пользователи делят пространство `username`; вход через LDAP «усыновляет» локальную учётку и затирает пароль (`services/userProvisioning.ts:84-103`), идентификатор источника в ключ не входит (V6.8.1). Break-glass исключён.
- **Почему важно:** доступность аварийного входа и однозначность идентичности — свойства, которые клиентский ИБ-отдел проверит.
- **Что сделать:**
  1. Блокировка по паре (аккаунт, IP/сеть) или экспоненциальная задержка вместо жёсткой блокировки; break-glass не блокировать целиком, а замедлять; описать в SECURITY_OVERVIEW.
  2. Убрать значение `admin` по умолчанию: `ADMIN_USERNAME` обязателен (`${ADMIN_USERNAME:?…}` в `render-compose.sh` → `docker-compose.yml`, пустое значение в `.env.example`, `scripts/release/.env.example`, `server/.env.example`); `config.ts` отказывает в запуске при общеизвестных именах (`admin`, `administrator`, `root`, `sa`, `taskira`) без явного `ADMIN_USERNAME_ALLOW_COMMON=true`; `install.sh` спрашивает имя или генерирует его. Для существующих установок — предупреждение в `/api/health` и инструкция переименования в OPERATIONS.md.
  3. Таблица «путь входа → фактор → ограничения → где реализовано» в SECURITY_OVERVIEW.
  4. Для усыновления — подтверждение администратором (флаг/список) или запрет по умолчанию, события в аудите (`auth.ldap.adopt`).
- **Критерий готовности:** тест: пять неверных паролей с чужого IP не блокируют вход владельца; тест конфигурации: запуск с `ADMIN_USERNAME=admin` без явного разрешения отклоняется, compose без `ADMIN_USERNAME` не рендерится; усыновление локальной учётки требует явного разрешения и пишет аудит; документ обновлён; строки V6.1.1, V6.1.3, V6.3.2, V6.3.4, V6.8.1 в ASVS-L2.md пересмотрены.
- **Не сделано:** ничего из перечисленного.
