# SEC-WEB-01 — кука без префикса `__Host-`, HSTS API 180 дней и дубли заголовков, нет проверки `Origin` для запросов без preflight

**Статус: открыт.** **Severity: low.** Найдено в SEC-ASVS-01 (самопроверка ASVS 5.0 L2, глава V3, добавлена при пересмотре 2026-10-06; [docs/security/ASVS-L2.md](../security/ASVS-L2.md)).

- **Требования:** ASVS 5.0: V3.3.1 (префикс), V3.3.3, V3.4.1 (HSTS API), V3.5.1, V3.5.2. Умолчание `Secure` для V3.3.1 — в [SEC-TLS-01](SEC-TLS-01-transport-security-defaults.md), `CORS_ORIGIN=*` (V3.4.2) — в [SEC-CFG-01](SEC-CFG-01-exposed-endpoints-ws-origin-trace.md), JWT в теле ответа входа (V3.3.4) — в [SEC-SESS-01](SEC-SESS-01-session-lifecycle-controls.md).
- **Факт:**
  - Сессионная кука называется `taskira_session` (`server/src/sessionCookie.ts:4`) — без префикса `__Host-`/`__Secure-`. Атрибуты host-only (`Path=/`, без `Domain`, `sessionCookie.ts:33`) уже соответствуют `__Host-`, кроме того, что `Secure` штатно выключен.
  - API (helmet) отдаёт `Strict-Transport-Security: max-age=15552000; includeSubDomains` — 180 дней при требуемом годе (`server/src/app.ts:99`; проба `buildApp()` 2026-10-06). Клиентский nginx ставит год (`nginx.conf:15`), но блоки `location` загрузок и `/api/` (`nginx.conf:36-61`) наследуют серверные `add_header`, поэтому ответы API через nginx несут по два `Strict-Transport-Security` и `Content-Security-Policy` и противоречивые `X-Frame-Options` (`SAMEORIGIN` от helmet, `DENY` от nginx). По RFC 6797 §8.1 браузер учитывает только первый HSTS. `scripts/test-security-headers.sh` проверяет только `/`.
  - На сервере нет ни анти-CSRF-токенов, ни проверки `Origin`/`Sec-Fetch-Site`. Межсайтовые запросы отсекает `SameSite=Strict`, JSON-маршруты — preflight. Без preflight проходят multipart-загрузки (вложения, аватар, фото проекта, логотип) и POST без тела (`/api/auth/logout`, `routes/onboarding.ts:64,71`, `routes/recurring.ts:53,62`). Для `SameSite` соседние поддомены того же регистрируемого домена (`*.corp.example`) — «тот же сайт»: страница на таком поддомене может отправить эти запросы с кукой пользователя.
  - Попутно: `POST` с `Content-Type: application/x-www-form-urlencoded` возвращает 500 `INTERNAL` вместо 415 — обработчик ошибок (`server/src/app.ts:157-172`) превращает любую ошибку, кроме `ApiHttpError`/zod/валидации, в 500 и теряет статус ошибки Fastify.
- **Почему важно:** каждое по отдельности — эшелонированная защита (атака через соседний поддомен требует контроля над ним), но эти пункты первыми находит сканер заголовков и аудитор V3; 500 на ошибку клиента засоряет журнал и мониторинг.
- **Что сделать:**
  1. Имя куки `__Host-taskira_session`, когда `Secure` включён; при `Secure=false` (HTTP-стенд) — прежнее имя. Переходный релиз читает обе куки и при ротации переписывает на новое имя; logout чистит обе. Зависит от умолчания `Secure` (SEC-TLS-01).
  2. helmet: `hsts.maxAge = 31536000` (или `hsts: false` на API и единый заголовок от nginx). nginx: в `location /api/` и в блоке загрузок не наследовать серверные `add_header` (свой набор или `proxy_hide_header` для дублирующихся), чтобы у ответа был один HSTS, одна CSP и один `X-Frame-Options`. `scripts/test-security-headers.sh` — дополнительно проверять `/api/health` на единственность заголовков.
  3. Хук `onRequest`: для небезопасных методов, аутентифицированных кукой (не Bearer), требовать `Origin` из `CORS_ORIGIN` или собственного origin либо `Sec-Fetch-Site: same-origin`; иначе 403 и запись в аудит. Не-браузерные клиенты используют Bearer и не затрагиваются.
  4. Обработчик ошибок: для ошибок Fastify с `statusCode` 4xx отдавать этот статус (415, 413, 400) в едином формате `{ error: { code, reason } }`.
- **Критерий готовности:** тесты: имя и атрибуты куки при `SESSION_COOKIE_SECURE=true`; `POST` с кукой и чужим `Origin` → 403, со своим → 2xx; multipart-загрузка с чужим `Origin` → 403; Bearer без `Origin` работает; `form-urlencoded` → 415; HSTS API ≥ 31536000; проверка заголовков через nginx на `/api/`. Строки V3.3.1, V3.3.3, V3.4.1, V3.5.1, V3.5.2 в ASVS-L2.md пересмотрены.
- **Не сделано:** ничего из перечисленного.
