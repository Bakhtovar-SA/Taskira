# SEC-PWD-02 — политика паролей расходится с ASVS 5.0 (составные правила, нет списков, усечение bcrypt)

**Статус: открыт.** **Severity: medium.** Найдено в SEC-ASVS-01 (самопроверка ASVS 5.0 L2, 2026-10-06; [docs/security/ASVS-L2.md](../security/ASVS-L2.md)).

- **Требования:** ASVS 5.0: V6.1.2, V6.2.4, V6.2.5, V6.2.8, V6.2.9, V6.2.11, V6.2.12.
- **Факт:**
  - `passwordPolicy.ts:24-26` требует три из четырёх групп символов — ASVS 5.0 (V6.2.5) прямо запрещает составные правила; правило закреплено тестом `passwordPolicy.test.ts:7-9` и описано в SECURITY_OVERVIEW.
  - Чёрный список — 8 значений (`passwordPolicy.ts:3-12`) вместо топ-3000 (V6.2.4); проверки по скомпрометированным паролям (V6.2.12) и списка контекстных слов (V6.1.2, V6.2.11) нет.
  - `bcryptjs` 2.4.3 учитывает только первые 72 байта пароля: проба `я`×40 совпадает с `я`×36+`x` (V6.2.8/V6.2.9). Максимум 128 символов разрешён, но значимо 72 байта.
- **Почему важно:** формальное несоответствие L1-требованию и тихое усечение длинных паролей, особенно кириллических фраз-паролей.
- **Что сделать:**
  1. Убрать требование групп символов, оставить длину ≥ 14 (или 12 — решение), запрет логина/имени организации/названия продукта.
  2. Поставлять список топ-3000+ (offline, в репозитории или артефакте релиза) и проверять против него; для V6.2.12 — offline-набор k-anonymity-диапазонов или документированное исключение для air-gapped установок.
  3. Перед bcrypt предхэшировать пароль (SHA-256 → base64) либо перейти на argon2id/scrypt с переносом хэшей при входе; либо ограничить длину честно (72 байта) и сказать об этом пользователю.
  4. Список контекстных слов (Taskira, Megafon, названия отделов) — в документацию и в проверку.
- **Критерий готовности:** тест: пароли `я`×40 и `я`×36+`x` не совпадают; `Aaaaaaaaaaaaaaaa1` и фраза из четырёх слов нижним регистром принимаются/отвергаются по списку, а не по группам; SECURITY_OVERVIEW обновлён.
- **Не сделано:** ничего из перечисленного.
