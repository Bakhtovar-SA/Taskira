## 1. Зачем

Интерфейс несёт наследие ранней Jira-подобной модели, от которой
[SCOPE.md](SCOPE.md) осознанно отказался: спринты и scrum-церемонии, «эпик» вместо
«направления», вход сразу в один проект (нелогично при нескольких отделах),
«Бэклог» как экран планирования спринтов. Плюс мелкие точки трения (кнопка «+» в
каждой колонке доски). Задача — привести UI к модели SCOPE **до** визуального
редизайна, чтобы дизайн делался уже по правильной структуре.

Пять изменений (из задания):

1. Убрать спринты полностью — таблица `sprints`, `issues.sprint_id`, роуты, право
   `manageSprints`, весь клиентский UI.
2. «Эпик» → «Направление» — везде в подписях и текстах. Поле `epicId` (и вся
   серверная модель группировки) **не меняется** — только отображение.
3. Создание задачи — только через кнопку «+ Создать» в шапке и «+» в первой
   колонке доски («К выполнению»); из остальных колонок «+» убрать.
4. Главный экран при входе (до выбора проекта): «Мои задачи» (назначенные мне по
   всем доступным проектам) + «Недавние проекты» (доступные отделы/проекты).
5. «Бэклог» → «Список задач»: плоский список задач с фильтрами, без секций
   спринтов.

## 3. Ключевые решения — НА ПОДТВЕРЖДЕНИИ

Каждое — рекомендация + отклонённые альтернативы. **Ничего не реализуется до
подтверждения.**

### D1. Спринты — полное удаление, включая право `manageSprints` и колонку `sprint_id`

**Рекомендация.**
- **Миграция `012_drop_sprints.sql`**: `ALTER TABLE issues DROP COLUMN sprint_id;`
  (снимает FK и `idx_issues_sprint`) → `DROP TABLE sprints;`. Бэкфилла нет.
  **Необратима** (данные спринтов и привязки задач теряются) — как `006` (drop
  `access_role`). Перед применением на БД с данными — снять дамп
  (`pg_dump -t sprints -a`), если планирование в спринтах кому-то важно для
  истории. На dev — только сид-спринт, потеря безболезненна.
- **Право `manageSprints` удаляется из `MATRIX` в обеих копиях `permissions.ts`**
  (не оставляем tombstone-ключ): `PermId`, `MATRIX`, `PERM_NAMES`,
  клиентский `PERMISSIONS`. Все вызовы (`roleHas(.., "manageSprints")`,
  `requirePerm("manageSprints")`, `can("manageSprints")`) снимаются в этой же
  фазе, одним коммитом.
- **Сервер:** удалить `routes/sprints.ts`, `services/sprints.ts`, регистрацию
  `sprintRoutes` в `app.ts`; из `routes/issues.ts` — ветку `sprintId` в
  `PATCH /:id`, весь `PATCH /:id/sprint`, `IssueQuery.sprint`, `sprint_id` в
  `INSERT` и `mapIssue`; из `routes/projects.ts` bootstrap — `sprints`; из
  `contract.ts` — `SPRINT_STATUSES`, `MoveToSprintBody`, `sprintId` в
  `IssueCreateBody`/`IssuePatchBody`, `sprint` в `IssueQuery`, вариант
  `sprint:changed` в `WsMessage`; из `services/issues.ts` — `sprint_id`/`sprintId`;
  из `seedProject.ts` — вставку спринта.
- **`audit_log`** — строки `entity='sprint'` и `action LIKE 'sprint%'` / `issue.sprint.move`
  **не трогаем** (исторический журнал, `entity`/`action` — свободный текст, FK нет).
- **Клиент:** удалить `Sprint` тип, `Data.sprints`, `Issue.sprintId`, `sprintsApi`,
  `issuesApi.setSprint`, экшены `setSprint`/`startSprint`/`completeSprint`,
  `sprintId` в `mapIssue`; из `Board.tsx` — фильтрацию по спринту и баннер
  (доска всегда показывает все задачи проекта); поле «Спринт» из `IssueModal` и
  `CreateIssueModal`. `Backlog.tsx` переписывается в Фазе 5.

**Обоснование.** SCOPE с самого начала помещает спринты в «не делаем»; держать
мёртвую таблицу, право и три роута — только запутывает. `manageSprints` не
относится к «замороженной матрице» в смысле [ROLE_MIGRATION.md §3.2](ROLE_MIGRATION.md)
(там про `editWorkflow`/`manageAccess`) — это удаление *возможности*, а не
переназначение прав; матрица меняется в обеих копиях одним коммитом, как
`manageCollaborators` добавлялся.

**Отклонено.**
- *Оставить `sprints` в БД, убрать только UI* — «зомби-схема», роуты и право
  остаются поверхностью; при следующем чтении кода снова вопрос «а это точно не
  используется».
- *Tombstone-ключ `manageSprints` в `MATRIX`* — компилируется, но `PermissionsView`
  показывает строку про несуществующую фичу; чистое удаление честнее.
- *Оставить `issues.sprint_id` «на всякий»* — nullable-колонка без смысла;
  `epic_id`/`color`/`t_start`/`t_span` остаются (D2), `sprint_id` — нет.

### D2. «Эпик» → «Направление» — только отображение

**Рекомендация.** Меняем строки в UI и текстах:
- `IssueModal.tsx`: `<Field label="Эпик">` → `«Направление»`; «Без эпика» → «Без
  направления».
- `CreateIssueModal.tsx`: подпись «Эпик» → «Направление», «Без эпика» → «Без
  направления».
- `Board.tsx` / `Backlog.tsx`: бейдж эпика — логика та же, подпись/`title` (если
  есть) → «направление».
- `TimelineView.tsx`: «Дорожная карта эпиков…» → «…направлений», «Эпиков пока
  нет» → «Направлений пока нет», подсказки, колонка «Эпик» → «Направление».
- `DocsView.tsx`: заменить «эпик»/«эпики» на «направление»/«направления» в
  тексте; заодно убрать абзацы про спринты (они устаревают Фазой 1). Полный
  переписывание `DocsView` (там ещё упоминания localStorage и «Сбросить
  демо-данные») — **вне захода**, отдельный пункт.
- Внутренние идентификаторы **не трогаем**: `Issue.epicId`, `epic_id`,
  `IssueCreateBody.epicId`, `getIssueDto.epicId`, `ViewId` `timeline`,
  комментарии в коде («тип epic упразднён…») можно оставить как есть.

**Обоснование.** SCOPE прямо: «Epic / эпик → Направление». Поле остаётся тем же —
меняется только слово, которое видит пользователь. Переименовывать `epicId` в
коде — лишний диф без пользы (и рискованно: поле в контракте API).

**Отклонено.** Переименование `epicId` → `directionId` в типах/контракте —
ломающее изменение API ради косметики; отложено (если вообще нужно).

### D3. Создание задачи — «+ Создать» в шапке + «+» только в первой колонке доски

**Рекомендация.** В `Board.tsx` кнопку «+» (инлайн `<QuickCreate>`) оставляем
**только у первого столбца с `category === 'todo'`** (по `position`); у остальных
столбцов кнопку убираем. Кнопка «+ Создать» в топбаре (`<CreateIssueModal>`) —
без изменений. `<QuickCreate>` создаёт задачу сразу в статусе своего столбца — для
первого `todo`-столбца это ожидаемо («К выполнению»).

**Обоснование.** Быстрое создание нужно только «в начало потока»; «+» в колонках
«В работе»/«На ревью»/«Готово» провоцирует создавать задачу сразу в неестественном
статусе. Общая кнопка в шапке остаётся для случаев «создать и заполнить поля».

**Отклонено.**
- *Убрать «+» из всех колонок, оставить только шапку* — теряется удобный
  quick-add в основном сценарии (накидать задач в «К выполнению»).
- *Оставить «+» во всех `todo`-столбцах* — дефолтный workflow имеет один `todo`,
  но кастомный может иметь несколько; правило «первый по позиции» однозначно.

### D4. Главный экран при входе — «Мои задачи» + «Недавние проекты»

**Рекомендация.**
- **Сервер:** новый `GET /api/issues/assigned-to-me` (project-less, на уровне
  `/api`, `requireAuth` — как `/api/issues/collaborating`): открытые задачи
  (`ws.category <> 'done'`), где `assignee_id = me`, по всем проектам, которые
  пользователь может `browse` (участник ∪ департамент ∪ `is_shared` ∪ глоб.
  admin — тот же предикат, что `listVisibleProjects`). Ответ:
  `{ issueId, projectId, key, title, statusName, statusCategory, priorityId,
  projectKey, projectName }`. Сортировка — по приоритету, затем `updated_at`.
- **Клиент:**
  - `bootStatus` += `"home"` (или переиспользуем `"ready"` + `ui.view="home"` без
    загруженного проекта — решить при реализации; чище отдельный статус).
  - `bootstrap()`: при **≥ 2 доступных проектах** — грузим список проектов +
    `assigned-to-me` + уведомления, ставим `bootStatus="home"`, **в проект не
    входим**. При **ровно 1 проекте** — как сейчас (сразу в него, главный экран
    бессмыслен). При 0 — как сейчас (solo / пустой экран).
  - `<HomeView>` *(новый)*: шапка (лого, колокол, меню пользователя — переиспользовать
    из топбара), два блока:
    - **«Мои задачи»** — список из `assigned-to-me`, строка = ключ · проект ·
      заголовок · статус · приоритет; клик → войти в проект и открыть задачу
      (`switchProject(projectId)` затем `#/issue/<pid>/<iid>` через существующий
      hash-механизм).
    - **«Недавние проекты»** — проекты, сгруппированные по департаменту
      (`data.departments` + `projects`), последний открытый (`readLastProject`) —
      первым, помечен «продолжить». Клик по проекту → `switchProject` → обычная
      оболочка.
  - Вернуться на главный экран из проекта: хлебная крошка «Проекты» в топбаре
    делается кликабельной → `bootStatus="home"` (проект выгружать не обязательно —
    просто показать `<HomeView>` поверх; уточнить).
- `writeLastProject` вызывается при входе в проект (уже так); главный экран его
  читает для «продолжить».

**Обоснование.** При нескольких отделах/проектах «кинуть сразу в один» —
дезориентирует. «Мои задачи по всем проектам» — самый частый вход («что мне
делать?»). Эндпоинт по образцу уже существующего `/issues/collaborating` —
project-less, дёшево.

**Отклонено.**
- *Всегда показывать главный экран, даже при 1 проекте* — лишний клик, когда
  выбора нет.
- *Считать «мои задачи» на клиенте из уже загруженного проекта* — покрывает
  только текущий проект, а смысл экрана — кросс-проектный обзор.
- *Полноценный дашборд с виджетами/графиками* — вне захода (и вне «без
  визуального редизайна»); MVP — два списка.

### D5. «Бэклог» → «Список задач» — плоский список с фильтрами

**Рекомендация.**
- `Sidebar.tsx`: пункт `backlog` → label «Список задач» (id `backlog` и `kbd:"2"`
  оставляем внутренними, чтобы не трогать `ViewId`/`App.tsx`/маршрутизацию хэша —
  минимальный диф; переименование id в `list` — опционально, отдельно).
- `Backlog.tsx` переписывается: секции спринтов, drag между секциями, кнопки
  «Начать/Завершить спринт» — **удалить**. Остаётся **плоский список** всех
  `data.issues` (без сортировки по спринту) + панель фильтров:
  статус (по `data.workflow.statuses`), исполнитель (`data.users`), тип

## 5. Риски и внимание

- **Миграция 012 необратима** — удаляет `sprints` + `issues.sprint_id`. На БД с
  реальным планированием — снять дамп до применения; в README-чек-лист явный
  пункт. Историю в `audit_log` не трогаем.
- **`MATRIX` меняется в ОБЕИХ копиях `permissions.ts` одним коммитом** (правило
  CLAUDE.md). Удаление ключа `manageSprints` — все вызовы (`roleHas`/`requirePerm`/
  `can`/`PERM_NAMES`/`PERMISSIONS`) снять синхронно, иначе не компилируется.
- **`PermissionsView`** (матрица прав на клиенте) — после удаления строка
  «Управление спринтами» исчезает; проверить, что таблица рендерится (тотальность
  `permMeta()`).
- **`Backlog.tsx`** — если Фазу 1 влить без Фазы 5, экран временно сломан
  (`data.sprints` нет). Делать Ф5 сразу за Ф1 в одной ветке, не мержить
  промежуточно.
- **Хэш-навигация к задаче** (`#/issue/<pid>/<iid>`) — главный экран и «Мои
  задачи» переиспользуют существующий механизм (`readIssueHash` + эффект в
  `store.tsx`); проверить кросс-проектный переход (`switchProject` затем открыть).
- **`bootstrap()` — горячий путь входа.** Добавление ветки «home» не должно
  ломать: 1 проект (сразу внутрь), 0 проектов (solo / пусто), прямую ссылку
  `#/issue/...` (должна вести в нужный проект, минуя/через home).
- **`assigned-to-me`** — предикат видимости проекта обязан совпасть с
  `listVisibleProjects` (участник ∪ департамент ∪ `is_shared` ∪ admin), иначе
  экран покажет задачи из проектов, которые пользователь потом не сможет открыть.
- **Клиентский CI (Фаза 0)** — после включения `client`-job красный клиентский
  `tsc` начнёт блокировать мерж; убедиться, что `main` сейчас зелёный (по
  аудиту — да, 0 ошибок).
- **`WsMessage.sprint:changed`** — тип не используется (Этап 3c), но удалить
  аккуратно (единый `WsMessage` union).
- **Скриншоты** делаются на dev-данных; на чистой БД (1 сид-проект) главный
  экран не покажется (правило «≥2 проекта») — для скриншота Фазы 4 завести
  второй проект/отдел временно.
