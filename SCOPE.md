# SCOPE — Taskira

Внутренний корпоративный трекер задач для компании с несколькими отделами/департаментами.
Аутентификация через LDAP/AD. Работает на собственном сервере (on-prem).

Цель: гибкий и удобный инструмент уровня Jira, но **без узкоспециализированного сленга
разработчиков** — им должны одинаково комфортно пользоваться ИБ, HR, бухгалтерия,
разработка и любой другой отдел.

> Решения, стоящие за этим документом, фиксируются на дату в [docs/adr/](docs/adr/README.md) (спринты — ADR-0002/0003,
> сложность вместо story points — ADR-0004, «Направление» как обычная задача — ADR-0006, роли в проекте — ADR-0005).
> Документ описывает намерение и границы продукта; актуальное состояние — код и порождаемые из него документы.

## Терминология (без жаргона)

| Не используем (Jira-сленг) | Используем вместо | Статус в UI |
|---|---|---|
| Epic / эпик | Направление | ✅ подписи (поле `epicId` в API оставлено) |
| Sprint / спринт | Спринт | ⚠️ по умолчанию по-прежнему не используется (удалено миграцией 012 из базового workflow); вернулось как **опциональный, выключенный по умолчанию модуль** — миграция 023, [SPRINTS_MIGRATION.md](SPRINTS_MIGRATION.md) |
| Story points | Сложность (простая / средняя / сложная) | ✅ поле `complexity`, редактируется в карточке (миграция 018); модуль спринтов (выше) её не заменяет |
| Backlog | Список задач | ✅ плоский список + фильтры + сортировка |
| Board | Доска | ✅ |
| Issue | Задача | ✅ |
| JQL | — (не используется, обычные фильтры в UI) | ✅ |

Реструктуризация UI под эту терминологию — [UI_RESTRUCTURE.md](UI_RESTRUCTURE.md)
(спринты, «Направление», «Список задач», главный экран, точки создания задачи).

## Иерархия доступа

Организация → Департамент (отдел) → Проект(ы) отдела → Задачи

- Департамент соответствует группе в LDAP/AD.
- У департамента может быть один или несколько проектов.
- Проект по умолчанию виден только участникам своего департамента.
- Отдельно поддерживаются "общие" (кросс-департаментные) проекты — для задач,
  где участвует несколько отделов (например, ИБ + IT + юридический).

## Роли и права (по проекту, не глобально)

Роль пользователя назначается **в рамках конкретного проекта**, а не на всё приложение —
один и тот же человек может быть менеджером в своём проекте и наблюдателем в чужом,
если ему открыли доступ.

| Роль | Что может |
|---|---|
| Администратор | Всё: настройка проектов, отделов, статусов, прав |
| Менеджер проекта | Создание/редактирование/удаление задач своего проекта, управление составом |
| Исполнитель | Создание задач, смена статусов, комментарии; редактирует только свои задачи |
| Наблюдатель | Только просмотр |

## В рамках MVP (входит)

- Департаменты и проекты (иерархия доступа выше)
- Задачи: название, описание, статус, исполнитель, автор, приоритет, сложность, метки, комментарии, история изменений
- Доска (канбан) по статусам, drag&drop
- Список задач (без временных итераций/спринтов) — плоский список с фильтрами
- Направления — опциональная группировка связанных задач (замена эпиков, без жёсткой иерархии)
- Связи между задачами: «связана с» (симметрично), «блокирует» / «заблокирована» (направленно)
- Настраиваемые статусы и переходы между ними (админ)
- Ролевая система доступа, привязанная к проекту
- Аутентификация через LDAP/AD, синхронизация членства в департаменте по группе AD
- Уведомления (в приложении + email) о назначении задачи, смене статуса, упоминании
- Вложения к задачам (файлы)
- Глобальный поиск и фильтры (без JQL — обычные выпадающие фильтры)

## Опциональные модули (не часть базового MVP)

- **Спринты** — точечное, осознанное исключение из строки ниже: бэклог +
  жизненный цикл спринта (future/active/completed, перенос незакрытых задач
  в бэклог при завершении), включается per-project флагом
  `project.sprintsEnabled` (по умолчанию выключен). Причина исключения —
  новая бизнес-цель (продаваемый Agile-модуль для отдельных проектов),
  которой не было на момент решения ниже удалить спринты целиком (миграция
  012). Для всех проектов без этого флага ничего не изменилось. Подробности
  и что **не** сделано (burndown/velocity, Scrum-церемонии, встраивание в
  общий workflow) — [SPRINTS_MIGRATION.md](SPRINTS_MIGRATION.md).

## Осознанно откладываем / не делаем

- Scrum-церемонии (стендапы, ретро, планирование в реальном времени),
  burndown/velocity-чарты — даже для проектов с включённым модулем спринтов
  (выше): у них есть бэклог и жизненный цикл спринта, но не полноценный
  Agile-профиль
- Оценка в story points (Fibonacci и т.п.) — задачи по-прежнему оцениваются
  «Сложностью» (simple/medium/hard), не в очках
- JQL и любой язык запросов
- Конструктор автоматизации с условиями ("если поле = X, то сделать Y") — вместо этого
  простая валидация переходов статусов (уже реализована в текущем коде)
- Тайм-трекинг, биллинг, отчётность по трудозатратам
- Множественные workflow-схемы на проект (пока одна схема статусов на проект достаточно)

## Открытые вопросы (требуют решения перед разработкой)

- ~~Как именно мапить группы LDAP/AD на департаменты~~ — решено: явно, DN одной
  группы на департамент (`departments.ldap_group_dn`), см. LDAP_MIGRATION.md D5.
- Нужны ли кросс-департаментные проекты в MVP или это следующая итерация
- ~~Формат уведомлений: только в приложении, или обязательно email~~ — решено:
  in-app всегда, email опционально за `NOTIFY_EMAIL_ENABLED` + корп. SMTP; письмо
  несёт только ссылку, без содержимого задач. См. NOTIFICATIONS_MIGRATION.md D1/D9.
