# Taskira — корпоративный трекер задач

Внутренний трекер задач для компании с несколькими отделами: канбан-доска с drag&drop,
плоский список задач с фильтрами, таймлайн направлений, настраиваемый workflow,
вложения, уведомления и **ролевая модель прав, привязанная к проекту**.

Две независимые npm-сборки:

- **корень** (`src/`) — SPA на React 18 + TypeScript + Vite + Tailwind CSS 4. Весь UI — на русском.
- **`server/`** (`server/src/`) — API на Fastify 5 + PostgreSQL + JWT. **Здесь источник истины по правам.**

Данные хранятся в PostgreSQL на сервере; в браузере — только токен сессии
(`taskira.token`) и выбор оформления (`taskira.theme` / `taskira.bg`).
Клиент общается с сервером исключительно через `src/api/` + `src/store.tsx`.

## Запуск

Клиент (из корня):

```bash
npm install
npm run dev        # Vite на http://localhost:3000 (strictPort)
npm run build      # прод-сборка в dist/
npm run typecheck  # tsc --noEmit — единственная проверка клиента
```

Сервер (из `server/`):

```bash
cd server
npm install
cp .env.example .env      # заполнить DATABASE_URL, JWT_SECRET (≥32 симв.), ADMIN_USERNAME/ADMIN_PASSWORD
npm run dev               # tsx watch → миграции → seed админа и проекта → :8080
npm test                  # vitest — интеграционные тесты прав/контракта (~90)
```

Нужен доступный локально PostgreSQL (`DATABASE_URL`): миграции и seed выполняются
до `listen`. Подробности API и модели данных — [`server/README.md`](server/README.md).

## Разделы приложения

| Раздел | Что умеет |
| --- | --- |
| **Доска** | Колонки = статусы workflow; drag&drop с валидацией переходов и прав; быстрое создание в первой `todo`-колонке; фильтры по исполнителю, тексту и быстрые чипы (мои / просроченные / без исполнителя); цветная полоса приоритета/направления на карточке |
| **Список задач** | Плоский перечень всех задач проекта; фильтры (статус, исполнитель, тип, текст, просроченные) и сортировка; без спринтов и итераций |
| **Таймлайн** | Направления на недельной шкале, прогресс закрытия, линия «сегодня» |
| **Рабочий процесс** | SVG-граф статусов и переходов; добавление/удаление переходов и сброс схемы (только администратор); изменения сразу действуют на доске |
| **Права доступа** | Матрица «роль × право» и управление составом проекта |
| **Департаменты** | CRUD отделов и проектов, привязка отдела к группе LDAP, флаг «общий проект» (только глобальный админ) |
| **Мои подключения** | Задачи, к которым пользователь приглашён точечно, без доступа к проекту целиком |
| **Документация** | Встроенный справочник: роли, workflow, модель данных, горячие клавиши |
| **Главный экран** | При входе с ≥ 2 доступными проектами — «Мои задачи», список проектов по отделам и недавняя активность |
| **Карточка задачи** | Inline-редактирование названия и описания; статус, исполнитель, приоритет, направление, срок, метки; связанные задачи, вложения, комментарии, история изменений |

## Права доступа

Двухуровневая модель (как Permission Schemes в Jira):

1. **Ролевой уровень** — матрица `MATRIX` (`src/permissions.ts` ↔ `server/src/permissions.ts`,
   зеркальные копии) задаёт, каким ролям доступно каждое разрешение.
2. **Уровень задачи** — для роли `employee` право `edit` сужается: редактировать можно
   только задачи, где он **исполнитель** или **автор**.

Роль назначается **в рамках проекта**, а не глобально: эффективная роль =
`resolveRole(globalRole, projectRole)` — глобальный `admin` → `admin`, иначе роль
участника проекта (`project_members.role`), иначе доступа к проекту нет.

| Роль | Что может |
| --- | --- |
| **Администратор** | Всё: отделы, проекты, схема workflow, права, удаление задач |
| **Менеджер проекта** | Создание/редактирование/удаление задач проекта, управление составом |
| **Сотрудник** | Создание задач, смена статусов, комментарии; редактирует только свои задачи |
| **Наблюдатель** | Только просмотр |

| Разрешение | admin | manager | employee | viewer |
| --- | :-: | :-: | :-: | :-: |
| Просмотр проекта (`browse`) | ✓ | ✓ | ✓ | ✓ |
| Создание задач (`create`) | ✓ | ✓ | ✓ | — |
| Редактирование (`edit`) | ✓ | ✓ | ✓\* | — |
| Смена статуса (`transition`) | ✓ | ✓ | ✓ | — |
| Комментарии (`comment`) | ✓ | ✓ | ✓ | — |
| Удаление задач (`delete`) | ✓ | ✓ | — | — |
| Приглашённые к задаче (`manageCollaborators`) | ✓ | ✓ | — | — |
| Схема workflow (`editWorkflow`) | ✓ | — | — | — |
| Пользователи и роли (`manageAccess`) | ✓ | — | — | — |

\* — только задачи, где сотрудник является исполнителем или автором.

**Где проверяется:** клиент (`store.tsx` → `requirePerm()`, `can()`) — для мгновенной
обратной связи (скрытые кнопки, замки на полях, тост с причиной отказа); сервер
(`middleware.ts` → `requirePerm` / `requireIssuePerm`) — на каждом запросе, авторитетно.

## Workflow

Ориентированный граф статусов в БД (`workflow_statuses` + `workflow_transitions`),
одна схема на проект. Дефолт:

```
К выполнению ─► В работе ─► На ревью ─► Готово
     │            ▲ │  ▲       │ ▲          │
     └────────────┘ └──┴───────┘ └── (переоткрытие) ─┘
     └──────────────────────────────────────► Готово
```

Смена статуса любым способом (drag на доске, меню в карточке) сверяется со схемой:
`POST …/issues/:id/transition` вне графа возвращает `409`. Даже администратор не
перетащит задачу против схемы — граф и права проверяются независимо.

## Аутентификация

- `AUTH_MODE=local` (по умолчанию) — вход по логину и паролю (bcrypt).
- `AUTH_MODE=ldap` — вход против LDAP/AD (сервис-bind → поиск → re-bind),
  JIT-провижининг пользователя, членство в отделе по `departments.ldap_group_dn`,
  break-glass локальный админ. См. [`LDAP_MIGRATION.md`](LDAP_MIGRATION.md) /
  [`LDAP_SETUP.md`](LDAP_SETUP.md).

JWT re-валидируется на сервере: `requireAuth` каждые ≤30 с перечитывает
`global_role` / `is_active` из БД, поэтому смена роли и деактивация действуют
без перевыпуска токена.

За reverse-proxy (nginx) задайте `TRUST_PROXY` — иначе `req.ip` будет адресом
прокси, что ломает rate-limit логина по IP и IP в audit-логе.

## Вложения, уведомления, связи

- **Вложения** — файлы на карточке задачи; guard по расширению и magic-байтам
  (исполняемые запрещены), хранилище за абстракцией `Storage`:
  `STORAGE_DRIVER=local` (диск) | `s3` (S3-совместимое). См.
  [`FILES_MIGRATION.md`](FILES_MIGRATION.md) / [`STORAGE_SETUP.md`](STORAGE_SETUP.md).
- **Уведомления** — in-app-лента (колокол, polling) на событие: назначение,
  комментарий по подписке, `@`-упоминание, смена статуса, подключение к задаче,
  добавление в проект. Email — опционально (`NOTIFY_EMAIL_ENABLED` + `SMTP_*`)
  фоновым воркером; в письме **только тип события, ключ задачи и ссылка**, без
  содержимого. См. [`NOTIFICATIONS_MIGRATION.md`](NOTIFICATIONS_MIGRATION.md) /
  [`NOTIFICATIONS_SETUP.md`](NOTIFICATIONS_SETUP.md).
- **Связи задач** — `relates` (симметрично) или `blocks` / `blocked_by`
  (направленно), в пределах одного проекта.

## Модель данных (клиент — `src/types.ts`)

- **Project** `{key, name, description, departmentId, isShared}` — под отделом.
- **Department** `{id, name, ldapGroupDn}` — соответствует группе LDAP/AD.
- **User** `{id, name, jobRole, globalRole: admin | member}` + `ProjectMember {projectId, userId, role: manager | employee | viewer}`.
- **Issue** `{key: "CORP-N", typeId: task | bug | request, statusId, priorityId: low | medium | high | critical, assigneeId, reporterId, epicId, dueDate, labels[], links[], comments[], activity[]}`.
- **IssueLink** `{issueId, linkedIssueId, type: relates | blocks}`.
- **Направление** — не отдельная сущность: обычная задача, на которую ссылаются
  другие через `epicId`; несёт `color`, `tStart`/`tSpan` для таймлайна.
- **Workflow** `{statuses: [{id, sid, name, category}], transitions: [{from, to}]}`.

Типы `story`/`epic` слиты в `task` (миграция 002); приоритетов было 5, стало 4
(миграция 013); спринты удалены целиком (миграция 012). Поле `points` осталось в
схеме, но из карточки убрано.

## Оформление

Светлая / тёмная / системная тема + 6 фоновых пресетов. Палитра — токены
(`--c-*` на `:root` / `:root[data-theme="dark"]`), `@theme` лишь ссылается на них,
поэтому утилитарные классы (`bg-canvas`, `text-ink`, …) резолвятся по теме
на лету. Выбор хранится в `localStorage`; переключатель — в меню профиля
(«Оформление»).

## Стек

Клиент: React 18, TypeScript, Vite 6, Tailwind CSS 4. Без внешних UI-библиотек —
иконки, дропдауны, модалки и тосты написаны вручную; роутинг — хэш вручную в `App.tsx`.

Сервер: Fastify 5, PostgreSQL (`pg`), `@fastify/jwt`, `zod`, `bcryptjs`, `ldapts`,
`nodemailer`, `@aws-sdk/*` (драйвер S3). Миграции — plain SQL в `server/migrations/`,
по одной транзакции на файл, отслеживаются в `schema_migrations`.
